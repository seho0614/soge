# 소개뱅크 다국어 kit 개발 설계 v1.0

Oct 4, 2026 · @박세호

## 0. 결론과 전제

다국어는 별도 묶음이 아니라 **본 kit 에 꺼진 상태로 넣습니다.** 화면 문구가 `sgb/site` 의 코드 안에 한글로 적혀 있어, 떼어 낸 묶음으로는 적용할 수 없습니다. 스위치(`i18n.enabled`)를 켜기 전까지는 지금과 똑같이 한국어로만 동작합니다.

| 항목 | 설계 값 |
| --- | --- |
| 정본 | 한국어. 번역이 없거나 낡으면 한국어로 보임 |
| 1차 언어 | 영어 (제안값 · 결정 필요) |
| 대상 | 사용자 웹(`sgb/site`). 운영 화면(`sgb/web`)은 한국어 유지, 「번역 관리」 탭만 추가 |
| 문구 저장 | 한국어 원문은 코드의 문구 파일, 번역문은 DB (승인된 것만 노출) |
| 언어 판별 | 회원 설정 → 쿠키 → 브라우저 → 한국어. 주소(URL)는 바꾸지 않음 |
| 번역 초안 | 번역 엔진을 갈아 끼우는 구조. 운영은 n8n `translate`, 개발과 점검은 모의 엔진 |
| 납품 | 5단계. 단계마다 kit 한 판 (zip + tar · 시안 포함) |

**추가 (10/04)** — 게시물과 등록 글도 번역 대상에 넣었습니다. 방식 · DB · API · 화면은 10장에, 작업 순서는 절차 탭 6-3 에 있습니다.

**실측 반영 (10/05)** — kit v10.16 을 열어 0단계 실측을 마쳤습니다. 아래 본문에서 바뀌는 13건은 「0단계 실측 보고」 탭 6장에 있고, 본문은 1단계 판을 낼 때 그 표대로 고칩니다. 그때까지 두 곳이 다르면 실측 보고가 맞습니다.

### 이 문서의 전제

아래 설계는 다음을 기준으로 작성했습니다. 조건이 다르면 알려 주십시오.

1. 기준 kit 은 v10.16 (`SGB_DevDocker_Integrated_20261002_v10_16`) 입니다.
2. 오늘 작성한 「AI 적용 목록 · 자동화 설계」 4장(다국어 설계)을 개발 수준으로 구체화했습니다. 표 이름과 API 주소는 그 문서의 가칭을 그대로 씁니다.
3. 지원 언어와 여는 시점은 아직 결정 전이라 제안값(영어 먼저)으로 썼습니다. 언어가 달라져도 구조는 같습니다.
4. 이 대화에서는 kit 을 다시 열어 보지 못했습니다. 구조는 앞 대화의 실측과 프로젝트 문서에 근거합니다. 실측 내용: 사용자 웹은 `<html lang="ko">` 고정이고, 번역 라이브러리 · 언어 컬럼 · 번역 표가 없습니다.

| 10/04 AI 적용 목록 4장 | 새 표 3 + 컬럼 1 | 새 표 4 + 컬럼 1 | 화면 문구 원문을 등록하는 표(`i18n_sources`)가 있어야 낡은 번역을 찾을 수 있음 (3장) |

## 1. 방식 선택

추천 조합은 **원문은 파일 · 번역문은 DB · 쿠키로 언어 판별 · next-intl · 엔진 교체형**입니다. 네 가지 선택을 각각 비교했습니다.

### 1-1. 문구를 어디에 두는가

| 방식 | 좋은 점 | 나쁜 점 | 판정 |
| --- | --- | --- | --- |
| A. 원문과 번역문 모두 파일 | 단순함. DB 변경 없음 | 번역 한 줄을 고쳐도 kit 을 다시 배포. 승인 기록이 남지 않음 | 채택 안 함 |
| B. 원문은 파일, 번역문은 DB | 운영 화면에서 고치고 승인하면 배포 없이 반영. 낡은 번역을 DB 가 찾아냄 | 원문을 DB 에 등록하는 절차가 하나 생김 | **추천** |
| C. 원문과 번역문 모두 DB | 운영이 한국어 문구도 고칠 수 있음 | 코드와 DB 가 어긋나면 화면에 빈 글자가 나옴 | 채택 안 함 |

### 1-2. 어떤 언어로 보여 줄지 어떻게 아는가

| 방식 | 좋은 점 | 나쁜 점 | 판정 |
| --- | --- | --- | --- |
| A. 쿠키 (주소는 그대로) | 내부 링크 · 시안 경로 짝 · 검정 스크립트를 고치지 않음 | 영어 화면이 검색엔진에 따로 잡히지 않음 | **1차 추천** |
| B. 주소에 언어 (`/en/…`) | 검색 노출. 주소를 공유해도 언어가 유지됨 | 내부 링크 전부와 경로 검사를 고쳐야 함 | 해외 검색 유입이 목표가 될 때 |
| C. 언어별 도메인 | 나라별 운영이 분리됨 | 인증서 · DNS · 로그인 쿠키를 따로 관리 | 채택 안 함 |

A 로 시작해도 문구 키와 DB 구조는 B 에서 그대로 씁니다. 나중에 B 로 옮길 때 다시 하는 일은 링크와 경로뿐입니다.

### 1-3. 사용자 웹의 번역 도구

| 방식 | 좋은 점 | 나쁜 점 | 판정 |
| --- | --- | --- | --- |
| A. next-intl | 서버 · 클라이언트 컴포넌트 모두 지원. 복수형 · 날짜 · 숫자 형식 포함. 주소를 바꾸지 않는 설정을 공식 문서가 안내 | 의존 패키지 1개 추가. kit 의 Next.js 버전과 맞는지 확인 필요 | **추천** |
| B. 직접 만든 `t()` 함수 | 의존 패키지 없음 | 영어의 단수와 복수, 날짜 형식을 직접 구현 | 버전이 맞지 않을 때의 대안 |

### 1-4. 번역 초안을 누가 만드는가

| 엔진 | 좋은 점 | 나쁜 점 | 쓰는 곳 |
| --- | --- | --- | --- |
| `N8N` — n8n `translate` 워크플로우 | 10/04 설계 그대로. 용어집 반영, 출력 검사, 실행 기록이 한 길 | 자동화 서버와 모델 키가 있어야 함 | 운영 (**추천**) |
| `MANUAL` — 사람이 직접 입력 | 외부 의존과 호출비가 없음 | 문구가 많으면 느림 | 엔진이 없을 때의 기본값 |
| `MOCK` — 모의 번역 | 인터넷 없이 로컬 점검이 끝까지 돎 | 실제 번역이 아님 (`[en] 원문` 형태) | 개발 · `realcheck` |

엔진은 설정 값 `i18n.engine` 하나로 바꿉니다. 번역 API(예: 9/23 설계의 Google 번역)를 쓰려면 같은 자리에 엔진을 하나 더 꽂으면 됩니다.

## 2. 전체 구조

&#91;embedded content: 문구의 길 · 칸 9개 · 노출 규칙 1곳\]

한국어 원문은 사용자 웹 안에 들어 있어, 번역을 내려 주는 서버가 응답하지 않아도 화면은 한국어로 나옵니다. 번역문은 `v_i18n_live` 를 통과한 것만 내려가며, 원문의 해시가 달라진 번역은 여기서 빠집니다. 번역 엔진은 초안만 만들고, 승인은 운영 화면에서 사람이 합니다.

## 3. DB 설계

새 표 4개, 컬럼 1개, 뷰 4개, 설정 5개를 마이그레이션 하나로 넣습니다. 기존 표는 `accounts` 에 컬럼 하나를 더하는 것 말고는 건드리지 않습니다.

### 3-1. 목록

| 이름 | 종류 | 내용 | 넣는 단계 |
| --- | --- | --- | --- |
| `i18n_sources` | 표 (신규 제안) | 화면 문구의 한국어 원문과 해시. 배포 때 문구 파일에서 옮겨 적음 | 1 |
| `i18n_texts` | 표 | 고정 문구 번역. `DRAFT` · `APPROVED` | 1 |
| `i18n_glossary` | 표 | 용어집. 고유 이름을 항상 같은 말로 | 1 |
| `content_translations` | 표 | 사용자 글 번역 저장 | 4 |
| `accounts.locale` | 컬럼 | 회원의 언어 설정. 비어 있으면 쿠키 → 브라우저 순 | 1 |
| `v_i18n_source` | 뷰 | 모든 영역의 현재 원문을 한 모양으로 | 1 |
| `v_i18n_live` | 뷰 | 화면에 내보낼 번역. 승인됐고 낡지 않은 것만 | 1 |
| `v_i18n_stale` | 뷰 | 원문이 바뀌어 낡은 번역 | 1 |
| `v_i18n_coverage` | 뷰 | 영역과 언어별 번역 비율 | 1 |

### 3-2. 마이그레이션 (예시)

파일 위치는 `sgb/prisma/migrations/<다음 번호>_i18n/migration.sql` 입니다. 번호는 kit 의 마지막 마이그레이션 다음으로 붙입니다.

```sql
-- 1) 화면 문구 원문 — 코드의 문구 파일(ko.json)을 배포 때 그대로 옮겨 적는다
CREATE TABLE i18n_sources (
  domain      text NOT NULL DEFAULT 'ui',
  key         text NOT NULL,                 -- 예: 'consult.form.submit'
  text_ko     text NOT NULL,
  source_hash text NOT NULL,                 -- md5(text_ko). 항상 DB 가 계산
  note        text,                          -- 번역할 때 참고할 설명
  retired_at  timestamptz,                   -- 코드에서 사라진 키
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (domain, key)
);

-- 2) 고정 문구 번역 — 승인된 것만 노출
CREATE TABLE i18n_texts (
  domain      text NOT NULL,                 -- ui | code_label | notification | faq | terms
  key         text NOT NULL,
  locale      text NOT NULL CHECK (locale ~ '^[a-z]{2}(-[A-Z]{2})?$' AND locale <> 'ko'),
  text        text NOT NULL,
  source_hash text NOT NULL,                 -- 번역할 때의 원문 해시
  status      text NOT NULL DEFAULT 'DRAFT' CHECK (status IN ('DRAFT','APPROVED')),
  made_by     text NOT NULL CHECK (made_by IN ('MODEL','HUMAN','MOCK')),
  approved_by uuid,
  approved_at timestamptz,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (domain, key, locale),
  CHECK (status <> 'APPROVED' OR approved_by IS NOT NULL)   -- 승인자 없는 승인은 없다
);

-- 3) 용어집
CREATE TABLE i18n_glossary (
  term_ko text NOT NULL,
  locale  text NOT NULL,
  term    text NOT NULL,
  note    text,
  PRIMARY KEY (term_ko, locale)
);

-- 4) 회원의 언어 설정
ALTER TABLE accounts ADD COLUMN locale text;

-- 5) 현재 원문 — 1단계는 화면 문구만. 알림 · 자주 묻는 질문은 4단계에서 UNION ALL 로 붙인다
CREATE VIEW v_i18n_source AS
SELECT domain, key, text_ko, source_hash
  FROM i18n_sources
 WHERE retired_at IS NULL;

-- 6) 화면에 내보낼 번역 — "승인됨 + 원문이 그대로" 를 여기 한 곳에서만 정의
CREATE VIEW v_i18n_live AS
SELECT t.domain, t.key, t.locale, t.text
  FROM i18n_texts t
  JOIN v_i18n_source s ON s.domain = t.domain AND s.key = t.key
 WHERE t.status = 'APPROVED'
   AND t.source_hash = s.source_hash;

-- 7) 낡은 번역
CREATE VIEW v_i18n_stale AS
SELECT t.domain, t.key, t.locale, t.status, t.updated_at
  FROM i18n_texts t
  JOIN v_i18n_source s ON s.domain = t.domain AND s.key = t.key
 WHERE t.source_hash <> s.source_hash;
```

`content_translations` 의 확정 정의는 10-4 에 있고 4단계의 마이그레이션에 넣습니다. `v_i18n_coverage` 는 영역 · 언어별로 원문 수, 승인 수, 초안 수, 낡은 수, 없는 수를 셉니다.

### 3-3. 설정 값

kit 의 설정 표에 넣습니다 (v10.14 의 `poll.*` · `sns.*` 와 같은 방식).

| 키 | 처음 값 | 뜻 |
| --- | --- | --- |
| `i18n.enabled` | `false` | 꺼져 있으면 언어 고르기가 보이지 않고 항상 한국어 |
| `i18n.locales` | `en` | 고를 수 있는 언어. 쉼표로 나눔 |
| `i18n.engine` | `MANUAL` | `MANUAL` · `MOCK` · `N8N` |
| `i18n.content_translate` | `false` | 사용자 글 「번역 보기」 (4단계) |
| `i18n.guest_daily_limit` | `0` | 비회원의 「번역 보기」 하루 횟수. 0 이면 회원만 |

### 3-4. 지켜야 할 규칙 세 가지

1. **노출 규칙은 뷰 하나.** 서버는 `v_i18n_live` 만 읽습니다. 승인되지 않았거나 낡은 번역은 어떤 길로도 화면에 나가지 않습니다.
2. **해시는 DB 가 계산.** 원문 등록과 번역 저장 모두 `md5(text_ko)` 를 SQL 에서 계산합니다. 서버 코드와 DB 가 서로 다른 값을 내는 일을 막습니다.
3. **승인 때 변수 검사.** 번역문의 변수 자리(`{name}` 등)가 원문과 다르면 서버가 승인을 거부합니다. 승인과 수정은 감사 기록에 남깁니다 (`I18N_APPROVE` · `I18N_UPDATE`).

## 4. 백엔드 · API 설계

모듈 하나(`sgb/src/modules/i18n/`)와 스크립트 두 개를 새로 만들고, API 는 10개를 더합니다 (4-2 표의 8번은 메서드가 둘). 기존 모듈에는 「언어 헤더 읽기」 한 곳만 넣습니다. 파일과 주소 이름은 가칭입니다.

### 4-1. 파일 구성

```
sgb/src/modules/i18n/
  i18n.controller.ts          공개 · 회원 API (문구 묶음, 내 언어)
  i18n-admin.controller.ts    운영 API (목록 · 저장 · 초안 · 승인 · 용어집)
  i18n.service.ts             v_i18n_live 조회, 묶음 버전 계산
  i18n-admin.service.ts       초안 만들기 · 승인 · 감사 기록
  i18n.dto.ts                 요청 · 응답 모양 (OpenAPI 응답 스키마 포함)
  i18n-check.ts               번역 검사 규칙 (승인과 엔진 출력에 같이 씀)
  locale.ts                   X-Locale 헤더 → 지원 언어 판정
  translator/
    translator.port.ts        엔진 공통 모양
    manual.translator.ts      초안을 만들지 않음 (사람이 입력)
    mock.translator.ts        '[en] 원문' 을 돌려줌 (개발 · 점검)
    n8n.translator.ts         n8n translate 워크플로우 호출
sgb/scripts/
  i18n-sync.js                site/messages/ko.json → i18n_sources 등록
  check-i18n.sh               검정: 한글 하드코딩 · 키 누락 · 변수 불일치
```

`i18n-sync.js` 에는 선택 기능이 둘 있습니다. `--mock <언어>` 는 개발 DB 에 모의 번역을 채우고(운영에서는 동작하지 않음), `--export <언어>` 는 승인된 번역을 파일로 내보냅니다.

### 4-2. API 목록

| # | 메서드 · 주소 | 누가 | 무엇 | 단계 |
| --- | --- | --- | --- | --- |
| 1 | GET `/i18n/{locale}` | 누구나 | 승인된 문구 묶음과 버전 | 1 |
| 2 | PATCH `/me/locale` | 회원 | 내 언어 설정 저장 (비우기 가능) | 1 |
| 3 | GET `/admin/i18n/texts` | ADMIN · SUPER | 목록과 번역 비율. 상태로 거름: 없음 · 초안 · 승인 · 낡음 | 3 |
| 4 | PUT `/admin/i18n/texts` | ADMIN · SUPER | 번역 한 건 저장. 저장하면 초안 상태 | 3 |
| 5 | POST `/admin/i18n/texts/draft` | ADMIN · SUPER | 고른 문구의 초안 만들기 (엔진 호출) | 3 |
| 6 | POST `/admin/i18n/texts/approve` | ADMIN · SUPER | 승인. 검사를 통과해야 함 | 3 |
| 7 | GET `/admin/i18n/glossary` | ADMIN · SUPER | 용어집 목록 | 3 |
| 8 | PUT · DELETE `/admin/i18n/glossary` | ADMIN · SUPER | 용어 추가 · 수정 · 삭제 | 3 |
| 9 | POST `/content/{type}/{id}/translate` | 회원 (설정에 따라 비회원) | 사용자 글 「번역 보기」 | 4 |

기존 API 한 개를 넓힙니다: `/site-settings/public` 응답에 `i18n.enabled` 와 `i18n.locales` 를 더합니다.

### 4-3. 서버가 만드는 글의 처리

| 서버가 만드는 글 | 처리 | 단계 |
| --- | --- | --- |
| 오류 안내 | 서버는 오류 코드를 주고, 화면이 `errors.<코드>` 문구로 바꿔 보여 줌. 문구가 없으면 서버의 한국어 안내 그대로 | 2 |
| 코드 이름 (업종 · 상태 등) | `X-Locale` 헤더를 보고 번역된 이름을 내려 줌. 없으면 한국어 | 2 |
| 알림 (메일 · 앱 안 알림) | 받는 사람의 `accounts.locale` 로 템플릿을 고름. 알림톡은 한국어만 | 4 |
| 약관 · 계약 · 법정 고지 | 한국어본이 정본. 번역본은 참고용 표시 | 4 |

오류 응답에 코드가 빠짐없이 들어 있는지는 0단계 실측에서 확인합니다.

### 4-4. 번역 엔진 연결 (예시 코드)

아래 코드는 구조를 보여 주는 예시이며, 이 대화에서 실행해 보지 않았습니다.

```ts
// translator/translator.port.ts
export interface TranslateItem   { key: string; text: string; note?: string }
export interface TranslateResult { key: string; text?: string; error?: string }
export interface GlossaryTerm    { ko: string; to: string }

export interface Translator {
  readonly name: 'MANUAL' | 'MOCK' | 'N8N';
  translate(items: TranslateItem[], target: string, glossary: GlossaryTerm[]): Promise<TranslateResult[]>;
}

// translator/mock.translator.ts — 인터넷 없이 로컬 점검이 끝까지 돌게 한다
export class MockTranslator implements Translator {
  readonly name = 'MOCK' as const;
  async translate(items: TranslateItem[], target: string) {
    return items.map((i) => ({ key: i.key, text: `[${target}] ${i.text}` }));
  }
}
```

```ts
// i18n-check.ts — 어긋난 항목의 이름을 돌려준다. 빈 배열이면 통과
const ARG = /\{\s*([A-Za-z0-9_]+)\s*[,}]/g;                 // {name} 과 {count, plural, …} 의 이름
const names = (s: string) => [...new Set([...s.matchAll(ARG)].map((m) => m[1]))].sort().join(',');
const digits = (s: string) => (s.match(/\d+/g) ?? []).sort().join(',');

export function checkTranslation(src: string, out: string, glossary: GlossaryTerm[]): string[] {
  const errs: string[] = [];
  if (names(src) !== names(out)) errs.push('VARS');                       // 변수 자리가 다름 → 승인 거부
  if (digits(src) !== digits(out)) errs.push('NUMBERS');                  // 숫자가 다름 → 경고
  for (const g of glossary)
    if (src.includes(g.ko) && !out.toLowerCase().includes(g.to.toLowerCase())) errs.push(`GLOSSARY:${g.ko}`);
  if (out.length > Math.max(src.length * 3, 24)) errs.push('TOO_LONG');   // 버튼이 넘침
  return errs;
}
```

| 검사 | 고정 문구 (사람이 승인) | 사용자 글 (자동 노출 · 4단계) |
| --- | --- | --- |
| `VARS` 변수 자리 | 승인 거부 | 번역 실패로 처리, 원문을 보여 줌 |
| `NUMBERS` 숫자 | 경고만. 「1만원 → 10,000 KRW」처럼 맞는 번역도 걸리므로 사람이 판단 | 번역 실패로 처리 |
| `GLOSSARY` 용어 | 경고 | 경고 기록 |
| `TOO_LONG` 길이 | 경고 | 번역 실패로 처리 |

### 4-5. 반영 속도

사용자 웹은 문구 묶음을 1분 동안 기억합니다 (공개 설정과 같은 방식). 운영 화면에서 승인하면 1분쯤 뒤 화면에 반영되고, 운영 화면에 그 안내를 적습니다.

## 5. 사용자 웹 설계

가장 큰 일은 화면 코드 안의 한글을 문구 키로 바꾸는 것입니다. 틀은 next-intl 의 「주소를 바꾸지 않는 설정」을 따릅니다 ([공식 문서](https://next-intl.dev/docs/getting-started/app-router)). 아래 코드는 예시이며 이 대화에서 실행해 보지 않았습니다.

### 5-1. 파일 구성

```
sgb/site/
  messages/ko.json                  한국어 원문 (정본)
  next.config.*                     next-intl 플러그인 연결
  src/i18n/request.ts               요청마다 언어와 문구를 정함
  src/i18n/messages.ts              ko.json 위에 승인된 번역을 덮어씀 (1분 기억)
  src/components/LocaleSwitch.tsx   언어 고르기
  src/app/layout.tsx                <html lang> 을 고른 언어로, 문구를 클라이언트에 전달
  src/lib/api.ts                    서버 호출에 X-Locale 헤더를 붙임
```

### 5-2. 언어를 정하는 순서

판별은 쿠키 `sgb_locale` 하나로 합니다. 회원 설정은 로그인할 때와 언어를 바꿀 때 이 쿠키에 맞춰 둡니다. 그래서 순서는 회원 설정 → 쿠키 → 브라우저 → 한국어가 됩니다.

```ts
// site/src/i18n/request.ts
import { cookies, headers } from 'next/headers';
import { getRequestConfig } from 'next-intl/server';
import { getI18nSettings, loadMessages } from './messages';

export default getRequestConfig(async () => {
  const { enabled, locales } = await getI18nSettings();      // /site-settings/public (1분 기억)
  let locale = 'ko';
  if (enabled) {
    const picked  = (await cookies()).get('sgb_locale')?.value;
    const browser = (await headers()).get('accept-language')?.split(',')[0]?.slice(0, 2);
    locale = [picked, browser].find((l) => l === 'ko' || (l && locales.includes(l))) ?? 'ko';
  }
  return { locale, messages: await loadMessages(locale) };
});
```

```ts
// site/src/i18n/messages.ts
import ko from '../../messages/ko.json';
import { apiGet } from '@/lib/api';            // kit 의 호출 함수 이름에 맞춤

export async function loadMessages(locale: string) {
  if (locale === 'ko') return ko;
  try {
    const { messages } = await apiGet(`/i18n/${locale}`, { revalidate: 60 });
    return overlay(ko, messages);              // 번역이 있는 키만 덮어씀 → 없는 키는 한국어
  } catch {
    return ko;                                 // 서버가 응답하지 않아도 한국어로 화면이 나옴
  }
}

// 'mal.consult.submit' 같은 점 표기 키를 중첩 객체의 제자리에 넣는다
function overlay(base: any, flat: Record<string, string>) {
  const out = structuredClone(base);
  for (const [key, text] of Object.entries(flat)) {
    const path = key.split('.');
    let node = out;
    for (const p of path.slice(0, -1)) node = node?.[p];
    const leaf = path.at(-1);                  // kit 의 형 검사 때문에 path[path.length - 1] 은 빌드가 멈춤
    if (leaf && node && typeof node[leaf] === 'string') node[leaf] = text;   // 원문에 없는 키는 버림
  }
  return out;
}
```

### 5-3. 문구 키 규칙

키는 `<계열>.<묶음>.<요소>` 세 마디입니다. 첫 마디는 화면 ID 의 계열을 소문자로 씁니다. 관 이름이 바뀌어도 키는 바뀌지 않고, 화면 목록과 바로 대조됩니다.

| 첫 마디 | 대상 | 예 |
| --- | --- | --- |
| `common` | 헤더 · 푸터 · 공용 버튼 | `common.header.login` |
| `errors` | 오류 안내 | `errors.AUTH_EXPIRED` |
| `hom` | 메인 · 소개광장 · 로그인 (`SB-HOM-…`) | `hom.poll.vote` |
| `mal` | 안심소개 (`SB-MAL-…`) | `mal.consult.submit` |
| `hlt` | 소개뱅크몰 건강관 (`SB-HLT-…`) | `hlt.order.pay` |
| `myp` · `afc` · 그 밖 | 나의공간 · 제휴 파트너 등 화면 ID 계열 그대로 | `myp.account.save` |

1. 한 문장은 한 키입니다. 문장을 잘라 이어 붙이지 않고, 바뀌는 부분은 변수(`{name}`)로 둡니다.
2. 수에 따라 달라지는 말은 복수형 문법으로 씁니다.
3. 금액 · 날짜는 문구에 글자로 넣지 않고 형식 함수로 만듭니다. 통화는 원화 그대로입니다.
4. 글자가 같아도 쓰임이 다르면 키를 나눕니다 (예: 버튼의 「신청」과 상태의 「신청」).
5. 키는 정하면 바꾸지 않습니다. 바꾸면 그 키의 번역이 떨어져 나갑니다.

### 5-4. 화면 코드를 바꾸는 모양

```tsx
// 바꾸기 전
<button className="btn">인증번호 받고 신청</button>
<p>참여 {count}명</p>

// 바꾼 뒤 — 서버 컴포넌트
import { getTranslations } from 'next-intl/server';
const t = await getTranslations('mal.consult');
<button className="btn">{t('submit')}</button>

// 바꾼 뒤 — 클라이언트 컴포넌트 ('use client')
import { useTranslations } from 'next-intl';
const t = useTranslations('hom.poll');
<p>{t('voters', { count })}</p>
```

```json
    "voters": "참여 {count}명"              // "{count, plural, one {# participant} other {# participants}}"
```

### 5-5. 언어 고르기

- 위치는 공통 헤더와 메인 전용 헤더 두 곳입니다. `i18n.enabled` 가 꺼져 있으면 보이지 않습니다.
- 고르면 쿠키를 심고, 로그인 상태면 `PATCH /me/locale` 을 부른 뒤 화면을 새로 그립니다.
- 내 정보 화면에 같은 설정을 둡니다.

운영자 계정(ADMIN · SUPER)으로 로그인하면 스위치가 꺼져 있어도 언어 고르기가 보입니다. 공개 전에 영어 화면을 미리 보는 길입니다. 사용자 웹이 로그인한 계정의 역할을 알 수 있는지는 0단계에서 확인합니다.

### 5-6. 이 kit 에서 조심할 곳

| 곳 | 문제 | 설계 |
| --- | --- | --- |
| 메인의 자른 그림 58장 | 그림 속 글자는 번역되지 않음 | 1차는 그림 그대로, 글자로 된 부분과 대체 글만 번역. 그림에 글자가 얼마나 있는지 0단계에서 확인 |
| 메인의 `content.ts` (내용 두 벌) | 내용이 코드가 아니라 자료 파일에 있음 | 그림 내용(`sampleContent`)은 키로 옮기고, 서버 자료(`liveContent`)는 서버 값 그대로 |
| 화면 그리기 방식 | 쿠키를 읽는 화면은 요청마다 새로 그림 | 지금 미리 만들어 두는 화면이 있으면 속도가 달라짐. 0단계에서 확인 |
| #418 (서버와 브라우저의 그림 불일치) | 브라우저에서 언어를 다시 판별하면 재발 | 언어는 서버에서만 정하고 브라우저 코드는 받은 값만 씀 |
| 클라이언트로 넘기는 문구 | 전체를 넘기면 화면이 무거워짐 | 화면이 쓰는 계열만 골라 넘김 |
| Tailwind 적용 작업 | 같은 화면 파일을 두 작업이 함께 고치면 충돌 | 흐름 단위로 순서를 정함 (절차 탭 4장) |

## 6. 운영 화면 · 시안

운영 화면은 번역하지 않고 「번역 관리」 탭 하나를 더합니다. 시안에는 새 화면 4종과 언어 전환 시연을 넣습니다.

### 6-1. 운영 화면 「번역 관리」

파일은 `sgb/web/src/app/admin/I18n.tsx`, 화면 ID 는 `SB-ADM-I18-010` (둘 다 가칭) 입니다.

| 구역 | 보이는 것 | 할 수 있는 일 |
| --- | --- | --- |
| 번역 비율 | 언어별 원문 수 · 승인 · 초안 · 낡음 · 없음 | 숫자를 누르면 그 상태만 목록에 |
| 문구 목록 | 키 · 한국어 원문 · 번역문 · 상태 · 검사 경고 | 번역문 고치기, 여러 줄 골라 승인 |
| 초안 만들기 | 번역이 없거나 낡은 문구 수 | 고른 문구의 초안 만들기. 엔진이 `MANUAL` 이면 버튼을 감춤 |
| 용어집 | 한국어 용어 · 언어 · 정한 번역 · 메모 | 추가 · 수정 · 삭제 |
| 설정 | 켜짐 · 언어 목록 · 엔진 | 바꾸기 (SUPER 만) |

화면에 두 가지 안내를 적습니다: 「승인하면 1분쯤 뒤 사용자 화면에 반영됩니다」, 「원문이 바뀐 번역은 다시 승인할 때까지 한국어로 보입니다」.

### 6-2. 사용자 웹에서 달라지는 화면

| 화면 | 달라지는 것 | 단계 |
| --- | --- | --- |
| 공통 헤더 · 메인 전용 헤더 | 언어 고르기 | 1 |

### 6-3. 시안에 넣는 것

시안(`sgb/spec/proto.html`) 전체를 영어로 만들지는 않습니다. 대표 흐름만 영어 사전을 넣고, 나머지 화면은 한국어로 남깁니다. 이것이 「번역이 없으면 한국어」 규칙의 시연이 됩니다.

| 시안 화면 | 시연 내용 | 단계 |
| --- | --- | --- |
| 헤더의 언어 고르기 | 누르면 헤더 · 푸터 · 메인 · 안심소개 상담 신청이 영어로 바뀜 | 1 · 2 |
| 내 정보의 언어 설정 | 고르고 저장 | 1 |
| 운영 「번역 관리」 | 목록 · 초안 만들기 · 승인 · 낡은 번역 표시 · 용어집 | 3 |
| 등록 글의 「번역 보기」 | 번역 보기와 원문 보기 전환, 「자동 번역」 표시 | 4 |

- 시안의 영어 사전은 손으로 따로 쓰지 않고, 실제 웹의 문구 파일과 승인된 번역에서 뽑아 넣습니다. 시안과 실제 웹의 문구가 어긋나지 않습니다.
- 새 화면은 시안의 경로 표에 등록해 「경로 짝」 검정과 「시연 보장」(무반응 버튼 없음)을 통과시킵니다.

## 8. 위험과 해결 · 비용과 자원

가장 큰 위험은 번역이 아니라 **문구를 옮기다 한국어 화면이 달라지는 것**입니다. 그래서 스위치를 끈 상태에서 옮기기 전후의 화면이 같아야 통과시킵니다.

## 10. 게시물 · 등록 글 번역 (추가)

게시물과 등록 글은 **쓴 사람과 틀렸을 때의 피해**에 따라 세 방식으로 나눠 번역합니다. 운영이 쓴 글은 승인 후 노출하고, 회원이 쓴 글은 자동 번역해 「자동 번역」 표시와 함께 보여 줍니다.

「등록 문서」는 소개장터 · 안심소개 · 소개창업에 올리는 등록 글의 제목과 본문으로 읽었습니다. 첨부 파일(PDF · 그림 속 글자)은 번역하지 않습니다. 뜻이 다르면 알려 주십시오.

### 10-1. 세 가지 방식

| 방식 | 언제 번역하나 | 사람의 확인 | 화면 표시 | 저장하는 곳 |
| --- | --- | --- | --- | --- |
| ① 미리 번역 + 승인 | 운영이 글을 쓴 뒤 「번역 관리」에서 | 승인한 것만 노출 | 표시 없음 | `i18n_texts` |
| ② 게시될 때 자동 번역 | 검수 통과 · 게시 뒤 배치가 | 사후 (신고 · 표본) | 「자동 번역 · 원문 보기」 | `content_translations` |
| ③ 누를 때 번역 | 읽는 사람이 「번역 보기」를 누를 때 | 사후 (신고) | 「자동 번역 · 원문 보기」 | `content_translations` |

②는 목록에서도 번역된 제목이 보이고 비용이 글 수에 비례합니다. ③은 비용이 누른 횟수에 비례하고, 목록은 원문으로 남습니다.

### 10-2. 글의 종류별 방식

| 글 | 쓰는 사람 | 방식 | 번역하는 칸 | 비고 |
| --- | --- | --- | --- | --- |
| 공지 · 자주 묻는 질문 | 운영 | ① | 제목 · 본문 | 고정 문구와 같은 승인 흐름 |
| 「이건 어때?」 투표 | 운영 | ① | 제목 · 설명 · 보기 | `polls` · `poll_options` |
| 등록 글 (소개장터 · 안심소개 · 소개창업) | 회원 · 인증업체 | ② | 제목 · 본문 | 금액 · 지역 · 업종은 번역하지 않고 서버 값과 코드 이름으로 |
| 자격 확인 업종의 등록 글 (의료 · 보험 등) | 인증업체 | 번역 안 함 | — | 번역문이 광고 규정의 대상인지 법무 확인 뒤 |
| 소개광장 게시글 | 회원 | 제목 ② · 본문 ③ | 제목 · 본문 | 제목은 짧아 미리, 본문은 누를 때 |
| 댓글 · 후기 · 1:1 대화 | 회원 | ③ | 본문 |  |
| 소개뱅크몰 상품 설명 | 판매자 | 번역 안 함 | — | 법무 확인 뒤 (8-1 의 6번) |
| 첨부 파일 · 그림 속 글자 | — | 번역 안 함 | — | 범위 밖 |

### 10-3. 지키는 규칙

1. **게시 중인 글만.** 검수 전 · 반려 · 숨김 · 삭제된 글은 번역하지 않습니다. 번역이 이미 있어도, 읽을 때 원문의 상태를 함께 보고 내보내지 않습니다.
2. **검수와 금칙어 판정은 원문으로.** 번역문은 판정에 쓰지 않습니다. 번역으로 검수를 비켜 갈 수 없습니다.
3. **보내기 전 연락처 가림.** 번역문에 연락처 모양이 새로 생기면 그 번역은 실패로 처리합니다.
4. **숫자가 다르면 버림.** 금액 · 기간 · 수량이 원문과 다른 번역은 내보내지 않고 원문을 보여 줍니다 (4-4 의 사용자 글 기준).
5. **원문이 바뀌면 낡음.** 다시 번역될 때까지 원문을 보여 줍니다.
6. **글쓴이에게는 항상 원문.** 자기 글은 번역되지 않은 모습으로 봅니다.
7. **검색은 원문 기준.** 영어 검색어로 한국어 글을 찾는 기능은 1차 범위 밖입니다.
8. **하루 상한.** 자동 번역 건수에 하루 상한을 두고, 넘으면 새 글부터 다음 날 이어서 합니다.

1차는 한국어 글을 외국어로 옮기는 방향만 다룹니다. 외국어로 쓴 글의 처리는 10-8 의 결정 사항입니다.

### 10-4. DB

새 표는 늘지 않습니다. `content_translations` 에 칸 넷을 더해 확정하고, 뷰 하나 · 설정 둘 · 배치 하나를 더합니다. 4단계의 마이그레이션에 넣습니다.

```sql
-- 사용자 글 번역 (② · ③) — 10/04 정의에 status · attempts · error · made_by 를 더함
CREATE TABLE content_translations (
  target_type text NOT NULL CHECK (target_type IN ('LISTING','POST','COMMENT','REVIEW','MESSAGE')),
  target_id   uuid NOT NULL,
  field       text NOT NULL CHECK (field IN ('title','body')),
  locale      text NOT NULL,
  text        text,                           -- 실패하면 비어 있음
  source_hash text NOT NULL,                  -- 번역할 때의 원문 해시
  status      text NOT NULL DEFAULT 'OK' CHECK (status IN ('OK','FAILED','HIDDEN')),
  attempts    int  NOT NULL DEFAULT 1,        -- 실패 3회면 배치가 더 시도하지 않음
  error       text,                           -- 검사에서 걸린 이름 (NUMBERS 등)
  made_by     text NOT NULL CHECK (made_by IN ('MODEL','MOCK','HUMAN')),   -- HUMAN = 운영이 고쳐 씀
  run_id      bigint,                         -- 에이전트 실행 기록 (있을 때)
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (target_type, target_id, field, locale),
  CHECK (status <> 'OK' OR text IS NOT NULL)
);
```

```js
const fs = require('fs'), path = require('path');
const root = path.join(__dirname, '..', 'site', 'src');
const rows = [];
(function walk(dir) {
  for (const name of fs.readdirSync(dir)) {
    const p = path.join(dir, name);
    if (fs.statSync(p).isDirectory()) { walk(p); continue; }
    if (!/\.(tsx?|jsx?)$/.test(name)) continue;
    const hits = fs.readFileSync(p, 'utf8').split('\n')
      .filter((l) => /[가-힣]/.test(l) && !/^\s*(\/\/|\*|\/\*)/.test(l));   // 주석 줄은 뺀다
    if (hits.length) rows.push([path.relative(root, p), hits.length]);
  }
})(root);
rows.sort((a, b) => b[1] - a[1]);
console.log('file,lines');
for (const r of rows) console.log(r.join(','));
console.error(`파일 ${rows.length}개 · 한글이 든 줄 ${rows.reduce((s, r) => s + r[1], 0)}줄`);
```

### 3-1. 작업 순서

1. 마이그레이션을 추가합니다 — 표 3 · 컬럼 1 · 뷰 4 · 설정 5 (설계 탭 3장).

5. 언어 고르기 부품과 내 정보의 언어 설정을 만듭니다.
6. 헤더와 푸터의 문구를 키로 옮깁니다. 첫 시범이며, 여기서 키 규칙을 확정합니다.

8. 시안에 언어 고르기와 언어 설정을 넣습니다.

## 4. 2단계 — 문구 추출

### 4-1. 흐름의 순서 (제안 · 0단계 결과로 확정)

| 순서 | 흐름 | 키의 첫 마디 |

헤더와 푸터는 1단계에서 이미 옮겼습니다.

### 4-2. 한 흐름의 작업 순서

1. 그 흐름의 Tailwind 적용이 끝났는지 확인합니다. 끝나지 않았으면 Tailwind 를 먼저 끝냅니다. 두 작업을 같은 판에 섞지 않습니다.
2. 옮기기 전의 한국어 화면을 저장합니다. 그 흐름의 주소를 모두 열어 화면의 글자만 뽑아 둡니다 (기준).
3. 화면 파일의 한글을 키로 바꾸고 `messages/ko.json` 에 원문을 넣습니다 (설계 탭 5-3 · 5-4).
4. `check-i18n.sh` 를 돌립니다 — 그 흐름의 폴더에 한글이 남지 않았는지, 쓰는 키가 모두 원문에 있는지 봅니다.
5. 한국어 화면의 글자를 다시 뽑아 기준과 대조합니다. **차이가 0 이어야** 다음으로 갑니다.
6. 개발 DB 에 모의 번역을 채우고 영어로 엽니다. 옮긴 문구는 전부 `[en]` 이 붙어 보입니다. 붙지 않은 글자가 빠진 문구입니다.
7. 그 흐름이 쓰는 API 의 코드 이름과 오류 안내에 `X-Locale` 을 반영합니다.
8. 시안에 반영합니다 (대표 흐름은 영어 사전 포함).
9. 공통 절차(7장)를 거쳐 포장합니다.

```bash
# 6번 — 개발 DB 에서만 동작. 모든 키에 '[en] 원문' 을 승인 상태로 채운다
node scripts/i18n-sync.js --mock en
```

이 명령은 운영 DB 에서 실행되면 안 됩니다. 운영 환경이면 아무것도 하지 않고 멈추게 만들고, 그 점을 「시험 안전」 검정에 넣습니다.

### 4-3. 한글이 남아도 되는 곳 (허용 목록)

| 곳 | 이유 |
| --- | --- |
| 주석과 개발용 기록 | 화면에 나오지 않음 |
| 서버가 내려 주는 자료를 그대로 보여 주는 자리 | 서버 쪽에서 처리 (설계 탭 4-3) |
| 사용자가 쓴 글 · 상품 설명 | 4단계의 「번역 보기」 |
| 약관 · 법정 고지의 본문 | 한국어본이 정본. 4단계에서 참고 번역 |

허용 목록은 파일 하나로 관리하고, 늘릴 때마다 이유를 적습니다.

### 4-4. 통과 기준 (흐름마다)

- [ ] 한국어 화면 대조에서 차이 0
- [ ] 그 흐름의 폴더에 허용 목록 밖의 한글 0
- [ ] 모의 번역 화면에서 `[en]` 이 붙지 않은 글자가 모두 「서버 글 · 사용자 글 · 그림」으로 설명됨
- [ ] 390px 에서 가로 넘침 0
- [ ] 통합 검정 실패 0

## 5. 3단계 — 번역 관리와 영어 승인

이 단계가 끝나고 아래 「켜는 조건」이 채워지면 영어를 켭니다. 번역문의 정본은 **운영 DB** 입니다. 승인은 운영 화면에서 사람이 합니다.

### 5-1. 작업 순서

1. 운영 API 7개, 검사 규칙, 감사 기록을 만듭니다 (설계 탭 4장).
2. 엔진 3종을 만듭니다. `N8N` 엔진이 부를 `translate` 워크플로우는 아직 설계만 있으므로, 이 단계에서 만들어 n8n 에서 돌려 확인하고 연동 묶음의 다음 판으로 냅니다.
3. 운영 화면에 「번역 관리」 탭을 만듭니다 (설계 탭 6-1).
4. 운영자 미리 보기를 만듭니다 — 운영자 계정(ADMIN · SUPER)으로 로그인하면 스위치가 꺼져 있어도 언어 고르기가 보입니다.
5. 번역 내보내기를 만듭니다 (`node scripts/i18n-sync.js --export en`). 내보낸 사본은 kit 에 실어 개발 DB 채우기와 시안의 영어 사전에 씁니다.
6. 시안에 「번역 관리」 화면을 넣습니다.
7. 공통 절차(7장)를 거쳐 포장하고 운영에 적용합니다. 스위치는 꺼진 채입니다.

### 5-2. 영어 번역을 만드는 순서 (운영 화면에서)

1. 용어집부터 채웁니다. 고유 이름(소개뱅크 · 소개장터 · 안심소개 · 소개창업 · 소개뱅크몰 · 소개광장 · 소개코드 · 소개비)의 영어 표기는 대표가 정합니다.
2. 흐름 순서대로 「초안 만들기」를 누릅니다. 엔진이 `MANUAL` 이면 직접 입력합니다.
3. 검토자가 읽고 고칩니다. 검사 경고(숫자 · 용어 · 길이)가 붙은 문구부터 봅니다.
4. 「승인」을 누릅니다. 변수 자리가 다른 문구는 승인되지 않습니다.
5. 운영자 미리 보기로 영어 화면을 흐름마다 끝까지 눌러 봅니다. 넘치는 버튼과 어색한 문구를 고쳐 다시 승인합니다.

kit 을 새로 적용해도 운영 DB 의 승인된 번역은 덮어쓰지 않습니다. kit 에 실린 사본 가운데 운영에 없는 문구만 초안으로 들어갑니다.

### 5-3. 켜는 조건

- [ ] 정한 범위(예: 흐름 1 \~ 3)의 번역 비율이 승인 100%
- [ ] 범위 밖의 화면이 한국어로 보인다는 점을 대표가 확인
- [ ] 법무 회신: 번역본 표시 방식 (설계 탭 9-2)
- [ ] 영어 화면에서도 동의는 한국어본으로 받고, 「한국어본이 우선」 안내가 영어로 보임
- [ ] 영어 문의를 누가 어떻게 받을지 확정
- [ ] 본인 확인 · 결제처럼 외부 업체가 띄우는 화면의 언어를 확인하고, 한국어로만 나오면 그 앞에 안내를 둠
- [ ] 운영자 미리 보기로 흐름마다 화면 점검을 마침

### 5-4. 켜기와 끄기

| 할 일 | 방법 | 걸리는 시간 |
| --- | --- | --- |
| 켜기 | 운영 화면 「번역 관리」 → 설정 → 켜짐 | 1분쯤 뒤 반영 |
| 끄기 (문제가 생겼을 때) | 같은 곳에서 꺼짐 | 1분쯤 뒤 전부 한국어 |
| 문구 하나만 되돌리기 | 그 번역을 고쳐 다시 승인, 또는 초안으로 내림 | 1분쯤 뒤 그 문구만 한국어 |

끄는 데 배포가 필요 없습니다. 이것이 번역문을 DB 에 두는 이유 가운데 하나입니다.

## 6. 4단계 — 확장

영어가 켜진 뒤에 하나씩 엽니다. 항목마다 여는 조건이 다르므로 묶지 않고 각각 kit 한 판으로 냅니다.

| 순서 | 항목 | 하는 일 | 여는 조건 |
| --- | --- | --- | --- |
| 1 | 알림 번역 (메일 · 앱 안 알림) | `v_i18n_source` 에 알림 템플릿을 붙이고, 보낼 때 받는 사람의 언어로 고름. 알림톡은 한국어만 | 영어 운영 중 |
| 2 | 자주 묻는 질문 번역 | `v_i18n_source` 에 `faqs` 를 붙임 | 영어 운영 중 |
| 3 | 약관 · 처리방침 참고 번역 | 번역본 맨 위에 「참고용 번역 · 한국어본 우선」 표시. 동의는 한국어본 | 약관 정식본 확정 + 법무 회신 |
| 4 | 사용자 글 「번역 보기」 | 마이그레이션(`content_translations`), API 1개, 연락처 가림, 횟수 제한, 「자동 번역」 표시와 신고 | 법무 회신(국외 전송) + `N8N` 엔진 운영 중 + 월 상한 설정 |
| 5 | 언어 추가 | 아래 절차. 개발은 거의 없음 | 수요 확인 + 그 언어를 읽을 검토자 |

### 6-1. 언어를 하나 늘리는 절차

1. 그 언어를 읽고 승인할 검토자를 정합니다.
2. 용어집에 그 언어의 표기를 넣습니다.
3. 「초안 만들기」 → 검토 → 승인을 흐름 순서대로 합니다 (5-2 와 같음).
4. 운영자 미리 보기로 화면을 점검합니다. 번역이 있는 언어는 공개 전에도 운영자가 고를 수 있습니다.
5. 설정 `i18n.locales` 에 그 언어를 더합니다. 이때부터 사용자에게 보입니다.

아랍어처럼 오른쪽에서 왼쪽으로 쓰는 언어는 화면 배치를 뒤집는 개발이 따로 필요합니다. 이 설계의 범위 밖입니다.

### 6-2. 「번역 보기」의 기능 검증

| # | 해 볼 것 | 맞는 결과 |
| --- | --- | --- |
| 1 | 영어 사용자가 등록 글에서 「번역 보기」를 누름 | 번역문과 「자동 번역 · 원문 보기」 표시 |
| 2 | 같은 글을 다시 누름 | 저장된 번역이 바로 나옴 (엔진을 다시 부르지 않음) |
| 3 | 글쓴이가 본문을 고친 뒤 누름 | 새로 번역함 |
| 4 | 본문에 전화번호가 든 글 | 엔진으로 보내는 글에 번호가 가려져 있음 |
| 5 | 검수를 통과하지 않은 글 | 번역하지 않음 |
| 6 | 하루 횟수를 넘김 | 안내와 함께 거절 |
| 7 | 엔진이 멈춤 | 「지금은 번역할 수 없습니다」 안내, 원문은 그대로 보임 |

### 6-3. 게시물 · 등록 글 번역의 작업 순서 (추가)

위 표의 2번과 4번을 넓혀 세 걸음으로 나눕니다. 걸음마다 kit 한 판을 냅니다. 설계는 설계 탭 10장입니다.

| 걸음 | 대상 | 하는 일 | 여는 조건 |
| --- | --- | --- | --- |
| A 운영 글 | 공지 · 투표 · 자주 묻는 질문 | 원문 뷰에 세 영역을 붙임. 「번역 관리」에 「운영 글」 영역. 조회 API 가 승인된 번역을 내려 줌 | 영어 운영 중. 엔진이 없어도 가능 |
| B 등록 글 | 세 관의 등록 글, 소개광장 글 제목 | 아래 작업 순서 | 법무 회신 + `N8N` 엔진 + 하루 상한 |
| C 번역 보기 | 게시글 본문 · 댓글 · 후기 · 1:1 대화 | 「번역 보기」 버튼과 API (6-2 의 검증) | B 와 같음 |

**B 의 작업 순서**

1. 0단계 결과로 등록 글 · 게시글 표의 상태 칸과 API 주소를 확정합니다.
2. 마이그레이션을 넣습니다 — `content_translations`, 대기 목록 뷰, 설정 2, 배치 한 줄.
3. 배치 `content_translate` 를 만듭니다: 대기 목록 → 연락처 가림 → 엔진 → 검사 → 저장. 실패는 사유와 함께 남깁니다.
4. 목록 · 상세 응답에 `translated` 묶음을 더합니다. 원문 칸은 건드리지 않고, 응답 모양을 API 문서에 적습니다.
5. 화면에 번역된 제목과 본문, 「자동 번역 · 원문 보기」, 번역 신고를 넣습니다.
6. 운영 화면 「번역 관리」에 「사용자 글」 구역을 넣습니다.
7. 시안에 등록 글 상세와 「사용자 글」 구역을 넣습니다.
8. 공통 절차(7장)를 거쳐 포장하고 적용합니다. `i18n.content_auto` 는 꺼진 채 나갑니다.
9. 하루 상한을 낮게 두고 켠 뒤 2주 동안 실패율과 신고 수를 봅니다.

**B 의 기능 검증**

## 7. 단계마다 거치는 공통 절차

kit 한 판을 낼 때마다 아래 일곱 가지를 순서대로 거칩니다. 하나라도 통과하지 못하면 그 판은 내지 않습니다.

| # | 절차 | 하는 일 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | 매트릭스 작성 | 그 판의 화면 · 백엔드 · API · DB 목록을 실제 이름과 화면 ID 로 채워 추적 매트릭스에 넣음 | 새로 만들거나 바꾼 것이 목록에 빠짐없이 있음 |
| 2 | 기능 검증 | 단계별 검증 표, 공격 시험, 통합 검정, `check-i18n.sh` | 실패 0 |
| 3 | 시안 확인 | 새 화면이 시안에 있는지, 시연이 안 되는 버튼이 없는지, 경로 짝이 맞는지 | 무반응 버튼 0 · 경로 짝 불일치 0 |
| 4 | 최종 버전 | 실제 웹 · 운영 화면 · 시안 · 보고 문서를 한 판으로 모음 | 시안이 그 판에 들어 있음 |
| 5 | 로컬 테스트 | 모든 주소를 한국어와 영어로 한 번씩 순회, 화면 사이의 이동 확인 | 콘솔 오류 0 · 4xx 0 · `undefined` 0 · 한국어 화면 대조 차이 0 |
| 6 | 포장 | zip 과 tar 두 개로 만듦 | 두 파일의 내용이 같음 |
| 7 | AWS 적용 | 적용 전 점검 → DB 스냅샷 → 적용 → 적용 후 확인 | 점검 두 번 모두 실패 0 · 스위치가 꺼져 있음 |

### 7-1. 한국어 화면 대조 (2번 · 5번에서 씀)

1. 문구를 옮기기 전의 판에서 대상 주소를 모두 열어 화면의 글자만 뽑아 저장합니다 (기준).

## 4. 서버 쪽

오류 코드 체계와 설정 표는 이미 있어 그대로 씁니다. 새로 알게 된 것은 **서버가 한글 안내를 직접 만드는 곳이 많다**는 점입니다.

### 4-1. 오류 안내

| 항목 | 실측 |
| --- | --- |
| 오류 응답의 모양 | `{ code, message, field? }` — 코드가 항상 있음 (`src/core/errors.ts`) |
| 서버 코드가 던지는 오류 | 323곳 · 코드 181종 |
| DB 트리거가 던지는 오류 | 389곳 · 코드 118종 (한글 안내 364곳) |
| 화면이 서버의 안내를 그대로 보여 주는 곳 | 97곳 |
| 화면이 코드를 보고 갈라 처리하는 곳 | 48곳 |

설계 탭 4-3 의 방식(화면이 `errors.<코드>` 로 바꿔 보여 주고, 없으면 서버 안내 그대로)을 그대로 쓸 수 있습니다. 다만 코드가 약 300종이라 한꺼번에 옮기지 않고, 각 흐름에서 실제로 나오는 코드부터 번역합니다. 번역이 없는 오류는 한국어로 보입니다.

### 4-2. 코드 이름과 운영이 고치는 글

| 항목 | 실측 | 뜻 |
| --- | --- | --- |
| `code_labels` | `domain · code · label · short_label · audience` | 화면은 `/codes` 로 묶음을 받아 코드를 이름으로 바꿈. 이 API 하나에 번역을 붙이면 대부분 해결 |
| `ui_messages` | `code · message · placement · basis` 12건 | 법적 근거가 있는 안내를 운영이 고치는 표. 코드 문구 1,830종을 넣는 자리가 아님 |
| 운영 화면 | `CodeLabels.tsx` 탭이 이미 있음 | 한국어 이름은 거기서, 번역은 새 「번역 관리」 탭에서 |
| 서버 코드가 `code_labels` 를 직접 읽는 곳 | 23곳 | 응답에 이름을 넣어 주는 조회. 흐름마다 확인 |

결론: `i18n_sources` 는 설계대로 새로 만듭니다. `ui_messages` 는 번역의 원문 가운데 하나로 붙입니다.

### 4-3. 설정 표

| 항목 | 실측 |
| --- | --- |
| 표 | `site_settings (key, value, scope, description, value_pattern, value_example, …)` · 94건 |
| 범위 | `PUBLIC` 4 · `GLOBAL` 89 · `PRIVATE` 1. `/site-settings/public` 은 범위가 `GLOBAL` 인 값을 내려 줌 (서버 코드로 확인) |
| 켜고 끄는 값 | `on` / `off` (예: `poll.guest_vote`), 형식은 `value_pattern` 으로 검사 |

다국어 설정도 같은 규칙으로 넣습니다. 화면이 알아야 하는 `i18n.enabled` 와 `i18n.locales` 는 `GLOBAL` 로 둡니다. 엔진 · 상한처럼 밖으로 나가면 안 되는 값은 `GLOBAL` 이 아닌 범위로 두어야 하며, 어느 범위가 맞는지는 1단계에서 정합니다.

### 4-4. 그 밖

| 항목 | 실측 | 뜻 |
| --- | --- | --- |
| 로그인 정보의 역할 | 사용자 웹의 `me()` 가 `roles` 를 받음 | 운영자 미리 보기를 만들 수 있음 |

| 에이전트 실행 기록 표 | 없음 | `content_translations.run_id` 는 에이전트 기반이 들어온 뒤에 |

## 7. 확인하지 못한 것과 다음 할 일

### 7-1. 확인하지 못한 것

- 서버(API)를 띄워 화면 전체를 순회하지 않았습니다. next-intl 구동은 사용자 웹만 띄워 `/login` 한 화면에서 확인했습니다.
- 브라우저에서 도는 부품 70개에 next-intl 을 넣었을 때 #418 이 나지 않는지는 문구를 옮기면서 화면마다 확인해야 합니다.
- Docker 와 `realcheck` 는 돌리지 않았습니다. DB 는 kit 의 내장 PostgreSQL 16 으로 띄웠습니다.
- 문구 수는 정규식으로 센 어림값입니다. 주석을 뺐지만, 화면에 나오지 않는 한글(기록용 글 등)이 섞여 있을 수 있습니다.
- Next.js 가 서버 호출의 기억 키에 헤더를 넣는지는 확인하지 않았습니다. 주소로 구분하면 어느 쪽이든 안전하므로 그 방식을 택했습니다.
- 번역 엔진 · n8n 워크플로우 · 시안 쪽 구현은 시험하지 않았습니다. 시안은 파일 크기(3.9MB)와 화면 ID 189종만 확인했습니다.
