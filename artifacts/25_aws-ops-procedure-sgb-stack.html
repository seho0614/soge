소개뱅크 AWS 구축·운영·관리 절차서 (sgb 스택 기준)

대상 스택: NestJS + TypeScript + Prisma + PostgreSQL 16 · Next.js(사용자) · Vite SPA(어드민) 리전: 서울(ap-northeast-2) · 도메인: sogaebaenk.co.kr 작성 기준: 대표(박세호) 직접 구축 · 외주 없이 콘솔 작업

기존 프로젝트 자료(AWS 적용 절차 v1.0/v1.1)는 Spring Boot + MySQL 스택을 전제로 작성되어 있습니다. 현재 실제 채택 스택은 NestJS + PostgreSQL이므로, 이 문서는 같은 원칙(예산 알림 우선, 기본 VPC, 키페어 백업, RDS 프라이빗 등)을 Node/PostgreSQL 환경으로 다시 옮긴 것입니다. DB 엔진·런타임·배포 방식이 전부 다르므로 기존 문서를 참고할 때는 이 문서를 우선하십시오.

1. 착수 전 확정 사항 — 이식성 규칙 (Node/PostgreSQL 버전)

로컬에서 만든 뒤 AWS로 옮길 때, 아래를 처음부터 지키면 "설정 교체"로 끝나고, 안 지키면 "코드 수정 + 재검증"이 됩니다.

# 규칙 내용 안 지키면
1 설정 외부화 DB 접속 정보·API 키·경로를 코드에 넣지 않음. .env + @nestjs/config로 주입. 비밀값은 환경변수로만 운영 서버가 개발 DB를 바라보는 사고
2 파일 업로드 추상화 ★ StorageService 인터페이스로 감싸고 LocalStorage/S3Storage 구현 분리. 서비스 코드에서 fs.writeFile 직접 호출 금지 업로드 걸린 화면 전부 재작업 (사업자등록증, 신뢰지표 증빙, 회사 이미지 7종 등)
3 PostgreSQL 버전 통일 로컬도 Docker/네이티브 PostgreSQL 16.x로 RDS와 동일 마이너 버전 로컬은 되는데 서버에서 안 되는 쿼리 차이
4 세션 외부화 인메모리 세션 금지, Redis 세션 스토어 필수 (서브도메인 5개 관 간 세션 공유 전제) 서버 재시작마다 로그인 풀림, 서브도메인 세션 공유 불가
5 시간대 통일 서버·DB·애플리케이션 모두 UTC 고정, 표시 시점에만 KST 변환 데이터 소급 보정 사실상 불가
6 경로 환경변수화 Windows 경로·하드코딩 절대경로 금지 컨테이너/서버에서 로그·업로드 경로 소실
7 DB 스키마는 코드로 관리 Prisma Migrate로만 스키마 변경. db push는 로컬 실험용으로만, 운영 반영은 prisma migrate deploy 로컬·RDS 스키마 분기, 정본 불명

검수 기준: 서비스 계층에서 fs.writeFile/fs.readFile import 0건, 소스 전체에서 DB 접속 문자열·API 키 하드코딩 0건.

2. AWS 계정과 과금 기반 (0단계, 가장 먼저)

  1. 루트 계정 생성 → 즉시 MFA 등록 (OTP 앱)
  2. AWS Budgets에서 월 임계 알림 설정 — 예: 30만원. 메일 수신 확인까지 완료. 이 알림을 켜기 전에는 다음 단계로 가지 않습니다.
  3. 결제 설정에 사업자등록번호(429-88-01533) 등록 → 세금계산서 발행. 나중에 등록하면 소급이 번거로움
  4. 리전을 서울(ap-northeast-2)로 고정. 개인정보가 들어가는 서비스이므로 국내 리전 필수
  5. IAM 관리자 사용자 생성 → 루트는 봉인. 이후 모든 콘솔·CLI 작업은 IAM 사용자로 수행

이 단계에서 확정되는 값 — 호스팅제공자 = Amazon Web Services Korea LLC. 푸터 법정고지·통신판매업 신고서에 필요한 항목입니다.

3. 네트워크 — 기본 VPC + 보안그룹 3벌

VPC를 직접 만들지 않습니다. 콘솔 마법사로 새 VPC를 만들면 NAT 게이트웨이가 함께 켜지는 경우가 많고, 이것만으로 월 6만원 안팎이 아무 일도 하지 않고 나갑니다. 최소 구성에는 기본 VPC로 충분합니다.

보안그룹 3벌만 만듭니다.

보안그룹 인바운드 허용 대상
sb-web 80, 443 ← 0.0.0.0/0 운영 EC2
sb-ops 22 ← 사무실/자택 고정 IP만, /admin 경로는 애플리케이션 레벨에서도 IP 제한 전 서버
sb-db 5432 ← sb-web 보안그룹만 RDS PostgreSQL

Redis를 EC2에서 직접 운영한다면 sb-db에 6379도 sb-web에서만 열어둡니다.

4. EC2 구성

4-1. 인스턴스 구성

서버 타입 용도
dev-staging t3.small 개발 통합 테스트 + 스테이징 (초기 1대로 병행 가능)
production t3.medium 운영 API 서버
  • AMI: Ubuntu 24.04 LTS
  • 키페어(.pem) 생성 즉시 2곳(로컬 + 별도 보관소)에 백업. AWS는 분실 시 재발급하지 않으며, 분실하면 서버 접속이 영구히 막혀 인스턴스를 새로 만들어야 합니다
  • 운영 서버에는 Elastic IP를 선점해둡니다 — 카카오 알림톡/SMS 대행사가 발신 서버 IP 등록을 요구하는 경우가 많고, 애플리케이션 완성 전에도 IP는 먼저 확보할 수 있습니다 (t3.small + Elastic IP ≈ 월 3만원)

4-2. 서버 초기 설정 (Ubuntu 24.04 기준)

# Node.js 24 LTS (nvm 권장 — 버전 전환 용이)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.0/install.sh | bash
source ~/.bashrc
nvm install 24
nvm alias default 24

# PM2 — 프로세스 관리자, systemd와 연동해 재부팅 시 자동 기동
npm install -g pm2
pm2 startup systemd   # 출력되는 명령을 그대로 sudo로 실행

# PostgreSQL 클라이언트(마이그레이션·점검용, DB 자체는 RDS 사용)
sudo apt install -y postgresql-client-16

# Nginx (리버스 프록시)
sudo apt install -y nginx

4-3. 배포 단위 — Docker 없이 갈 경우

Docker를 쓰지 않기로 했다면(로컬 개발 절차 문서 기준과 동일하게), PM2 ecosystem 파일로 대체합니다.

// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'sgb-api',
    script: 'dist/main.js',
    instances: 1,
    exec_mode: 'fork',
    env_production: {
      NODE_ENV: 'production',
      TZ: 'UTC',
    },
  }],
};

pm2 start ecosystem.config.js --env production
pm2 save

5. RDS — PostgreSQL 16

항목 값
엔진 PostgreSQL 16.x (로컬과 마이너 버전까지 일치)
인스턴스 클래스 db.t3.micro (초기) → 트래픽 보고 db.t3.small로 상향
퍼블릭 액세스 아니오 (반드시)
보안그룹 sb-db만 허용
백업 보관 기간 7일 이상, 자동 백업 활성화
파라미터 그룹 타임존 UTC 고정
Multi-AZ 초기는 비활성(비용), 운영 안정화 후 재검토

복원 연습 1회를 반드시 수행합니다. 스냅샷에서 새 인스턴스로 복원해보고, 애플리케이션이 접속되는지 확인 후 삭제. 이 30분을 건너뛰면 정말 필요한 날 복원이 안 되는 것을 그때 알게 됩니다.

Prisma 연결 문자열 예:

DATABASE_URL="postgresql://sgb_app:${DB_PASSWORD}@<RDS엔드포인트>:5432/sogaebaenk?schema=public"

6. Redis — 세션·캐시

선택지 두 가지:

  1. ElastiCache for Redis (권장, 관리형) — cache.t3.micro로 시작, sb-db와 별도 보안그룹으로 sb-web에서만 접근 허용
  2. EC2 내 Redis 직접 설치 — 초기 비용 절감용. apt install redis-server, bind 127.0.0.1 또는 내부 IP로 제한

서브도메인 5개 관(MNY/MAL/BIZ/LED/HLT) 간 세션 공유가 전제이므로, @nestjs/session 또는 connect-redis 기반 세션 스토어를 반드시 사용하고 인메모리 세션은 쓰지 않습니다.

7. S3 — 파일 업로드

  1. 버킷 생성 (예: sogaebaenk-uploads-prod), 퍼블릭 액세스 차단 기본값 유지
  2. 업로드 파일은 애플리케이션이 사전 서명 URL(presigned URL)로 접근하거나, CloudFront + OAC로 배포
  3. IAM 사용자(또는 EC2 인스턴스 프로파일)에 해당 버킷 한정 최소 권한 정책 부여 (s3:PutObject, s3:GetObject, s3:DeleteObject — 버킷 ARN 한정)
  4. StorageService 구현체(S3Storage)에서 AWS SDK v3 사용:
npm install @aws-sdk/client-s3 @aws-sdk/s3-request-presigner
  1. 사업자등록증·인증 서류 등 민감 업로드는 버킷을 분리하거나 접두어(prefix)로 구분하고, 접근 권한을 더 엄격히 관리

8. Route 53 & 도메인

  • 도메인: sogaebaenk.co.kr 단일 (기존 문서의 도메인 불일치 이슈는 해소됨)
  • 5개 관을 서브도메인으로 운영할 경우 (예: mal.sogaebaenk.co.kr, led.sogaebaenk.co.kr) Route 53에 A/CNAME 레코드 등록
  • Route 53 호스팅 영역으로 네임서버 위임 완료 후 진행

9. HTTPS — Let's Encrypt 와일드카드 인증서

AWS ACM 무료 인증서는 EC2에 직접 붙지 않으므로(ALB/CloudFront 전용), EC2 + Nginx 구성에서는 Let's Encrypt를 사용합니다.

sudo apt install -y certbot python3-certbot-dns-route53
sudo certbot certonly --dns-route53 \
  -d sogaebaenk.co.kr -d "*.sogaebaenk.co.kr"
  • 서브도메인 세션 공유 전제이므로 와일드카드 인증서가 필요
  • 갱신은 자동(certbot renew cron/systemd timer)이지만, 갱신 실패 알림을 이메일이나 Slack으로 받도록 설정
  • Nginx는 80/443을 받아 내부 3000번(NestJS)으로 리버스 프록시
server {
    listen 443 ssl;
    server_name sogaebaenk.co.kr;
    ssl_certificate /etc/letsencrypt/live/sogaebaenk.co.kr/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/sogaebaenk.co.kr/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

10. 배포 절차 (사용법)

10-1. 최초 배포

git clone <repo> && cd sgb
cp .env.example .env        # 값 채워넣기 (커밋 금지)
npm ci
npx prisma migrate deploy    # 스키마 반영 — 절대 db push 사용 금지(운영)
npm run build
pm2 start ecosystem.config.js --env production

10-2. 이후 배포 (업데이트) — deploy.sh

#!/usr/bin/env bash
set -euo pipefail
git pull origin main
npm ci
npx prisma migrate deploy
npm run build
pm2 reload sgb-api --update-env   # 무중단 재기동
  • 롤백 절차: 배포 전 태그(git tag pre-deploy-$(date +%Y%m%d%H%M))를 남기고, 문제 발생 시 해당 태그로 git checkout 후 재배포. 마이그레이션이 개입된 배포는 롤백 연습을 최소 1회 미리 해봅니다 — 스키마 되돌리기가 항상 간단하지 않기 때문입니다
  • 프런트(Next.js/Vite)는 별도 빌드 산출물을 S3+CloudFront로 배포하거나, 같은 EC2에서 정적 파일을 Nginx로 서빙

11-1. 일상 점검

11-2. 로그 로테이션

pm2 set pm2-logrotate:max_size 50M
pm2 set pm2-logrotate:retain 14

11-3. 보안 관리 체크리스트

  • 보안그룹에 0.0.0.0/0으로 22번 포트가 열려있지 않은지 월 1회 점검
  • /admin 경로 접근이 IP 제한되어 있는지 확인 (서버 권한 계층 체계가 완비되기 전까지의 임시 방어선)
  • IAM 사용자 액세스 키 정기 교체(90일)
  • RDS·EC2 OS 보안 패치 월 1회 적용 (apt update && apt upgrade)
  • .env 파일 권한 600, git 추적 제외 확인

11-4. 비용 관리

  • 인스턴스 종료 후에도 공인 IP·EBS 볼륨·스냅샷은 남아 과금됩니다. 분기별로 콘솔에서 미연결 리소스(Elastic IP, 볼륨)를 점검해 정리
  • Budgets 알림 임계값은 트래픽 증가에 맞춰 상향 조정
  • RDS/EC2를 스테이징에서 야간·주말 자동 중지(Lambda 스케줄)하면 비용 절감 가능 (선택)

11-5. 백업·복구

  • RDS 자동 스냅샷(7일) + 필요 시 수동 스냅샷(주요 배포 직전)
  • S3 버킷 버저닝 활성화로 실수 삭제 대비
  • 분기 1회 복원 연습을 정기 일정으로 못박아 둘 것을 권장 — 문서 작성 시점에만 하고 잊히는 항목이 되기 쉬움

12. 운영 전환(구서버 → AWS) 시 주의

  1. Route 53 TTL을 전환 1~2일 전에 짧게(300초) 낮춰둠
  2. 신규 서버에서 데이터 마이그레이션 후 read-only 모드로 며칠 병행 운영해 정합성 확인
  3. 전환 직후 24~48시간은 구서버를 살려둔 채(DNS만 전환) 롤백 여지를 남김
  4. 전환 완료 후 TTL을 원래 값으로 복원

13. 착수 시 오늘 정할 것

# 항목 비고
1 ElastiCache vs EC2 Redis 초기 비용 vs 관리 편의성
2 프런트 배포 방식 S3+CloudFront vs 동일 EC2 Nginx 서빙
3 스테이징/운영 EC2 분리 시점 초기엔 1대 병행도 가능, 트래픽 늘면 분리
4 알림톡/SMS 대행사의 발신 IP 등록 요건 확인 확인되면 Elastic IP 선점을 그에 맞춰 조정
5 야간 스테이징 자동 중지 여부 비용 절감 목적, 선택 사항

  2. 키페어 분실 — 생성 즉시 이중 백업
  3. 복원 안 해본 백업 — 분기 1회 실제 복원 연습
  4. 방치된 리소스 — 예산 알림을 가장 먼저 켜서 방어
