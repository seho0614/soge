01

축 체계 — 세 축을 계층으로 고정

관은 정산 규칙과 플랫폼 책임 범위가 실제로 갈리는 지점이므로 1군입니다. 업종은 관 안에서만 의미가 있고, 역할은 같은 목록을 뒤집어 보는 방식일 뿐이므로 목록 내부로 내립니다.

업종 집합은 관마다 다르다

현 시안의 카테고리 18종은 관과 매핑되지 않은 평면 목록입니다. “자동차/오토바이”는 소개몰에는 있어야 하지만 소개창업에는 없어야 하고, “외식·식당”은 소개창업에만 있어야 합니다. 관 × 업종 매트릭스를 확정하기 전에는 등록폼도 목록 필터도 만들 수 없습니다.

02

Depth 정책

탐색은 최대 3뎁스(관 → 업종 → 상세)에서 끝납니다. 거래 흐름(/chat, /deal)은 상세의 하위가 아니라 독립 경로로 둡니다 — 하나의 대화·거래가 여러 리스팅을 참조할 수 있고, 리스팅이 삭제돼도 거래 기록은 남아야 하기 때문입니다.

03

내비게이션 모델

네 층위로 나눕니다. 각 층위는 담당 범위가 정해져 있고, 다른 층위의 항목을 끌어올리지 않습니다. 시안에서 “커뮤니티”와 “혜택안내”가 GNB 5번 자리를 놓고 다투는 것이 바로 이 규칙이 없어서입니다.

시안은 커뮤니티(3안)와 혜택안내 + 고객센터(1안)로 갈립니다. 오픈 시점에 운영 인력이 붙지 않는 커뮤니티는 빈 게시판으로 남아 신뢰를 깎습니다. 오픈 시에는 고객센터를 두고, 커뮤니티는 콘텐츠가 쌓인 뒤 6번째로 추가하는 편을 권합니다. 혜택안내는 이용안내 하위 문서로 흡수합니다.

  • GNB → 햄버거. 관 3종은 드로어 최상단에 고정.

06

상태 전이

IA의 마지막 층은 화면이 아니라 상태입니다. 어떤 화면이 보이는지가 상태로 결정되기 때문입니다.

엔티티상태노출 · 접근 규칙
ListingDRAFT본인 마이페이지에서만 보임
PENDING본인 + 관리자 검수 큐. 공개 경로 전부 차단
LIVE모든 공개 경로에 노출. 수정 시 재검수
REJECTED본인만. 사유 코드 + 수정 가이드 동반
CLOSED상세는 열리되 문의 차단 + 마감 배너

AWAIT_CONFIRM확인 n/2 표시. 상대에게 알림 최대 3회
CONFIRMED정산 생성 가능 · 후기 작성 가능

배치 규칙

새 요소를 어디에 둘지 다툼이 생길 때 이 규칙으로 판정합니다.

R규칙판정 기준위반 사례 (현 시안)
R11군은 관만 정산 규칙 또는 플랫폼 책임이 갈리지 않으면 1군에 올리지 않는다 메인 A가 역할 탭을, 카테고리 페이지가 업종을 1군에 둠
R2업종은 관에 종속 업종 목록은 관마다 다르며 전역 목록을 만들지 않는다 관과 매핑되지 않은 평면 카테고리 18종
R3단일 소스 같은 데이터를 두 곳에서 보여줄 때 API 응답은 하나여야 한다 사이드바 18종과 아이콘 12종이 서로 다른 목록
R4정보 계약 목록 카드에 표시한 필드는 상세에 반드시 존재한다 목록에 8,500만원 · 상세에 가격 없음
R5Action 1개 한 화면에 전환 CTA는 하나. 나머지는 보조 스타일 상세에 전화하기 · 문의하기 두 개가 동일 강도
R6정책은 서버에서 제한업종 · 금칙어는 UI가 아니라 API에서 차단한다 사이드바에 “법률/세무/노무”, “부동산”이 그대로 존재
R7미구현 비노출 기능이 없는 것을 문구로 먼저 약속하지 않는다 “에스크로 보안 · 계약서 양식 제공 · 실시간 채팅” 문구만 존재
R8거래는 독립 경로 대화 · 계약 · 정산은 리스팅의 하위가 아니다 —
R9부분 실패 허용 한 섹션이 실패해도 페이지 전체를 오류로 대체하지 않는다 —
R10복귀 경로 유지 로그인 유도 후 원래 화면으로 돌아온다. 홈으로 보내지 않는다 —
08
