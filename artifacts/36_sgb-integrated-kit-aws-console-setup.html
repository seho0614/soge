소개뱅크 (sgb-integrated-kit) AWS 콘솔 구축 절차서

기준 자료: 업로드된 sgb-integrated-kit.zip 내 docs/26_환경설치절차서.md §3(AWS 운영 환경), docs/25_배포운영절차서.md, infra/eventbridge-jobs.yaml 목적: 키트 문서의 N-01~N-11 구축 순서표를 실제 AWS 콘솔 클릭 단위 절차로 풀어씀. 문서에 이미 있는 "무엇을"에 "어떻게(콘솔 어디서)"를 채우는 문서입니다. 리전: 서울(ap-northeast-2) 고정 — 개인정보 국외이전 판단 자체를 피하기 위함(키트 §3-3 근거)

이 문서는 키트가 이미 전제한 아키텍처(ECS Fargate + ALB + ECR, RDS Multi-AZ, ElastiCache, SQS, Secrets Manager, EventBridge Scheduler)를 그대로 따릅니다. 이전에 드린 EC2+PM2 단순 구성 절차서와는 다른 문서이니, 이 키트를 쓰는 경우 이 문서를 기준으로 하십시오.

0. 착수 전 확인 — 키트가 아직 갖추지 않은 것

키트에는 운영용 Dockerfile이 없습니다. 현재 Dockerfile은 ts-node로 바로 띄우는 구동 테스트용입니다(주석에 "운영 이미지는 별도입니다"라고 명시됨). ECR에 올릴 운영 이미지를 아래처럼 별도로 만들어야 N-02부터 진행됩니다.

Dockerfile.prod (신규 작성 필요):

FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --no-audit --no-fund
COPY . .
RUN npm run build            # tsc → dist/

FROM node:22-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
      postgresql-client curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev --no-audit --no-fund
COPY --from=build /app/dist ./dist
COPY scripts ./scripts
COPY prisma ./prisma
EXPOSE 3000
HEALTHCHECK --interval=10s --timeout=5s --start-period=40s --retries=6 \
  CMD curl -fsS http://localhost:3000/api/v1/health || exit 1
CMD ["node", "dist/main.js"]

web/(관리자, Vite), site/(사용자, Next.js)도 동일하게 프로덕션 빌드용 Dockerfile이 필요합니다 (npm run build 후 정적 파일을 서빙하거나 next build && next start). 지금 있는 두 Dockerfile은 vite --host/next dev로 개발 서버를 띄우는 방식이라 운영에 쓰면 안 됩니다.

이 세 이미지가 준비된 뒤부터 아래 절차가 의미를 가집니다.

1. 사전 준비물

항목 준비
AWS 결제 수단 법인 카드 또는 계좌이체
사업자등록번호 429-88-01533 (세금계산서 발행용)
도메인 sogaebaenk.co.kr (Route 53 위임 또는 기존 등록대행사에서 NS 확인)
이메일 계정별 별칭 이메일 3개 (management+dev@, +stg@, +prod@ 형태 권장 — 루트 계정은 재사용 불가)
GitHub 저장소 sgb 코드 저장소 (Actions 활성화 상태)

2. Phase N-01 — 계정 구조 · Organizations · IAM Identity Center

키트 §3-1 기준: 비운영 계정 1개(dev+stg) + 운영 계정 1개(prod), Organizations로 묶고 SCP로 운영 계정을 보호합니다.

2-1. 관리(Management) 계정 생성

  1. https://aws.amazon.com 에서 신규 계정 생성 (이 계정이 결제 대표 계정이 됩니다)
  2. 루트 로그인 → IAM → Security credentials → MFA 등록 (가상 MFA 앱)
  3. Billing → Budgets → Create budget → 월 예산 임계값 설정, 알림 이메일 등록. 이 단계를 반드시 가장 먼저 완료합니다.
  4. Billing → Payment preferences → 사업자등록번호 등록

2-2. AWS Organizations 생성

  1. 콘솔 검색창에 Organizations 입력 → Create an organization
  2. "All features" 선택 (SCP 사용을 위해 필수, "Consolidated billing"만으로는 SCP 불가)

2-3. 멤버 계정 2개 생성

  1. Organizations 콘솔 → Add an AWS account → Create an AWS account
    • 계정명: sgb-nonprod (dev+stg), 이메일: 위 별칭 이메일
    • 계정명: sgb-prod, 이메일: 위 별칭 이메일
  2. 생성 후 각 계정의 Account ID를 기록해둡니다(이후 리소스 정책에 사용)

2-4. IAM Identity Center (구 SSO) 설정

  1. 관리 계정에서 콘솔 검색 IAM Identity Center → Enable
  2. Identity source는 기본(Identity Center 자체 디렉터리)으로 시작, 향후 Google Workspace 등 연동 가능
  3. Users → 본인 및 개발자 계정 추가
  4. Permission sets 생성:
    • AdministratorAccess — 대표(박세호) 전용
    • DeveloperAccess — 개발자용 (dev/stg만 상시, prod는 임시 승인형)
    • 정책 예: PowerUserAccess + ECS/RDS 콘솔 접근으로 커스터마이즈
  5. AWS accounts 탭에서 각 사용자·그룹을 sgb-nonprod/sgb-prod 계정에 permission set과 함께 할당
  6. prod 상시 권한을 주지 않습니다. 개발자는 dev/stg에는 DeveloperAccess 상시 할당, prod는 필요 시에만 임시로 할당 후 작업 종료 시 회수(수동 운영 또는 Permission Set의 세션 시간 제한을 짧게 설정)

2-5. SCP(서비스 제어 정책) — prod 계정 보호

  1. Organizations → sgb-prod 계정을 담을 OU(예: Production) 생성 → 계정을 OU로 이동
  2. Policies → Service control policies → Create policy
  3. 아래 정책을 Production OU에 연결:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLeaveOrg",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    },
    {
      "Sid": "DenyDisableCloudTrail",
      "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail"],
      "Resource": "*"
    },
    {
      "Sid": "DenyRegionOutsideSeoul",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "support:*", "budgets:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": "ap-northeast-2" }
      }
    }
  ]
}

3. Phase N-02 — 네트워크 · RDS · ECR · ECS · ALB (dev 환경)

이하 3~8은 각 계정(dev/stg는 sgb-nonprod, prod는 sgb-prod)에서 동일한 절차를 반복합니다. 여기서는 dev 기준으로 상세히 적고, stg/prod는 사양 차이만 표로 별도 정리합니다(§8, §9).

3-1. VPC 생성

  1. 콘솔 검색 VPC → Create VPC → VPC and more 선택 (마법사가 서브넷/라우팅까지 함께 만듭니다)
  2. 설정값:
    • Name tag: sgb-vpc-dev
    • IPv4 CIDR: 10.0.0.0/16
    • AZ 수: 2 (서울 리전 최소 2개 AZ로 고가용성 확보)
    • Public subnet: 2개 (10.0.0.0/24, 10.0.1.0/24) — ALB·NAT용
    • Private subnet: 2개 (10.0.10.0/24, 10.0.11.0/24) — ECS 태스크·RDS·ElastiCache용
    • NAT gateways: In 1 AZ (dev는 비용 절감을 위해 1개만 — 키트 §3-6 "초기 절감 3가지"의 NAT 1개 항목)
    • VPC endpoints: S3 Gateway 엔드포인트 체크 (ECR/S3 트래픽이 NAT를 안 거치게 해 비용 절감)
  3. 생성 완료 후 Elastic IPs 메뉴에서 NAT에 붙은 EIP를 확인·기록 (N-03에서 이 IP를 외부연동사에 등록)

3-2. 보안 그룹

보안그룹 인바운드 용도
sg-alb 80, 443 ← 0.0.0.0/0 ALB
sg-ecs-api 3000 ← sg-alb만 web-api 태스크
sg-rds 5432 ← sg-ecs-api, sg-ecs-worker RDS
sg-redis 6379 ← sg-ecs-api ElastiCache

VPC 콘솔 → Security groups → Create security group에서 각각 생성, VPC는 sgb-vpc-dev 지정.

3-3. ECR 리포지토리 생성

  1. 콘솔 검색 ECR → Create repository
  2. 3개 생성: sgb-api, sgb-web(관리자), sgb-site(사용자)
  3. Image scanning on push: Enable (취약점 스캔, N-08 대비)
  4. 로컬에서 최초 푸시:
aws ecr get-login-password --region ap-northeast-2 | \
  docker login --username AWS --password-stdin <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com

docker build -f Dockerfile.prod -t sgb-api .
docker tag sgb-api:latest <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sgb-api:latest
docker push <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sgb-api:latest

3-4. RDS PostgreSQL 16 생성

  1. 콘솔 검색 RDS → Create database
  2. Standard create 선택
  3. 엔진: PostgreSQL, 버전 16.x (16.4 이상 최신 마이너)
  4. 템플릿: dev는 Dev/Test
  5. 인스턴스 클래스: db.t4g.small (키트 §3-3 표 기준, dev/stg)
  6. 스토리지: gp3, 20GiB 시작, 자동 확장 체크
  7. Multi-AZ: dev는 비활성 (prod에서만, §8 참조)
  8. 연결: VPC sgb-vpc-dev, 퍼블릭 액세스: 아니오, 서브넷 그룹은 private subnet 2개로 새로 생성, 보안그룹 sg-rds 지정
  9. 인증: 암호 직접 관리(추후 Secrets Manager로 옮김) 또는 "Manage master credentials in Secrets Manager" 체크 (권장 — 처음부터 Secrets Manager 연동)
  10. 추가 구성: DB 이름 sgb, 백업 보존 7일(dev), 암호화 활성화(KMS 기본 키), 파라미터 그룹은 기본값 사용
  11. 생성 후 엔드포인트 주소를 기록

3-5. DB 확장 3종 설치

RDS는 슈퍼유저 권한이 제한적이지만 rds_superuser 역할로 확장 설치는 가능합니다.

psql "postgresql://<마스터계정>:<암호>@<RDS엔드포인트>:5432/sgb" -c "
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
"

3-6. ElastiCache Redis 생성

  1. 콘솔 검색 ElastiCache → Redis OSS caches → Create
  2. 배포 옵션: Design your own cache → Cluster mode: Disabled (세션 캐시 용도라 단일 샤드로 충분)
  3. 노드 타입: cache.t4g.micro (dev)
  4. 서브넷 그룹: private subnet 2개로 새로 생성
  5. 보안그룹: sg-redis
  6. 암호화: 저장 시/전송 중 암호화 모두 활성화
  7. 생성 후 Primary endpoint 기록

3-7. ALB(Application Load Balancer) + ACM 인증서

  1. ACM(Certificate Manager) → Request certificate → 도메인 api-dev.sogaebaenk.co.kr (또는 필요한 서브도메인들, 와일드카드 *.sogaebaenk.co.kr도 가능) → 검증 방식 DNS validation
  2. Route 53에 도메인이 위임되어 있다면 ACM이 제시하는 CNAME 레코드를 "Create records in Route 53" 버튼 한 번으로 자동 생성 가능
  3. EC2 → Load Balancers → Create Load Balancer → Application Load Balancer
    • Name: sgb-alb-dev
    • Scheme: Internet-facing
    • VPC: sgb-vpc-dev, 서브넷: public subnet 2개
    • 보안그룹: sg-alb
    • Listener: HTTPS:443 (ACM 인증서 선택), HTTP:80 → HTTPS로 리다이렉트 규칙 추가
  4. Target group 생성 (이 단계는 ECS 서비스 생성 시 함께 만들어도 됨): Target type IP, Protocol HTTP:3000, Health check path /api/v1/health

3-8. ECS 클러스터 · 태스크 정의 · 서비스

  1. ECS → Clusters → Create cluster → Name sgb-dev, Infrastructure: AWS Fargate
  2. Task definitions → Create new task definition
태스크 vCPU/메모리 컨테이너 이미지 포트
sgb-web-api 0.5 vCPU / 1GB ECR sgb-api:latest 3000
sgb-admin-bo 0.25 vCPU / 0.5GB ECR sgb-web:latest 5173
sgb-worker 0.25 vCPU / 0.5GB ECR sgb-api:latest, command node scripts/scheduler-daemon.js (dev에서만 임시, 운영은 EventBridge로 대체 — §6) —

각 태스크 정의에서:

  • Task role: S3(sgb-uploads), Secrets Manager 읽기 권한을 가진 IAM 역할 연결
  • Environment variables: NODE_ENV=production, PORT=3000 등 비민감 값만 직접 입력
  • Secrets: DATABASE_URL, JWT_SECRET, JOB_TOKEN 등은 "Secrets" 항목에서 Secrets Manager ARN 참조로 연결 (평문 입력 금지 — §7 참조)
  • Logging: awslogs 드라이버, CloudWatch Logs 그룹 /ecs/sgb-dev/web-api 자동 생성 체크

  1. Clusters → sgb-dev → Create Service

    • web-api: Desired count 2, Service auto scaling 활성화 (Target tracking, ECSServiceAverageCPUUtilization 70%, min 2 / max 4), Load balancer는 위에서 만든 ALB의 Target group 연결
    • admin-bo: Desired count 1, 고정(오토스케일링 없음), 별도 Target group + ALB 리스너 규칙(호스트 헤더 admin-dev.sogaebaenk.co.kr)으로 라우팅
    • worker: Desired count 1, 고정, ALB 연결 없음(백그라운드 프로세스)

  2. Route 53에서 api-dev.sogaebaenk.co.kr, admin-dev.sogaebaenk.co.kr A레코드(Alias)를 ALB로 연결

3-9. 최초 마이그레이션 실행

ECS 태스크로 1회성 실행(Run task, Desired count 0인 별도 태스크 정의 또는 ECS Exec):

aws ecs run-task \
  --cluster sgb-dev \
  --task-definition sgb-migrate \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[<private-subnet-id>],securityGroups=[sg-ecs-api],assignPublicIp=DISABLED}"

또는 로컬에서 RDS에 직접 접속 가능한 배스천/VPN이 있다면 npm run db:migrate를 로컬에서 DATABASE_URL만 RDS로 바꿔 실행해도 됩니다(단, 보안그룹에서 본인 IP를 한시적으로 허용해야 함 — 작업 후 반드시 제거).

4. Phase N-03 — NAT EIP 고정 · 외부연동 발신 IP 등록 ★ 임계 경로

키트 아키텍처 문서 기준 외부 연동 5~6종이 발신 IP 화이트리스트를 요구하며, 심사에 2~4주가 걸립니다. 이 단계가 늦어지면 이후 일정이 전부 밀립니다.

  1. §3-1에서 만든 NAT Gateway의 Elastic IP가 이미 고정 IP입니다 (NAT는 항상 고정 EIP를 사용). VPC 콘솔 → Elastic IPs에서 값 확인
  2. 이 IP를 아래 연동사에 사전 등록 신청합니다 (심사 소요 기간이 다르므로 가장 먼저 접수):
    • NTS(국세청 사업자 진위확인 API)
    • PASS(본인확인)
    • PG(토스페이먼츠) — 필요 시 화이트리스트 여부 확인
    • 은행 계좌 실명 확인(CODEF 등)
    • 카카오 알림톡 대행사
    • SMS 발송 대행사
  3. 신청 결과(승인/보류)는 관리자 화면 "외부 연동" 탭에서 발신 IP를 한 번 입력하면 6종에 일괄 반영되도록 설계되어 있음(docs/25 §2-1-③) — 승인 완료 후 이 화면에서 IP 입력하고 상태를 LIVE로 전환
  4. 주의: dev/stg와 prod는 별도 AWS 계정이므로 NAT EIP가 서로 다릅니다. 연동사에는 prod의 EIP를 등록해야 하며, prod 환경(§9)이 아직 없다면 이 시점에 prod용 VPC+NAT만 먼저 만들어 EIP를 선점해두는 것을 권장합니다(EC2/RDS 등 나머지 리소스는 나중에 만들어도 무방).

5. Phase N-04 — CI/CD 파이프라인

키트에는 이미 .github/workflows/db-invariants.yml(CI: 마이그레이션·불변식·문서 드리프트 검증)이 있습니다. 여기에 CD(배포) 단계를 추가합니다.

5-1. GitHub → AWS 인증 (OIDC, 액세스 키 미사용 권장)

  1. IAM → Identity providers → Add provider → OpenID Connect, Provider URL https://token.actions.githubusercontent.com, Audience sts.amazonaws.com
  2. IAM → Roles → Create role → Web identity → 위 provider 선택, GitHub repo 조건(repo:<org>/<repo>:ref:refs/heads/main) 지정
  3. 이 역할에 ECR push, ECS UpdateService 권한 정책 연결

5-2. GitHub Actions 워크플로 추가 (.github/workflows/deploy.yml)

name: Deploy
on:
  push:
    branches: [main]
jobs:
  deploy-stg:
    runs-on: ubuntu-latest
    permissions: { id-token: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::<계정ID>:role/github-deploy
          aws-region: ap-northeast-2
      - run: |
          aws ecr get-login-password | docker login --username AWS --password-stdin <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com
          docker build -f Dockerfile.prod -t sgb-api .
          docker tag sgb-api:latest <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sgb-api:$GITHUB_SHA
          docker push <계정ID>.dkr.ecr.ap-northeast-2.amazonaws.com/sgb-api:$GITHUB_SHA
      - run: |
          DATABASE_URL=${{ secrets.STG_DATABASE_URL }} ENVIRONMENT=stg npm run deploy:check
      - run: |
          aws ecs update-service --cluster sgb-stg --service web-api \
            --force-new-deployment --task-definition sgb-web-api:LATEST

prod 배포는 이 워크플로에서 자동 트리거하지 않습니다. 키트 §1-4가 "수동 승인 1클릭"을 명시하므로, prod는 GitHub Actions의 **Environment protection rule(수동 승인)**을 걸거나, 별도 workflow_dispatch(수동 실행) 트리거로 분리합니다.

5-3. 마이그레이션 러너

npm run db:migrate를 CD 파이프라인의 별도 단계(ECS one-off task 또는 CodeBuild)로 실행하도록 구성합니다. 애플리케이션 컨테이너 시작 시 자동 마이그레이션은 하지 않습니다 — 태스크가 여러 개 뜰 때 동시 실행되는 사고를 막기 위해서입니다(키트가 배치 스케줄러를 이런 이유로 EventBridge로 옮긴 것과 같은 원칙).

6. Phase N-05 — Secrets Manager · CloudWatch · 백업

6-1. Secrets Manager

콘솔 검색 Secrets Manager → Store a new secret → "Other type of secret"로 아래 키-값을 각각(또는 하나의 JSON 시크릿으로 묶어) 등록:

DATABASE_URL
JWT_SECRET          (32자 이상 — openssl rand -base64 32)
JOB_TOKEN            (32자 이상 — openssl rand -hex 24)
NTS_SERVICE_KEY
PG_SECRET_KEY        (토스페이먼츠)
PASS_API_KEY
BANK_VERIFY_KEY
ALIMTALK_KEY
  • Secret name 규칙: sgb/<env>/<key> (예: sgb/prod/JWT_SECRET)
  • Automatic rotation: DATABASE_URL은 RDS와 연동해 자동 순환 설정 가능(Secrets Manager의 RDS rotation 템플릿)
  • ECS 태스크 정의의 "Secrets" 필드에서 이 ARN들을 참조 (§3-8 4단계)

6-2. CloudWatch

  1. CloudWatch → Log groups: ECS가 자동 생성한 /ecs/sgb-<env>/* 로그 그룹의 보존 기간을 30일 이상으로 설정
  2. CloudWatch → Alarms → Create alarm:
    • ALB HTTPCode_Target_5XX_Count 급증 알람
    • ECS 서비스 CPUUtilization 90% 이상 알람
    • RDS FreeStorageSpace 저사용 알람, DatabaseConnections 임계 알람
    • Lambda sgb-job-invoker의 Errors/Invocations 알람은 infra/eventbridge-jobs.yaml 배포 시 자동 생성됨(§7)
  3. 알람 → SNS Topic 생성해 이메일/Slack(Chatbot 연동)으로 통지

6-3. 백업

  • RDS 자동 백업은 §3-4에서 이미 설정(dev/stg 7일). prod는 35일 + PITR로 §9에서 재설정
  • S3 버킷 버저닝 활성화(§7-2)
  • 스냅샷에서 실제로 복원해보는 연습을 분기 1회 일정으로 등록(캘린더에 반복 일정 추가 권장)

7. 부가 리소스 — S3 · SQS

7-1. S3 버킷 3개

콘솔 S3 → Create bucket:

버킷 설정
sgb-uploads-<env> 퍼블릭 액세스 차단(기본), 버저닝 활성화, presigned URL로만 접근
sgb-contracts-<env> Object Lock 활성화 (버킷 생성 시에만 켤 수 있음 — 나중에 못 켬)
sgb-audit-<env> Object Lock 활성화, Compliance 모드, 보존기간 5년으로 기본 잠금 정책 설정

Object Lock 설정 경로: 버킷 생성 화면에서 "Object Lock" 체크 → 생성 후 Properties → Default retention → Compliance / 5 years.

7-2. SQS 큐 4개 + DLQ

콘솔 SQS → Create queue, Standard 큐로 아래 4개와 각각의 DLQ를 생성:

큐 DLQ 용도
q-notify q-notify-dlq 알림 발송
q-review q-review-dlq 검수 큐 연동(있다면)
q-settlement q-settlement-dlq 정산 배치 연계
q-archive q-archive-dlq 귀속 로그 보관

각 큐 생성 시 Dead-letter queue 섹션에서 대응 DLQ를 지정하고 maxReceiveCount는 3~5로 설정.

8. Phase N-06 — stg 환경

dev와 완전히 동일한 절차(§3~§7)를 sgb-nonprod 계정 안에 별도 VPC(sgb-vpc-stg, CIDR 10.1.0.0/16)로 반복합니다. 차이점만 정리:

항목 dev stg
RDS 인스턴스 db.t4g.small db.t4g.small (운영과 동일 구성이나 축소)
ECS 오토스케일 min2/max4 min1/max2 (부하 적음)
도메인 *-dev.sogaebaenk.co.kr *-stg.sogaebaenk.co.kr
용도 개발자 공용 인수검증 · 마이그레이션 리허설
야간 자동 중지 선택 dev와 함께 EventBridge Scheduler로 야간 ECS Desired count 0 처리 (비용 절감)

야간 자동 중지는 EventBridge Scheduler에서 매일 22:00에 aws ecs update-service --desired-count 0을 호출하는 Lambda를 하나 더 만들어 연결하면 됩니다(§10의 EventBridge 설정과 같은 패턴).

9. Phase N-07 — prod 환경 (Multi-AZ, WAF)

sgb-prod 계정에서 §3~§7을 반복하되, 아래는 prod 전용으로 반드시 다르게 설정합니다.

9-1. RDS 차이

항목 값
인스턴스 클래스 db.t4g.medium
Multi-AZ 활성화 (단, 비용 때문에 오픈 D-14에 전환 — 그 전까지는 Single-AZ로 월 $130 절감)
백업 보존 35일
PITR(Point-in-Time Recovery) 자동 백업 활성화 시 기본 제공 — 별도 스위치 없음, 백업 보존기간만 35일로 설정하면 됩니다
커넥션 풀 한도 확인 태스크 수 × DB_POOL_MAX ≤ db.t4g.medium 최대 커넥션. 현재 web-api 2~4대 × 풀 10 = 최대 40이므로 여유 있게 설정되어 있는지 RDS 파라미터그룹의 max_connections 확인

9-2. ElastiCache Multi-AZ

  • 오픈 전 Multi-AZ(자동 장애 조치)로 전환: ElastiCache 콘솔에서 클러스터 수정 → Multi-AZ 활성화, 복제본 1개 이상 추가

9-3. WAF 연결

  1. 콘솔 검색 WAF & Shield → Web ACLs → Create web ACL
  2. Resource type: Regional resources → 리소스로 prod ALB 선택
  3. Rules 추가: AWS 관리형 규칙 그룹 AWSManagedRulesCommonRuleSet, AWSManagedRulesKnownBadInputsRuleSet, AWSManagedRulesSQLiRuleSet 최소 3종 연결
  4. Rate-based rule 추가(예: 5분간 동일 IP 2000요청 초과 시 차단)로 기본 DDoS/무차별 대입 방어

9-4. NAT EIP — §4의 prod 등록용 IP가 바로 이 계정의 것

prod VPC의 NAT EIP를 §4에서 미리 확인해 연동사에 등록 신청을 넣어두었는지 재확인합니다. 심사가 2~4주 걸리므로 N-02(prod)를 시작하는 시점에 이미 신청이 진행 중이어야 N-07 완료 시점과 맞습니다.

9-5. IAM 접근 통제

  • prod 계정은 §2-4에서 만든 IAM Identity Center의 임시 승인형 permission set으로만 접근
  • ECS 태스크 실행 역할(Task Execution Role)과 태스크 역할(Task Role)을 분리 — 실행 역할은 ECR pull + CloudWatch Logs만, 태스크 역할은 애플리케이션이 실제 쓰는 Secrets Manager/S3/SQS 권한만 최소 부여

10. 배치 스케줄 연결 (EventBridge) — prod 기준

키트에 이미 완성된 CloudFormation 템플릿(infra/eventbridge-jobs.yaml)이 있으므로 직접 만들지 말고 배포만 합니다.

  1. 먼저 JOB_TOKEN을 Secrets Manager에 등록(§6-1에서 이미 함) → ARN 확인
  2. AWS CLI로 배포 (콘솔에서도 CloudFormation → Create stack → Upload a template file로 동일하게 가능):
aws cloudformation deploy \
  --template-file infra/eventbridge-jobs.yaml \
  --stack-name sgb-jobs \
  --parameter-overrides \
      ApiEndpoint=https://api.sogaebaenk.co.kr \
      JobTokenArn=arn:aws:secretsmanager:ap-northeast-2:<계정ID>:secret:sgb/prod/JOB_TOKEN-xxxxxx \
  --capabilities CAPABILITY_IAM
  1. 배포되는 것: sgb-jobs 스케줄 그룹, 매분 tick을 부르는 Lambda(sgb-job-invoker), 실패/무응답 CloudWatch 알람 2종
  2. 확인:
aws scheduler list-schedules --group-name sgb-jobs
# 1건이어야 함 (Tick 스케줄 하나)
psql "$DATABASE_URL" -c "SELECT * FROM v_job_stale;"
# 0행이어야 정상
  1. 주의: dev/stg에서 스케줄러 데몬(npm run scheduler, docker-compose의 scheduler 서비스)을 계속 쓰는 것은 무방하지만, prod ECS에는 worker 태스크에 데몬을 올리지 않습니다 — EventBridge가 대체합니다. §3-8에서 만든 sgb-worker 태스크는 dev 한정이며, prod ECS 서비스 목록에는 worker를 아예 만들지 않는 것을 권장합니다.
