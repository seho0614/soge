# 소개뱅크(SGB) 요구사항정의서 및 설계서

Sep 18, 2026 · 작성 @박세호

## 0. 문서 개요 및 전제

**목적**: 앞서 정리한 소개뱅크(SGB) 용어집을 기반으로, 요구사항 정의서와 프론트엔드/백엔드/DB/API 4개 설계서를 하나의 문서로 통합 작성한다.

**전제·한계 (반드시 먼저 읽을 것)**

| 항목 | 상태 |
| --- | --- |
| 이 문서의 성격 | 기존 설계 문서·화면정의서·법무자문 문서에 이미 기록된 결정사항을 재구성한 **설계 수준 정의서**다. kit 실제 코드베이스 접근이 아직 이뤄지지 않아(현재상태 문서 기준 "코드 접근 닿지 않음"), 아래 API 라우트·DB 컬럼명 등 코드 레벨 세부사항은 **문서 기준 추정**이며 실측이 아니다 |
| 기술 스택(확정) | 백엔드 NestJS/TypeScript/PostgreSQL 16 · 프론트엔드 Next.js(사용자) + Vite SPA(어드민) · 결제 Toss Payments |
| 규모(실측, 2026-09-04 기준) | 화면 90개 · API 149개 라우트 · 자동화 테스트 294개(136 불변식·113 공격·22 문서·25 결제) |
| 규모(설계 단계 추정) | 통합본 기준 화면 최대 172개(건강몰 21 · 광고 플랫폼 26 포함), 라우트 최대 214개 — **문서마다 수치가 다르며 kit 대조 전까지 확정값 아님** |

**대상 범위**: 소개형 4관(MNY·MAL·BIZ·LED) + 건강몰(HLT). 광고 플랫폼(외부 송출형)은 별도 트랙이라 이 문서에서는 개요만 다룬다.

## 1. 요구사항 정의서 — 기능요구사항

### 1-1. 관(館) 공통 기능

| ID | 요구사항 | 설명 |
| --- | --- | --- |
| FR-01 | 회원가입/로그인 | 사업자 회원 가입, 사업자등록번호 진위확인(국세청 API), PASS 본인인증(시점 정책 B-07 미확정) |
| FR-02 | 리스팅 등록 | 관별 카테고리 선택 → 상세정보 입력 → 지역 등록 → 검수 대기 |
| FR-03 | 리스팅 검수 | 운영 BO에서 승인/반려, 반려 시 사유 필수 |
| FR-04 | 소개받기(요청) 등록 | 소비자/사업자가 원하는 조건의 요청을 등록 |
| FR-05 | 매칭·대화 | 리스팅과 요청 간 1:1 대화, 소개 제안·수락 |
| FR-06 | 거래 성사 확정 | 양측 당사자가 사람이 직접 확인(INV-3·4) |
| FR-07 | 소개비 정산 | 당사자 간 직접 수수, 플랫폼 비개입(INV-9) |
| FR-08 | 구독 관리 | BASIC/STANDARD/PRO 멤버십 가입·변경·해지, 무료 프로모션 기간 관리 |
| FR-09 | 소개코드 발급·초과과금 | 월 무료 건수 초과 시 건당 정액 과금 |
| FR-10 | 소개캐시 충전·차감·환불 | 선불 충전, FIFO 차감, 3년 만료 |

## 1-2. 요구사항 정의서 — 비기능요구사항 및 핵심 비즈니스 규칙

### 비기능요구사항(NFR)

| ID | 요구사항 | 기준 |
| --- | --- | --- |
| NFR-01 | 권한 계층(RBAC) | 서버 사이드 필수 — 현재 미구현(A-08), 완료 전까지 네트워크 IP 제한으로 임시 방어 |
| NFR-02 | 결제 안정성 | 2시간 주기 배치, 1일 최대 10회 재시도, RETRYABLE/TERMINAL 분류 |
| NFR-03 | 검수 처리 SLA | 검수 1명 기준 일 50건, 24시간 이내(B-09R) — 물량 증가 시 병목 |
| NFR-04 | 데이터 무결성 | 스키마 diff 0줄 유지, 기존 테이블에 컬럼 추가 금지(신규 도메인은 1:1 부속 테이블) |
| NFR-05 | 회귀 안전성 | 헤더/네비게이션 변경 시 상수는 append만, 덮어쓰기 금지 — 과거 관축재편 사고 사례 |
| NFR-06 | 테스트 커버리지 | 불변식·공격·문서·결제 4영역 자동화 테스트 유지(현재 294건) |
| NFR-07 | 소유권 검사 | 판매자센터 등 전 화면·API에 `seller_id` 소유권 검사 강제 — 프런트 파라미터 신뢰 금지 |

### 핵심 비즈니스 규칙(불변식 INV) — 시스템 설계의 제약 조건

| 코드 | 규칙 | 설계 영향 |
| --- | --- | --- |
| INV-9 | 소개비 당사자 직접 수수, 거래수수료 0원 | 정산 로직에 플랫폼 수수료 계산 로직 없음 (단, 정의 재확인 필요 — 하단 참고) |
| INV-11 | 플랫폼 자금 수탁 금지 | 에스크로 미보유, 결제는 구독/캐시 충전만 플랫폼 지갑 경유 |
| INV-2 | 90일 first-touch 단일 티어 귀속 | 귀속 판정 배치/트리거 필요 |
| INV-6 | 제한업종 등록 차단 | 관 단위 예외 플래그(I-06) 미구현 — 건강몰 착수 선행조건 |
| INV-L1\~L3 | 1리드=1사업자 독점, 재판매 금지 | 리드 배분 시 동시성 제어(락) 필요 |
| INV-H1\~H10 | 건강몰 자금분리·고지·자격·심의·재고·서버재계산·청약철회·주문분리·자격만료 | DB 트리거·CHECK 제약으로 집행(코드 로직 아님) |

> **INV-9 정의 확인 필요**: 종합 실행계획 문서에서 이미 표시한 대로, '소개비 직접 수수·공제 0원' 정의와 '회원 등급별 수수료 공제·거래수수료만 0원' 정의가 대화 중 함께 제시되었다. 정산 로직(특히 API/DB 설계의 수수료 계산 필드 존재 여부)은 이 정의에 따라 완전히 달라지므로, **이 문서의 API·DB 설계는 잠정적으로 INV-9(직접수수·공제 0원)을 기준으로 하되, 수수료 공제 방식이 확정되면 재설계가 필요하다.**

## 2. 프론트엔드 설계서

### 2-1. 기술 스택 및 앱 구성

| 앱 | 기술 | 대상 |
| --- | --- | --- |
| 사용자 사이트 | Next.js | 일반 사업자 회원, 건강몰 소비자 |
| 어드민(BO) | Vite SPA | 운영팀 |
| 판매자센터(건강몰) | 판매자 헤더(파트너 헤더 구조 복제) + 백오피스 slim 푸터 | 건강몰 BRAND/TENANT 판매자 |
| 파트너센터(레거시→통합) | 파트너 헤더 3종 | 소개리드 사업자 |

### 2-2. 화면 ID·라우팅 규칙

```
SB - <영역3> - <기능3> - <일련3>
영역: HOM(통합사용자) · MNY · MAL · BIZ · MYP(마이페이지) · PTC(파트너센터)
      ADM(운영BO) · AI(공통AI) · HLT(건강몰) · SLR(판매자센터)
```

- 한 화면 = ID 하나. 탭/모달은 화면이 아니라 상태로 취급(`-M1` 접미 예외)
- ID는 재사용 금지 — 화면 폐기 시에도 번호는 비워둠
- 새 화면은 기능 코드를 예약표에서 먼저 확보한 뒤 생성

### 2-3. 공통 UI 규칙

| 항목 | 규칙 |
| --- | --- |
| 헤더 | 사용자·운영·파트너 3종 + 모바일 앱바, 높이 59px 통일 |
| 푸터 | 전체·백오피스 slim·모바일 mini 3형, 법정고지 5건 표시(현재 TBD) |
| GNB 변경 | 관 목록 상수는 **append만** — 덮어쓰기 시 전 화면 헤더 붕괴 이력 있음 |
| 역할 탭 | 좌측 "소개 합니다"(등록) / 우측 "소개받기"(요청 목록), 14개 화면 공통 적용 |
| 뒤로가기 | 이력 스택 우선, 없으면 화면별 상위 화면(PARENT 매핑표) 적용 |
| 페이지네이션 | 실제 건수 기준 계산, 1쪽뿐이면 명시 |

### 2-4. 화면 구성 (관별 개략)

| 관 | 화면 수(추정) | 주요 그룹 |
| --- | --- | --- |
| 소개형 4관 통합(HOM 등) | 90개 실측 기준 다수 | 메인·가입·등록·목록·상세·대화·거래·정산·구독 |

| 건강몰 판매자센터(SLR) | 18개(P2) | 대시보드·상품·재고·주문·반품·정산·자격·QnA·계정·정책 |
| 운영 BO | 24개+ (건강몰 14개 별도) | 검수·거래감독·정책·사이트관리·건강몰 전용 |

### 2-5. 상태·데이터 처리 원칙

- 주문 금액 등 서버가 재계산하는 값은 클라이언트 계산값을 신뢰하지 않고 응답값으로 대체 표시(INV-H6)
- 판매자센터는 전 화면 `seller_id` 소유권 스코프 강제, 목록 쿼리에 프런트 파라미터로 타 판매자 데이터 접근 불가
- 자동 사전검사(상품 등록 시 BLOCK/WARN)는 제출 즉시 화면에서 결과 표시, 메일 통보 방식 지양(검수 인력 부담 경감이 목적)

### 2-6. 미확정 항목

- 모바일 전용 주소 체계(현재 데스크톱과 동일 주소 사용 중, C-04 결정 필요)
- 서브도메인 간 로그인 세션 공유 방식
- 건강몰 반응형 단일 URL 여부(별도 URL 결정 시 화면 수 재산정 필요)

## 3. 백엔드 설계서

### 3-1. 아키텍처 원칙

| 원칙 | 내용 |
| --- | --- |
| 도메인 격리 | 소개형(4관) · 건강몰(HLT) · 광고(별도 트랙)는 테이블·서비스 단위로 분리, 공통은 회원·인증·주소·카테고리·결제 게이트웨이만 |
| 무변경 우선 | 기존 149라우트·11개 마이그레이션 베이스라인은 신규 기능 추가 시 한 줄도 건드리지 않는 것이 목표 |
| 불변식 집행 위치 | 애플리케이션 코드가 아니라 DB 트리거·CHECK 제약으로 집행(INV-H1\~H10 등) — 우회 경로 원천 차단 |
| 결제 배치 격리 | 구독(기존) · 상품(건강몰) · 충전(광고)이 한 배치에 섞이면 재시도 대상이 아닌 건이 반복 재시도됨 → 테이블·서비스 완전 분리 |

### 3-2. 모듈 구성(NestJS)

| 모듈 | 책임 |
| --- | --- |
| Auth | 로그인·가입·본인인증(PASS)·사업자 진위확인(국세청 API) |
| Listing | 리스팅 등록·검수·목록 (소개형 4관 공통) |
| Deal | 매칭·대화·거래 성사 확정 |
| Referral | 소개코드·소개비 귀속(90일 first-touch), 소개캐시 |
| Subscription | 멤버십 구독(BASIC/STANDARD/PRO), 구독 결제 배치 |
| Lead | 리드 접수·배분(1리드=1사업자)·반려, 정액 슬롯 광고 |
| HLT-Catalog | 건강몰 상품·카테고리·옵션·SKU |
| HLT-Order | 장바구니·주문·결제·배송·반품, 서버 금액 재계산 |

### 3-3-1. 권한 설계 상세 (A-08)

> 아래는 실제로 설계·구현되어 검정 53건(DB 35 · HTTP 공격 18)을 통과한 내용이다. 3-3의 "없음" 표기는 **기존 149개 라우트에 대한 전수 적용이 안 된 상태**를 뜻하며, 설계·엔진 자체는 이미 존재한다.

**핵심 원칙 — 권한 판정 로직은 코드가 아니라 DB에 있다**

가드는 토큰만 꺼내 `fn_authorize()`를 호출하고 그 결과를 그대로 따른다. 새 라우트를 코드로만 추가해도 검사가 빠지지 않도록, "누가 무엇을 할 수 있는가"는 전부 DB 테이블에 등록한다.

| 테이블 | 역할 |
| --- | --- |
| `auth_route_acl` | 어떤 주소(라우트)에 어떤 권한이 필요한가 |
| `auth_role_permissions` | 어떤 역할이 어떤 권한을 갖는가 |
| `auth_resource_map` | 어떤 자원의 소유자 정보가 어느 테이블·컬럼에 있는가(조인 경유 포함) |
| `auth_account_roles` | 계정↔역할 매핑, `granted_by` 필수(부여자 없는 권한 부여 불가) |
| `auth_sessions` | 세션 유효성, 폐기 시 즉시 무효화 |
| `auth_audit` / `auth_grant_audit` | 접근·권한부여 감사 로그, append-only |

**fail-closed 원칙**: `auth_route_acl`에 등록되지 않은 라우트는 최고관리자(SUPER)가 호출해도 **404**로 거부한다 — 403이 아니라 404인 이유는 그 주소가 존재하는지조차 알려주지 않기 위함이다.

**역할(12종, 예시 구성)**: MEMBER · BIZ\_OWNER · BROKER · PARTNER · SELLER · ADVERTISER · PUBLISHER · CONTENT · OPS · **OPS\_PAYOUT**(지급 전담, 직무 분리) · LEGAL · SUPER

**권한 판정 순서**: 라우트 등록 확인 → 공개 여부 → 세션 유효성 → 권한 보유 → 소유권 검사. 하나라도 실패하면 즉시 거부하고 사유를 감사 로그에 남긴다.

**권한 관련 불변식**

| 코드 | 규칙 |
| --- | --- |
| INV-A08-1 | 등록되지 않은 라우트는 거부(fail-closed) |
| INV-A08-2 | 운영 권한(`admin.*`)은 운영 역할만 보유 가능 |
| INV-A08-3 | 본인 소유 자원만 접근 — 같은 역할이라도 타인 자원 접근 불가(IDOR 방지) |
| INV-A08-4 | 권한 부여는 부여자 기록 없이 불가 |
| INV-A08-5 | 자기 자신 또는 자기보다 높은 등급의 역할을 스스로 부여 불가(권한 상승 방지) |
| INV-A08-6 | 만료·폐기된 세션은 통과 불가 |
| INV-A08-7 | 감사 로그는 수정·삭제 불가(append-only) |

**직무 분리 예시(광고 정산 트랙에서 검증된 패턴 — 소개뱅크 정산에도 적용 권고)**

| 역할 | 이상 거래 감시 | 원장 열람 | 지급 실행 |
| --- | --- | --- | --- |
| OPS(운영팀) | 가능 | 가능 | **불가** |
| OPS\_PAYOUT(지급 전담) | 불가 | 가능 | 가능 |

→ 부정 판정을 만드는 사람과 돈을 내보내는 사람을 분리해, 사고 발생 시 되돌릴 근거를 남긴다.

**소유권 검사 예시**: 소유권 검사가 없으면 "역할은 맞지만 남의 자원"인 요청이 통과한다. `fn_owns()`가 `auth_resource_map`을 참조해 조인을 거쳐서라도 실제 소유자를 확인하고, 등록되지 않은 자원 종류는 항상 거짓(비소유)으로 판정한다.

**적용 상태 및 남은 일**

| 항목 | 상태 |
| --- | --- |
| 엔진(테이블·함수·트리거) | 설계·구현 완료, 검정 53건 통과 |
| 로그인 수단(PASS·비밀번호) 연동 | 미완 — 현재는 계정 id만 받는 데모 |
| BO 로그인 화면 | 없음 |
| 세션 갱신(refresh) | 없음 — 만료 시 재로그인 필요 |
| **기존 149개 라우트의 ACL 등록** | **미완료** — 코드 접근 후 전수 등록 필요, 미등록 상태로 전역 가드를 걸면 전부 404가 됨(순서 주의) |
| 판매자센터·건강몰·광고 3트랙 적용 | 설계 공유 완료, 개별 트랙 적용은 각 트랙 착수 시점에 진행 |

**ACL 미등록 상태의 의미와 절차**

| 현재 등록 | 미등록 |
| --- | --- |
| A-08 설계·검정 시 예시로 넣은 26건(공개 6·보호 20) | 기존 운영 중인 **149개 라우트 전부** |

fail-closed 원칙상 라우트가 `auth_route_acl`에 없으면 무조건 404로 거부되며, SUPER 권한으로도 통과할 수 없다. 따라서 **현재 상태에서 가드를 전역 적용하면 등록된 26건만 동작하고 나머지 149개는 전부 막힌다** — 절대 지금 바로 전역 적용해서는 안 된다.

**정해진 순서**

| # | 단계 | 선행 |
| --- | --- | --- |
| 1 | kit 코드 접근 → 실제 149개 라우트 목록 확보 | — |
| 2 | 라우트별 필요 권한·소유권 컬럼 매핑(등록표는 스크립트로 생성, 손으로 고치지 않음) | 1 |
| 3 | `auth_route_acl`에 149건 일괄 등록 | 2 |
| 4 | 스테이징에서 가드 전역 적용 | 3 |
| 5 | 기존 자동화 테스트 294건 재실행 — 권한 추가로 깨지는 곳 확인 | 4 |

> 현재는 1번(kit 코드 접근)이 막혀 있어 2\~5번이 전부 대기 상태다. 과거 유사 작업(3체계분리 라우트등록표)에서도 라우트 133건 중 106건이 "문서 기준 추정"으로 남았던 것과 같은 원인 — 실제 코드 없이는 정확한 경로·메서드를 확정할 수 없다.
