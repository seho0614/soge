# 702 권한 관리 검토 · 회원 · 직원 분리 설계 (v10.561 ~ 564 · D291)

- 날짜: 2026-11-21 · 대표 승인: A안(11/21) · 같은 날 「업무 목록 → 업무그룹 → 권한그룹 → 사원에게 부여(사원 권한은 권한그룹이 정함 · 회원은 기존 규칙)」를 A안과 합쳐 한 번에
- 판: v10.561 · 562 · 563 · 564(4판) · 마이그레이션 D291 하나(#329) · 문서 703 ~ 706 · 시험 test_v1561 ~ 1564

## 1. 결론
1. 계정 표(accounts)는 하나로 두고 **화면 · 규칙만 나눕니다**(A안). 「운영자」 = 운영 역할(account_roles) 하나 이상 — 새 역할을 만들지 않습니다.
2. 운영자 관리는 「직원 · 권한」 그룹 한 곳으로 모읍니다 — 운영자 목록 · 사원 권한 · 권한그룹 · 업무그룹 · 업무 목록 · 업무별 권한 · 역할 주기 · 권한 점검 · 접속 인증 · 바뀐 기록 · 내 2단계 · 내 비밀번호.
3. 사원(운영자)의 업무 권한은 **권한그룹이 정하도록** 판정을 바꿀 수 있게 하되(perm.mode GROUPS), 처음 값은 지금과 같은 ROLE 이고 COMPARE 로 「다름 0」을 확인한 뒤에만 GROUPS 로 갑니다. 회원 역할(MEMBER · BIZ_OWNER · BIZ_STAFF) 검사는 그대로입니다.

## 5. 운영 · 보안 주의
1. 잠김 방지 — SUPER 는 두 가드 모두 늘 통과 · perm.mode 바꾸기 API 는 SUPER 전용이라 권한그룹을 보지 않음 · GROUPS 는 서버 조건 + DB 트리거(app.perm_mode_ok)로만 · 되돌리기는 조건 없음.
2. 업무 단위가 탭이라 같은 탭 안에서 역할마다 다르던 API(예: 지급 데스크의 지급 실행은 PAYOUT 만)는 GROUPS 에서 그 업무 · 수준을 가진 사람에게 열릴 수 있음 — COMPARE 의 GROUP_ONLY 기록 · 조합 규칙 · DB 쪽 겸직 검사(fn_has_role · C710)가 남아 있음. GROUPS 전 COMPARE 로 확인 필수.
3. 정적 도구로 만든 주소 시드는 운영 서버 실제 주소(GET /admin/perm/unmapped-routes)로 다시 확인.
