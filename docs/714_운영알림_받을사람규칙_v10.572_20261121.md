# 714 · 운영 알림 받을 사람 규칙 — v10.572 (2026-11-21)

> 10차 운영 기반 ④. 운영 화면 **위험감지 › 알림 받을 사람 규칙**(탭 `opb-alert-routes` · SB-ADM-OPB-020) · **SUPER 만**. 앞머리 `opb_`.

## 1. 결론

1. 운영 알림 종류(`ops_alerts.alert_code`)마다 **받을 길**(텔레그램 · 메일 · 슬랙 · 게시판) · **급함 기준**(이 등급 이상이면 보냄) · **묶음 간격**(같은 종류를 그 길로 다시 보내기까지 분) · **받을 권한그룹**을 정합니다.
2. **처음 값 = 지금 동작**: 기본 줄(`*`) = CRITICAL 만 네 길 · D220 목록 13종 = 급함 상관없이 네 길 · 60분. 시험이 「처음 규칙으로 고른 것 = 지금 함수」를 DB 에서 확인합니다.
3. 스위치 둘 **처음 off** — `opb.alert_routes`(off = 규칙을 쓰지 않고 지금 함수 그대로) · `opb.alert_group_mail`(off = 권한그룹 사람에게 따로 메일 안 보냄). 표를 먼저 고쳐 두고 켜면 그때부터 따릅니다.

## 2. 늘 지키는 것(규칙으로 못 바꿈)

| 것 | 까닭 |
|---|---|
| 감사 기록 위변조 의심(`AUDIT_CHAIN_BROKEN`)은 규칙을 만들 수 없고 늘 네 길 | D235 · 잠시 끄기도 못 함(D239)과 같은 원칙 |
| CRITICAL 은 게시판을 꺼도 늘 게시판에 올림 | 기록이 남는 길 하나는 늘 남김 |
| 「알림 잠시 끄기」(alert_mutes)는 그대로 먹음(게시판 제외 — 지금과 같음) | D239 |
| 기본 줄(`*`)은 지울 수 없음(DB 트리거) | 목록에 없는 종류가 갈 곳 |
| 「다시 알림」(12시간 넘게 확인 안 한 CRITICAL)은 지금 함수 그대로 · 그 길이 규칙에서 꺼진 종류만 뺌 | D176 · D178 · D200 |

## 3. 화면

1. 스위치 두 개(사유 2 ~ 200자 · 바꾼 기록 · 설정 바뀐 기록에 남음).
2. **규칙 표** — 종류 · 텔레그램 · 메일 · 슬랙 · 게시판 · 급함 기준 · 묶음 간격 · 받을 권한그룹 · 처음 값과 같음/바뀜 · 「고치기」 · 「빼기」(기본 줄 제외).
3. **최근 30일 알림 종류** — 수 · 급함 수 · 마지막 · 따르는 줄(기본 · 전용) · 「지금 동작」 길 · 「규칙대로면」 길(다르면 빨강) · 「규칙 더하기」.
4. **바꾼 기록 30줄**(쌓기만 · 고치기 · 지우기 DB 가 막음).

## 4. 서버 연결(스위치 on 일 때만 · off 면 null 을 돌려 지금 코드 그대로)

| `alertPushPending` | 텔레그램 · 슬랙 대기 = `opbRoutePending('telegram' · 'slack')` — 운영 화면 미리보기도 같은 함수 |

| `scheduler.service.ts` `alertMail` | 대표 메일(ops.digest_to) 한 통 보낸 뒤 `opbGroupMail` — 스위치 둘 다 on 일 때만 · 그 묶음 종류의 권한그룹 사람(기한 안 · ACTIVE · 운영 역할 · 메일 있음 · 대표 메일 주소 빼고 · 20명까지)에게 **자기 그룹 알림만** 한 통씩 · 실패해도 대표 메일 결과 그대로 |

## 8. 켜는 순서(대표)

1. 규칙 표에서 바꾸고 싶은 종류만 「규칙 더하기」 · 고치기(예: 백업 실패 = 메일만 · 낯선 로그인 = 텔레그램만).
2. 「최근 30일 알림 종류」의 빨간 줄(지금 동작과 다름)을 확인.
3. 「규칙 쓰기」 켜기(사유) → 다음 보내기 차례(5분 안)부터 따름 · 이상하면 끄면 바로 지금 동작.
4. 권한그룹 메일은 메일 준비(ops.digest_to · SMTP) 뒤 · 받을 사람 명단을 권한그룹에서 확인한 뒤 켬.
