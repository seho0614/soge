# 322. 운영 지침서 — v10.202 (2026-11-06)

> 운영 화면(관리자 페이지)을 날마다 쓰는 운영진을 위한 지침서입니다. 개발 문서가 아닙니다.
> 기준 판은 **v10.203**(개발 · docs/324 까지)입니다. 운영 서버는 v10.202(11/6 docs/320 적용)라 v10.203 의 것(사용자 설명서 탭 · 내 2단계 인증 「설정 바꾸기」 · 「모든 기기에서 로그아웃」 · 운영 알림 한국어 이름 21종)은 docs/325 적용 뒤에 보입니다.
> 이 문서는 **코드에 적힌 것만** 옮겼습니다. 코드로 확인할 수 없는 것은 「추가 확인이 필요합니다」로 적고 9절에 모았습니다.
> 지금 외부 연동(결제 · 본인인증 · 1원 계좌인증 · 중개사 대조 · 전자세금계산서 · 알림톡 · 메일 등)은 **끝나지 않았습니다.** 여러 기능이 **간주 모드**(연결된 것으로 치고 실제로는 돌지 않는 상태)로 돌아갑니다. 화면에 「결제 완료」가 떠도 실제 돈이 오가지 않을 수 있습니다.
> 가장 중요한 세 가지:
> 1. 아침마다 **대시보드 「공개 직후 지켜보기」 → 운영 알림 → 검수 큐 → 신고 처리** 순서로 봅니다(3절).
> 2. **긴급(CRITICAL) 알림은 처리한 뒤 꼭 「확인」**을 누릅니다. 확인하지 않은 긴급이 남아 있으면 배포 점검이 실패합니다(4절).
> 3. **「주문 받기」는 결제대행사 연결 전에는 켜지 않습니다.** 잘못 켜졌으면 누구든(운영 · 최고 관리자) 바로 끕니다(5절 · 8절).

### 1-2. 운영 화면 쓰는 기본

1. **로그인**: 로그인 전에는 로그인 화면만 보입니다. 2단계 인증이 켜져 있으면 로그인 뒤 6자리 번호 넣기 화면(등록 안 했으면 등록 화면)만 보입니다.
2. **메뉴 모양**: 위 어두운 줄 = 묶음 메뉴 18개 · 본문 위 줄 = 그 묶음의 탭. 묶음을 누르면 그 묶음에서 볼 수 있는 첫 탭으로 갑니다. 권한이 없는 탭은 보이지 않습니다.
3. **주소로 바로 가기**: 지금 보는 탭이 주소 끝(`#/탭이름`)에 남습니다. 새로 고침 · 뒤로 가기에도 같은 탭이 열립니다. 예: `#/ops-alerts`(운영 알림) · `#/hlt-orders`(소개몰 주문).
4. **화면 번호**: 각 화면 제목 줄에 `SB-ADM-…` 번호가 있습니다. 개발에 문의할 때 이 번호를 함께 적습니다.
5. **사용자 웹에서 들어오기**: 운영 계정으로 사용자 웹에 로그인하면 머리줄 오른쪽에 **방패 아이콘**(마우스를 올리면 「관리자 페이지」)이 보입니다(v10.202). 휴대폰은 메뉴 줄 끝 「관리자 페이지」 글자입니다.
6. **기록이 남는 일**: 설정 바꾸기 · 확인 · 승인 · 반려 · 역할 주기 등은 누가 · 언제가 감사 기록에 남습니다. 사유 칸이 있으면 나중에 남이 읽고 알 수 있게 적습니다.
7. **문의 · 보고할 때 적을 것**: 화면 번호 · 시각 · 누른 단추 · 나온 글(오류 코드가 있으면 그대로 · 예: `ORDER_OPEN_REASON`).

## 2. 역할과 권한

### 2-1. 원칙

1. **최고 관리자(SUPER)는 모든 권한**을 가집니다. 서버 · DB · 운영 화면 모두 「SUPER 는 권한 검사를 늘 통과」로 만들어져 있습니다(decisions/super-all-permissions #1 · #2). 감사 기록은 SUPER 도 그대로 남습니다(#3).
2. 다만 **두 사람 원칙**(확정한 사람 ≠ 지급한 사람 · 신청자 ≠ 승인자 ≠ 집행자)은 SUPER 도 지킵니다(#5). 자기가 확정한 지급은 자기가 지급 기록을 남길 수 없습니다.
3. 운영 화면은 역할에 맞는 탭만 보여 줍니다. 보이지 않는 탭은 서버도 거절합니다(App.tsx 주석 「서버가 막는 탭을 보여 주면 눌러도 403 만 납니다」).
4. **역할 주기 · 회수는 SUPER 만** 합니다(메뉴 「권한 계층 › 권한 관리」 · 서버 `POST /admin/reports/roles` = SUPER). 사유를 꼭 적어야 하고, **자기 권한은 바꿀 수 없습니다**(`SELF_GRANT`).
5. 안심 · 제휴 파트너 담당과 운영(ADMIN)은 **지급 담당(PAYOUT)을 겸할 수 없습니다** — SUPER 는 예외(decisions/super-all-permissions #6 · partner-center-account-basis #19).

## 4. 운영 알림 대응표

### 4-1. 먼저 알아 둘 것

1. **알림 화면**: 위험감지 › 운영 알림. 맨 위 「급한 알림 메일」 줄 · 「급한 알림 텔레그램」 줄 → 「종류별」 표(확인 안 함 · 풀림 · 지난 7일 · 「모두 확인」) → 알림 목록(「확인」 · 「자세히」).
2. **급한 알림**(메일 · 텔레그램으로 10분 안에 보냄): 모든 **긴급(CRITICAL)** + `SETTING_CHANGED` · `UPLOADS_BACKUP_FAILED` · `UPLOADS_BACKUP_BAD` · `ORDER_OPEN_EXPIRED` · `STAFF_LOGIN_NEW` · `AGENT_LIVE` · `AGENT_READY_GAP` · `AGENT_CAP_NEAR` · `AGENT_STEP_READY`(D179 · D181 · D182 `fn_ops_alert_mail_pending`). 같은 종류는 1시간에 1통 · 24시간 지난 것은 보내지 않음 · 확인한 것 · 풀린 것은 보내지 않음.
3. **다시 알림**: 긴급을 보낸 뒤 12시간 넘게 「확인」하지 않으면 한 번 더 보냅니다(「[다시]」).
4. **지금 상태**: 운영 메일은 준비되지 않았습니다(「준비 안 됨 — 메일 설정 없음」 · NO_SMTP). 텔레그램은 대표가 봇 토큰 · 대화방을 넣어야 켜집니다(docs/317 4-3). **둘 다 준비 전이면 알림은 이 화면에만 쌓입니다** — 그래서 화면을 직접 보는 것이 중요합니다.
5. 텔레그램에는 **제목 · 등급 · 시각만** 갑니다. 자세한 내용은 운영 화면에서 봅니다.
6. **긴급이 확인 안 된 채 남아 있으면 배포 점검(deploy-check · postcheck)이 실패**합니다. 처리한 뒤 꼭 「확인」합니다.
7. 「풀림」은 원인이 없어졌다는 표시입니다. 풀린 알림은 「확인 안 한 알림」 수 · 메일 · 배포 점검에서 빠집니다. 화면은 기본으로 숨기고 「풀린 것도 보기(N건 숨김)」로 볼 수 있습니다.
8. v10.203 부터 아래 표의 모든 종류가 한국어 이름으로 보입니다(전에는 21종이 영어 코드로 보였음).

### 4-7. 알림 하나를 처리하는 순서

1. **등급을 봅니다.** 긴급 → 경고 → 안내 순서로 처리합니다.
2. **「자세히」를 엽니다.** 건수 · 기준 · 누가 · 어디서 같은 내용이 들어 있습니다.
3. **위 표에서 「할 일」을 찾습니다.** 표에 없는 코드면 개발에 화면 번호(SB-ADM-OPS-010) · 코드 · 제목을 보냅니다.
4. **원인부터 처리합니다.** 예: 검수 기한 넘김 → 검수 큐 처리 · 주문 받기 → 끄기.
5. **「풀림」이 붙는 종류는 잠시 기다려 봅니다.** 정기 작업이 원인이 없어진 것을 보면 「풀림」을 적습니다(백업 · 디스크 · 검수 기한 · 주문 받기 꺼질 시각 없음).
6. **「확인」을 누르고 메모를 남깁니다.** 긴급은 반드시.
7. **혼자 판단하기 어려우면** 대표에게 보고하고, 확인 메모에 「대표 보고 HH:MM」을 적습니다.

### 4-8. 「확인」 · 「모두 확인」 쓰는 법

1. 알림 한 줄의 「확인」 → 메모 칸(선택 · 200자)에 **무엇을 했는지** 적습니다. 예: 「주문 받기 끔 · 시험 주문 0건」.
2. 「모두 확인」은 그 종류의 확인 안 한 알림을 **풀린 것까지 함께** 한 번에 확인합니다. 원인을 보지 않고 누르지 않습니다.
3. 확인은 되돌릴 수 없습니다. 알림 내용도 고치거나 지울 수 없습니다.

2. 지금은 외부 연동이 끝나지 않아 간주를 끌 조건이 맞지 않습니다. 단추가 흐리게 보이는 것이 정상입니다.
3. 화면 안내: 「간주 모드를 하나라도 남긴 채 사용자 웹 접근 제한을 풀지 마십시오.」 — 사용자 웹은 2026-11-01 대표 결정으로 간주 모드인 채 공개되었습니다(open-blockers #27 · 대표가 위험을 알고 결정).
4. 오픈 체크리스트 탭은 SUPER 만 봅니다.

### 5-6. 다국어 (`i18n.enabled`)

1. 「다국어 켜기」 → 확인 창 「1분 안에 손님 화면 머리에 언어 단추가 나옵니다. 승인하지 않은 번역은 한국어 그대로 보입니다.」
2. **승인한 번역만** 손님 화면에 나갑니다. 켜기 전에 번역 화면에서 번역을 넣고 승인해 둡니다.
3. AI 자동 번역 · 「번역 보기」(소개광장)는 AI 설정이라 SUPER 만 바꿉니다.
4. 운영에서 지금 켜져 있는지는 추가 확인이 필요합니다.

### 5-8. 회원 투표 만들기 · 메인 투표

1. 「회원이 투표 만들기」(`poll.member_create` · 기본 꺼짐): 켜면 회원이 「궁금해요」 · 「써본 의견」 투표를 만들 수 있고 만들자마자 열립니다. 메인에는 나가지 않고, **신고 3건이면 저절로 감춰집니다**(알림 `POLL_HIDDEN_BY_REPORTS`).
2. 메인 「이건 어때?」 세 자리가 비면 사용자 웹에 「준비 중」이 보입니다. 대시보드 「메인 투표(3자리 중)」 칸이 3 아래면 노랗습니다.
3. 빈 자리는 SUPER 가 「확정 질문으로 빈 자리 채우기」 — **비어 있는 종류만** 확정 질문으로 만들고 바로 엽니다(표 0). 같은 질문이 이미 있으면 만들지 않고 알려 줍니다.

### 5-9. 운영자 2단계 인증 (`admin.mfa_required`)

1. 값: off(쓰지 않음) · SUPER(최고 관리자만) · ALL(운영 역할 모두 — 검수 · 운영 · 지급 · 최고 · 안심 파트너 · 제휴 파트너).
2. 켜기 전에 **켜는 사람이 먼저** 권한 계층 › 내 2단계 인증 「2단계 인증 등록」을 마쳐야 합니다(아니면 422 `MFA_ENROLL_FIRST` — 스스로 잠기는 일을 막음).
3. 켜면 운영 화면 로그인 뒤 6자리 번호를 넣어야 하고, 한 번 넣으면 `admin.mfa_hours`(기본 12시간) 동안 다시 묻지 않습니다.
4. 휴대폰을 잃어버린 운영자는 SUPER 가 회원 상세에서 「2단계 초기화」(본인 확인 뒤 · 사유 5자 이상).
5. 운영 화면에서 바꾸는 곳: 권한 계층 › 내 2단계 인증 「설정 바꾸기」(SUPER · v10.203 · 바꾸면 「중요 설정 바뀜」). 아무도 들어오지 못할 때 서버에서 비상으로 끄는 길은 `deploy/aws/mfa-reset.sh off`(서버 담당 · 사람이 · 「중요 설정 바뀜」 알림이 via DB 로 남음).
6. 지금 운영은 꺼진 채입니다(docs/318 계기 글).

## 6. 메뉴별 하는 일

> 순서는 운영 화면 위 묶음 메뉴(`GROUPS`) 순서입니다. 탭이 하나뿐인 묶음은 탭 줄이 없습니다. 「(SUPER)」 표시는 그 탭을 SUPER 만 봅니다.

### 6-1. 대시보드
- **대시보드**(SB-ADM-DSH-010) — 「오늘 처리해야 할 것과 처리할 수 있는 양」. 맨 위 「공개 직후 지켜보기」(ADMIN · SUPER) 칸을 누르면 해당 화면으로 갑니다. 그 아래 숫자 5칸(검수 대기 · 정산 승인 대기 · 신규 가입 승인 · 업종 신청 · 파트너 입점 · 검수) · 「검수 처리 여력」(하루 처리 기준 · 기본 50건) · 「확인이 필요한 것」 · 「활주로」(손익분기 · 필요 유료회원 등 · 실제 매출과 넣은 월 비용으로 계산) · 「다른 운영 화면」.
- 주요 단추: 「주문 받기 켜기 / 끄기」 · 「가입 잠시 막기」 · 「안내 띠 올리기」 · 「어제 요약 보기」 · 「시험 결제 주문 정리(발송 전 취소 · 알림)」(SUPER).

### 6-2. 검수
- **검수 큐** — 매물(리스팅) 검수. 기한 24시간 · 남은 4시간 미만은 임박. 「SLA 순」 · 「AI 의견 순」 · 「열기」 → 사유를 고르고 「반려」 또는 「승인」. **사유를 고르기 전에는 반려할 수 없습니다.** 같은 등록자가 제한업종 · 금칙 표현으로 3회 반려되면 7일 등록 정지(관리자에게도 알림). 「AI 의견과 같게 확인」은 AI 가 켜졌을 때만 뜻이 있고, 결정 · 책임은 검수자에게 있습니다.
- **자동검수 규칙** — 금칙어와 제한업종. 「배포 없이 바뀌지만, 잘못 넣으면 정상 등록이 반려됩니다.」 「규칙 추가」 · 「등록 차단」.
- **표본 감사** — 자동 승인된 건을 표본(약 5%)으로 다시 봅니다. 「적정」 · 「부적정」(부적정이면 그 매물 노출 중단) · 「표본 다시 뽑기」.
- **배지 신청** — 신뢰 배지 신청 「승인」 · 「반려」. 배지는 목록 노출에 영향을 주므로 근거 없이 주지 않습니다.
- **소개몰 리뷰 · 문의** — 효능 · 효과 단정 표현에 걸린 리뷰만 확인(「가리기」 · 「보이기」) · 상품 문의는 운영자가 답합니다.

### 6-3. 파트너사
- **파트너사** — 파트너센터에서 올라온 것을 본사가 처리. 하위 탭: 파트너사 목록 · 입점 신청 · 서비스 검수 · 리드 배정 · 리드 반려 · 리드 이용료 · 정산 · 의료 심의 · 카테고리 마스터 · 자격 심사. 돈이 걸린 일(이용료 등)은 ADMIN 만.
- **안심소개 입점 심사** — 안심소개 입점 신청을 축별로 「승인」 · 「반려」. 「중개사 인증이 먼저입니다」 안내가 뜨면 자격 심사부터.
- **법률·세무 정액 노출** — 전문가 정액 노출. 「입금 확인 · 노출 켜기」 · 「연장 입금 확인」 · 「반려」(사유 5자 이상 · 업체에게 그대로 보임) · 「종료」.

### 6-4. 정산
- **정산** — 「신청 → 승인 → 지급 실행」. 「승인」 · 「반려」. 소개비에서 떼는 금액은 없고, 지급은 당사자가 직접 합니다(화면 설명 INV-9 · INV-11).
- **지급** — 지급 데스크. 운영이 「확정」, 지급 담당(PAYOUT)이 「지급 기록」 · 광고비 「입금 기록」. 자기가 확정한 건은 자기가 지급 기록을 못 남깁니다.
- **소개몰 정산** — 주 단위 마감(배송 완료 뒤 7일 지난 건만). 「이번 주 마감」 · 반품 · 교환 처리 · 「지급 요청」. 맨 위 **입점 신청** 구역에 「입점 신청 받기 켜짐 / 꺼짐」 줄(5-3)과 신청 「승인」 · 「반려」.
- **청구** — 구독료 청구 현황(매출 감시). 「지금 대조」 · 「지금 청구 실행」 · 유예 일수 · 재시도 횟수 「저장」(설정이라 바로 반영). 결제는 지금 간주 모드입니다.

### 6-5. 거래
- **거래 모니터링** — 진행 중 거래 · 분쟁. 7일간 양측 확인이 안 된 건이 자동으로 올라옵니다. **관리자도 임의로 성사를 확정할 수 없습니다.** 「분쟁 처리로」.
- **분쟁** — 접수된 분쟁 처리(「보는 중」 · 「저장」). 분쟁이 걸린 거래는 정산이 보류됩니다.
- **소개몰 주문** — 결제 완료 주문 발송: 택배사 · 송장번호 넣고 「발송 처리」 → 「배송 완료로」. 「송장 고치기」. 지금 결제는 간주 모드라 「결제 완료」가 실제 입금이 아닐 수 있습니다.

### 6-6. 회원
- **회원** — 이름 · 이메일 · 연락처로 「찾기」 → 회원 상세. 「상태 변경」(정상 ↔ 정지 · 사유 필수 · 지울 수 없음) · 「등록 정지 풀기」 · 「잠금 풀기」(고객센터 본인 확인 뒤) · SUPER 만 「링크 만들기」(비밀번호 재설정 · 메일 준비 전) · 「2단계 초기화」.
- **사업자 인증** — 사업자 신청 「승인」 · 「반려」 · 회원 「정지」 · 「정지 해제」. 승인 시각이 소개비 수령 자격의 기준일입니다.

### 6-7. 업종
- **업종 승인** — 업종은 열린 집합: 신청 → 「승인」 / 「반려」 → 노출.

### 6-8. 노출
- **메인 운영** — 메인에 무엇을 띄울지(배포 없이 바로 반영). 하위: 배너 · 공지(ADMIN) · 관 노출 · 화면 구성 · 콘텐츠(SUPER). 광고는 추천 순위에 섞이지 않고 별도 자리에만 나갑니다.

### 6-9. 정책
- **정책**(SUPER) — 화면이 따르는 규칙의 원본. 값이 바뀌면 화면 문구와 계산이 함께 바뀝니다.
- **코드 라벨**(SUPER) — 화면에 보이는 상태 문구. 코드는 고정, 라벨만 바뀝니다(운영 · 이용자 쪽).

### 6-10. 관 관리
- **관 관리** — 관(사이트) 목록 · 순서. 새 관 만들기 · 관 설정 · 공유 경계는 SUPER.

- **통합 허브**(SUPER) — 통합 메인(관으로 보내는 허브) 관리.
- **오픈 체크리스트**(SUPER) — 오픈을 막는 항목. 위에 「대표 결정 · 법무 / 업체 대기 / 운영 화면에서 바로 / 날짜만 정하면 됨」 요약 · 「종류별로 보기」. 아래에 **관리자 스위치**(5-5). 「하나라도 미충족이면 열리지 않습니다」.
- **법정 고지** — 바닥줄 법정 고지 원본(「주소 반영」 · 「저장」 · 「오픈 체크리스트로」) · 요청 열람 한도 · 소개코드 범위 · 사회관계망 주소 · 맨 아래 **약관** 구역(SUPER).
- **약관**(SUPER) — 7절.
- **번역** — 번역을 넣고 「승인」 · 「반려(사유)」. 「다국어 켜기 / 끄기」(5-6).
- **소개몰 상품** — 상품 · 옵션 · 재고 · 그림 · 고시 「고치기」.

### 6-11. 광고
- **광고** — 소재 · 슬롯 · 세그먼트. 「심의필 확인」 · 「정상」 / 「중지」.
- **광고 과금** — 광고주 · 청구 · 입금 · 미수금(광고비는 소개비와 따로). 입금 기록은 지급 담당이 지급 화면에서.
- **외부 송출** — 외부 사이트 광고(클릭당 과금). 「도메인 확인」 · 「승인」 · 「보류」. 「자기가 신청한 것은 승인할 수 없습니다」.
- **퍼블리셔 지급** — 「월 마감 → 명세서」 → 신청 → 승인 → 「집행」(지급 담당). 퍼블리셔 실제 지급은 닫아 두고 정산서 · 장부까지만 운영합니다(프로젝트 규칙).

### 6-12. 위험감지

## 7. 약관 · 처리방침 게시 순서

> **원칙: 법무가 확인한 글만, 운영 화면에서 게시합니다.** 서버 스크립트 `publish-terms.sh` 는 쓰지 않습니다(docs/300 ~ 320 「하지 말 것」).
> 약관 게시는 SUPER 만 합니다(약관 API 전체가 SUPER).

### 7-1. 순서

| 순서 | 할 일 | 어디서 · 무엇을 | 누가 |
|---|---|---|---|
| 1 | 초안 고치기 | 관 관리 › 약관 → 「고치기」 → 판 번호 · 본문(50자 이상) → 「바뀐 곳 보기」 → 「저장(게시 아님)」. 게시 · 보관된 판은 고칠 수 없어 새 판 번호로 저장됩니다 | SUPER |
| 2 | 법무 검토 묶음 만들기 | 「법무 검토용 내려받기」 → HTML 파일 한 개(게시 안 된 초안 전부 · 지금 게시판과 바뀐 줄 초록/빨강 · 남은 〔미확정〕 노란 표시 · 확인 칸). 브라우저로 열어 PDF 로 인쇄해 보냄 | SUPER |
| 3 | 법무 확인 | 법무가 읽고 고칠 곳을 알려 줌. **이 파일은 검토를 돕는 자료일 뿐, 법적 판단은 법무가 합니다.** 파일은 공개된 곳에 올리지 않습니다 | 대표 · 법무 |
| 4 | 〔미확정〕 채우기 | 본문에 〔미확정〕이 한 곳이라도 있으면 「게시」 단추가 눌리지 않습니다(서버도 `TERM_HOLES`) | SUPER |
| 5 | 시행일 정하기 | 「시행일」 칸(오늘 이후 · 오픈일에 맞추는 것을 권함). 회원에게 불리한 변경이면 「회원에게 불리한 변경(30일 전 고지)」 체크 | SUPER · 법무 판단 |
| 6 | 게시 | 「게시」 → 확인 창(앞 판은 시행일 전날까지 그대로 · 재동의는 시행일부터 · 「법무 확인을 마친 글입니까?」) → 확인 | SUPER |
| 7 | 결과 확인 | 「… 을 시행 예정으로 게시했습니다 … 남은 오픈 차단 N건」 글 · 표의 상태 「시행 예정」 | SUPER |

### 7-2. 게시 때 알아 둘 것

1. **시행일 고지 기간**(이용약관 제14조 · 화면 확인 창 기준): 시행 7일 전 고지 · 회원에게 불리한 변경은 30일 전. 불리한 변경을 30일 안으로 게시하면 서버가 거절합니다(`TERM_ADVERSE_30D`). 실제 법 기준은 법무 확인이 필요합니다.
2. 시행일 전까지는 앞 판이 그대로 시행되고, 사용자 웹에 「바뀔 약관」 알림이 나갑니다.
3. 「시행 예정 게시 때 회원 알림」이 「보냄」이면 회원마다 「약관 변경 안내」 1건이 갑니다(사이트 안. 메일 · 알림톡은 켜진 뒤).
4. 「새 판 재동의: 시행일부터」가 기본입니다. 「게시 즉시로 바꾸기(법무 판단 뒤)」는 법무 판단 없이 누르지 않습니다.
5. 게시하면 이용자와의 계약 조건이 되고, 되돌려도 이미 받은 동의 기록은 남습니다.
6. 시행일 전이고 동의 기록이 없을 때만 「예정 취소」가 됩니다(법무 검토 판으로 돌아감). 동의가 한 건이라도 있으면 새 판으로 바꿔야 합니다(`TERM_HAS_CONSENT`).
7. 시행 예정인 판이 이미 있으면 새로 게시할 수 없습니다 — 먼저 그 판을 「예정 취소」(`TERM_SCHEDULED_EXISTS`).
8. **개인정보처리방침**은 표에 「국외 이전 조항 있음(AI 켜기 조건) / 없음」이 함께 보입니다. AI 를 켜려면 이 조항이 든 판이 게시돼 있어야 합니다(5-7).
9. **입점 약관(HLT_SELLER)**을 게시해야 「입점 신청 받기」를 켤 수 있습니다(5-3).
10. 운영의 게시 안 된 초안 수 · 남은 〔미확정〕 수는 운영 화면 결과 글로만 알 수 있습니다(9절).

## 8. 비상시 판단 순서

### 8-1. 「운영자 낯선 로그인」이 본인이 아님

| 순서 | 할 일 | 누가 |
|---|---|---|
| 1 | 알림 「자세히」에서 계정(이메일 앞 두 글자) · 역할 · IP 대역 · 브라우저 · 까닭을 적어 둠 | 본 사람 |
| 2 | 그 운영자에게 전화 등 **다른 길로** 직접 확인 | 본 사람 |
| 3 | 본인이 아니면 대표(SUPER)에게 바로 알림 | 본 사람 |
| 4 | 그 계정 비밀번호를 바꾸고 「모든 기기에서 로그아웃」 — 운영 화면 › 권한 계층 › 내 2단계 인증(v10.203 · 운영 역할 모두 · 지금 비밀번호 필요) | 그 운영자 |
| 5 | 그래도 의심되면 SUPER 가 회원 상세 「상태 변경」 → 정지(사유 필수 · 정지된 계정은 로그인이 막힘) 또는 권한 관리에서 역할 회수 | SUPER |
| 6 | 그 계정이 바꾼 것을 확인: 운영 알림 「중요 설정 바뀜」(by) · 위험감지 › 감사 › 기록 보기 | SUPER |
| 7 | 2단계 인증이 꺼져 있으면 켜는 것을 검토(5-9) | 대표 |
| 8 | 알림 「확인」(메모에 한 일) | SUPER |

- 정지 · 역할 회수는 **다음 요청부터 바로** 적용됩니다(서버가 요청마다 계정 상태와 역할을 다시 읽음 — 정지된 계정은 비로그인으로 봄).

### 8-2. 「주문 받기」가 잘못 켜짐

| 순서 | 할 일 |
|---|---|
| 1 | **먼저 끕니다.** 대시보드 「주문 받기 끄기」(ADMIN 도 됨) → 빨간 띠가 사라졌는지 확인 |
| 2 | 대시보드 「시험 결제 주문」 칸 숫자 확인 |
| 3 | 0 보다 크면 SUPER 가 「시험 결제 주문 정리(발송 전 취소 · 알림)」 — 발송 전 주문을 취소하고 주문한 분께 알림(돈은 받지 않았으므로 환불 없음) |
| 4 | 이미 발송 처리한 주문이 있으면 소개몰 주문 화면에서 하나씩 확인하고 대표에게 보고(정리 단추는 발송 전 주문만 취소) |
| 5 | 운영 알림 「중요 설정 바뀜」에서 누가 · 어디서(APP / DB) · 사유 확인 → 대표 보고 |
| 6 | 관련 알림(`SETTING_CHANGED` · `ORDER_OPEN_NO_END` · `STUB_PAYMENT_ORDER`) 「확인」 |

### 8-3. 이상 거래 · 위험감지

1. 위험감지 › 위험감지에서 경보의 근거 · 규칙 원문 · 오탐 가능성을 봅니다.
2. 실제 문제면: 해당 매물 · 글을 감추거나(글 검수 · 표본 감사 「부적정」) 회원을 「상태 변경」 → 정지(사유 필수).
3. 거래가 걸려 있으면 거래 모니터링 → 분쟁 처리로(분쟁이 걸리면 정산 보류).
4. 처리 뒤 경보 「조치 완료」, 잘못 잡은 것이면 「오탐」(오탐을 따로 세야 규칙을 고칠 수 있음).
5. 「탐지 질의가 깨진 규칙」이 보이면 개발에 보고합니다.
6. 돈이 걸린 이상(정산 정합성 · 청구 금액 불일치 알림)은 정산 승인 · 지급을 멈추고 대표 · 개발에 보고합니다.

### 8-4. 개인정보 권리 요청 (열람 · 정정 · 삭제 · 처리정지)

| 순서 | 할 일 |
|---|---|
| 1 | 위험감지 › 권리 요청 「처리 중」에서 기한 가까운 것부터. 기한은 접수일 + `privacy.request_due_days`(기본 10일) |
| 2 | **본인 확인**(회원 상세에서 계정 확인) |
| 3 | 요청대로 처리(정정 · 삭제 등은 해당 화면에서) |
| 4 | 결과를 5자 이상 적고 「처리 완료」 — 회원에게 그대로 알림. 끝난 요청은 고칠 수 없음 |
| 5 | 거절할 때는 사유를 적고 「거절」 |
| 6 | 기한 안에 못 하면 사유를 적고 「기한 연장」(한 번만) |

### 8-5. 서버 오류 급증

| 순서 | 할 일 |
|---|---|
| 1 | 대시보드 「서버 오류(1시간)」 칸 → 위험감지 › 서버 오류 |
| 2 | 「많이 난 곳」 주소 · 시각 · 건수를 적음(요청 내용 · 개인정보는 남지 않음) |
| 3 | 사용자 웹에서 그 기능을 한 번 해 보고 되는지 확인 |
| 4 | 개발 · 서버 담당에 보고. 운영 서버 조치(재시작 · 되돌리기)는 **대표 승인 뒤 서버 담당(ubuntu)이** 합니다 |
| 5 | 디스크가 같이 높으면 `DISK_LOW` 처리를 먼저 |
| 6 | 원인이 해결되면 `SERVER_ERROR_SPIKE` 「확인」 |

- 서버 오류 목록은 API 를 다시 띄우면 지워집니다. 적어 두고 보고합니다.

### 8-6. 가입 급증 · 자동 가입

1. 회원 화면에서 최근 가입 모양을 봅니다.
2. 이상하면 대시보드 「가입 잠시 막기」(기존 회원 로그인은 그대로).
3. 필요하면 「안내 띠 올리기」로 사용자에게 알립니다.
4. 대표에게 보고하고, 풀 때는 「가입 다시 받기」.

## 부록. 화면에 오류 코드가 떴을 때

> 운영 화면에서 단추를 눌렀는데 아래 코드가 섞인 글이 나오면, 고장이 아니라 **서버가 일부러 막은 것**입니다.

| 코드 | 뜻 | 할 일 |
|---|---|---|
| `ORDER_SETTING_SUPER` | 주문 받기 켜기는 SUPER 만 | SUPER 에게 요청(결제대행사 연결 전이면 켜지 않는 것이 원칙) |
| `ORDER_OPEN_CONFIRM` | 확인 문구가 다름 | 「시험 결제 주문을 받습니다」를 그대로 입력 |
| `ORDER_OPEN_REASON` | 사유가 10자 미만 | 사유를 10자 이상 |
| `ORDER_OPEN_HOURS` | 꺼질 시각이 1 · 2 · 4 · 8 · 24시간 밖 | 목록에서 고름 |
| `ORDER_UNTIL_AUTO` | 꺼질 시각을 직접 고치려 함 | 「주문 받기 켜기」에서만 고름 |
| `TENANT_SETTING_SUPER` | 입점 신청 켜기는 SUPER 만 | SUPER 에게 요청 |
| `TENANT_TERMS_FIRST` | 입점 약관이 아직 시행 중이 아님 | 7절 순서로 입점 약관부터 게시 |
| `AI_SETTING_SUPER` | AI 설정은 SUPER 만 | SUPER 에게 요청 |
| `SWITCH_PREREQ` | 스위치를 바꿀 조건이 아직 안 됨(연동 상태 · 키 · 월 상한 · 수금 계좌) | 글에 적힌 조건을 먼저 갖춤 |
| `PRIVACY_FIRST` | AI 고지가 든 처리방침이 게시 전 | 처리방침 게시(7절) 뒤 |
| `MODEL_UNPRICED` | 요금표에 없는 AI 모델 | 「모델 요금표」에 먼저 넣음(SUPER) |
| `ETAX_CONFIG_FIRST` · `ETAX_TEST_FIRST` | 세금계산서 업체 설정 · 7일 안 시험 성공이 없음 | 외부 연동에서 키 확인 · 시험 발행 뒤 |
| `MAIL_CONFIG_FIRST` · `MAIL_TEST_FIRST` | 메일 설정 · 7일 안 시험 메일 성공이 없음 | 외부 연동 › 메일 준비 뒤 |
| `MFA_SETTING_SUPER` · `MFA_ENROLL_FIRST` | 2단계 인증 설정은 SUPER 만 · 켜는 사람이 먼저 등록 | 「내 2단계 인증」 등록 뒤 |
| `TERMS_SETTING_SUPER` | 약관 설정은 SUPER 만 | SUPER 에게 요청 |
| `TERM_HOLES` | 본문에 〔미확정〕이 남음 | 채운 뒤 게시 |
| `TERM_ADVERSE_30D` | 불리한 변경인데 시행일이 30일 안 | 시행일을 30일 뒤 이후로 |
| `TERM_SCHEDULED_EXISTS` | 시행 예정 판이 이미 있음 | 그 판 「예정 취소」 뒤 |
| `TERM_HAS_CONSENT` | 이미 동의 기록이 있어 예정 취소 불가 | 새 판으로 |
| `SETTING_FORMAT` | 값 형식이 틀림 | 글에 적힌 예처럼 |
| `SELF_GRANT` | 자기 권한을 바꾸려 함 | 다른 SUPER 에게 요청 |
| `MAIL_TEST_WAIT` · `PUSH_TEST_WAIT` | 시험은 1분에 한 번 | 1분 뒤 다시 |
