## 0. 결론

- **고침**: 묶음 6 목록에 「BANK · SAFENUM · ESIGN · BROKER STUB」이라고 적었던 것은 틀렸습니다. 연동 표 기준으로 **실제 구현이 없는(STUB) 4건은 PASS(본인인증) · ALIMTALK(알림톡 · SMS) · SAFENUM(050 안심번호) · ESIGN(전자계약)**입니다. BANK(1원 계좌인증) · BROKER(국토부 중개사 대조) · PG · ETAX 는 REAL(호출 코드 있음 · 키 · 계약만 남음)입니다.
- 네 건 모두 **「업체 공통 HTTP 틀」은 이미 있습니다** — 주소 · 인증 머리글 · 결과 칸 위치를 .env 로 맞추는 방식이라, 업체를 정하면 업체 안내서대로 칸 이름만 채우고 시험합니다(새로 짜는 코드는 업체 형식이 틀과 다를 때만).
- **먼저 할 순서(추천)**: ① 알림톡 ② 본인인증 ③ 전자계약 ④ 050 안심번호.
  1. 알림톡이 없으면 인증번호를 못 보내 **소개리드 · 상담 신청이 막혀 있습니다**(사용자 웹 「인증번호 전달 메시지를 준비하고 있습니다」).
  2. 본인인증은 **소개비 켜기(feature.referral_fee)의 조건**(PASS · BANK 모두 LIVE)입니다.
  3. 전자계약 · 050 은 없어도 서비스가 돌고(수기 계약 · 실제 번호), 오픈 뒤 붙여도 됩니다.

## 3. 업체가 정해진 뒤 순서 (네 건 같음)

1. 신청 진행표에 「신청」 날짜 → 계약 · 키를 받으면 「키」 날짜.
2. 운영 화면 › 외부 연동 › **연동 키**에 키를 넣음(암호화 저장 · 값은 다시 보이지 않음).
3. Claude 에게 업체 안내서(API 문서) 전달 → `.env` 칸 이름(주소 · 인증 머리글 · 결과 칸 위치) 맞춤 · 틀과 다르면 그 부분만 개발(판 하나).
4. 점검판에서 시험 → 운영 반영(묶음) → 운영 화면 「연동 시험」 → 상태 TESTING → LIVE.
5. 처리방침 위탁 목록 갱신(법무 확인) — 알림톡 · 050 · 전자계약은 새 위탁처.
