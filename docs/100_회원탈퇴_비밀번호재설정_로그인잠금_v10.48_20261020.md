## 1. 정한 규칙

| # | 항목 | 값 | 바꾸는 곳 |
|---|---|---|---|
| 1 | 로그인 잠금 | 같은 이메일 **5회 연속 실패 → 30분 잠금**(423 `ACCOUNT_LOCKED`) · 성공하면 0 부터 | `auth.login.max_fail` · `auth.login.lock_minutes` |
| 2 | 잠금 풀림 | 30분 지나면 저절로 · 비밀번호 재설정 · 운영 화면 › 회원 상세 「잠금 풀기」 | — |
| 3 | IP 요청 제한 | 같은 IP 의 **실패한** 로그인 1분 5회 → 그 IP 1분 막음(429 `TOO_MANY_ATTEMPTS`) | `auth.login.ip_fail_per_min` |
| 4 | 재설정 메일 요청 제한 | 같은 이메일 · 같은 IP 각각 **1시간 5회**(429 `TOO_MANY_REQUESTS`) | `auth.reset.per_hour` |
| 5 | 재설정 링크 | 가입 메일로 · **30분 · 1회** · 새로 요청하면 전 링크 무효 | `auth.reset.ttl_minutes`(최대 60) |
| 6 | 비밀번호 바꾼 뒤 | 그 전에 발급한 로그인 증표 **모두 무효**(다른 기기 로그아웃) · 바꾼 기기는 새 증표로 이어 감 | — |
| 7 | 탈퇴를 막는 일 | 진행 중인 거래 · 분쟁 · 정산(요청 · 승인 · 보류) · 소개몰 주문 · 취소 · 반품 · 구독 환불 · 리드캐시 유상 잔액 · 리드캐시 환불 | 약관 제13조 ② |
| 8 | 탈퇴 처리 | 비밀번호 확인 + 사유 6종 → 매물 · 요청 내림 · 소개코드 정지 · 유료 구독 자동 결제 멈춤 · 결제 수단 해제 · 로그인 끊김 | — |
| 9 | 탈퇴 뒤 개인정보 | **기존 규칙 그대로** — 거래 기록이 있으면 5년 뒤, 없으면 다음 파기 배치(새벽)에서 이메일 · 이름 · 연락처 파기 | `fn_set_retention_on_withdraw` · `fn_purge_accounts` |

계획과 달라진 점

- IP 제한은 **실패한 로그인만** 셉니다. 계획에서는 「로그인 요청 1분 5회」였습니다. 성공까지 세면 사무실처럼 IP 하나를 여럿이 쓰는 곳과 자동 검정이 막힙니다.
- 계획에서는 「거래 기록이 없으면 30일 뒤 파기」라고 했습니다. 실제로는 기존 규칙이 **바로(다음 파기 배치)** 파기합니다. 개인정보를 더 빨리 지우는 쪽이라 기존 규칙을 따릅니다.

## 2. 구조

```
사용자 웹(서버 액션 · 접속자 IP 를 X-Forwarded-For 로 넘김)
  /login            로그인 ─────────────▶ POST /auth/login           fn_login_gate → bcrypt → fn_login_fail | fn_login_clear
  /login/forgot     비밀번호 찾기 ───────▶ POST /auth/password/forgot  fn_reset_request_allowed → fn_password_reset_issue → 메일(SES)
  /login/reset      재설정 ─────────────▶ POST /auth/password/reset   fn_password_reset_consume → 비밀번호 · token_version+1 · fn_login_clear
  /my/account       비밀번호 변경 ───────▶ PATCH /me/password          지금 비밀번호 확인(실패로 셈) → token_version+1 → 새 증표
  /my/account/withdraw 회원 탈퇴 ────────▶ GET /me/withdraw/check · POST /me/withdraw → fn_withdraw_blockers · fn_account_withdraw
운영 화면
  회원 상세 › 로그인 잠금 ─────────────▶ GET · DELETE /admin/accounts/:id/login-lock (감사 LOGIN_UNLOCK)
```

- 로그인 증표(JWT)에 판 번호 `tv` 를 넣습니다. 요청마다 `accounts.token_version` 과 비교하고, 다르면 비로그인으로 봅니다. refresh 는 거절합니다. 판 번호가 없는 옛 증표는 0 으로 봅니다(배포해도 로그인이 풀리지 않음).
- 이메일 · IP 원문은 저장하지 않습니다.
  - 이메일 키: sha256(소문자 · 앞뒤 공백 제거)
  - IP 키: HMAC-SHA256(서버 비밀 · 한국 날짜 · IP)
- **계정이 없는 이메일도 똑같이 세고 똑같이 답합니다.** 잠금이나 「메일을 보냈습니다」 안내로 가입 여부를 알아낼 수 없게 하기 위해서입니다.

## 3. DB (D102)

| 대상 | 내용 |
|---|---|
| `accounts.token_version` · `password_changed_at` | 증표 판 번호 · 마지막 비밀번호 변경 |
| `auth_throttle` | 로그인 실패 · 재설정 요청 횟수. 키는 64자 hex 만 받음. 잠금은 LOGIN_EMAIL 만 · 3시간 상한(CHECK) |
| `password_reset_tokens` | 증표 해시만 저장. 유효 1시간 상한(CHECK) · used_at / revoked_at |
| `account_withdrawals` | 탈퇴 사유(6종) · 메모(500자 · 「기타」면 필수) · 거래 기록 여부 |
| 함수 | `fn_login_gate` · `fn_login_fail` · `fn_login_clear` · `fn_reset_request_allowed` · `fn_password_reset_issue` · `fn_password_reset_consume` · `fn_withdraw_blockers` · `fn_account_withdraw` · `fn_purge_auth_records` |
| 트리거 | `trg_account_withdraw_guard` — 막는 일이 남았으면 `withdrawn_at` 을 찍는 **모든 경로**를 막음 |
| 설정 | `auth.login.max_fail` 5 · `auth.login.lock_minutes` 30 · `auth.login.ip_fail_per_min` 5 · `auth.reset.per_hour` 5 · `auth.reset.ttl_minutes` 30 |
| 알림 종류 | `PASSWORD_CHANGED` · `LOGIN_LOCKED` (수신거부 불가) |
| 감시 보기(0 이어야 정상) | `v_auth_lock_overlong` · `v_reset_token_live_overdue` · `v_withdrawn_with_open_items` |
| 배치 | 기존 `pii_purge` 가 `fn_purge_auth_records()` 도 부름 — 7일 지난 증표 · 2일 지난 실패 기록 삭제 |

## 7. 운영 적용 때

- 마이그레이션 D102 하나뿐입니다. `.env` 에 넣을 것은 없습니다. 메일은 기존 SES 설정을 씁니다.
- 적용 직후 로그인이 풀리지 않습니다(판 번호 0).
- 적용 순서는 다른 판과 같습니다(precheck → RDS 스냅샷 → apply → postcheck · 단계마다 나눔). D099 ~ D101(v10.46 · v10.47)과 함께 올리면 마이그레이션 4개입니다.
