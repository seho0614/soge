# 647. 감사 · 접속 기록 장기 보관 (v10.509 · D275 · 2026-11-20)

> 대표 11/20 「㊺ 기록 · 안전 · 운영」 ① · 같은 날 대표 결정 **「감사 · 접속기록은 3년 보관」**.
> 화면: 운영 화면 **위험감지 › 「기록 장기 보관」**(SB-ADM-OPX-010 · SUPER 만).

## 1. 결론

1. 감사 기록 · 개인정보 접속기록(열람 사유 포함) · 운영 알림 · 설정 바뀐 기록 · 운영자 로그인을 **달마다 한 묶음**(gzip JSON 줄)으로 만들어 **3년(36개월)** 보관합니다.
2. 묶음마다 **sha256 지문**, 묶음 목록마다 **목록 지문**(앞 묶음 목록 지문 + D235 감사 사슬 머리 순번 · 지문 + 이 묶음 값)을 남기고, 같은 거래에서 감사 기록 `OPX_ARCHIVE_BUNDLE` 한 줄을 써서 **목록이 감사 사슬 안에 묶입니다**.
3. **처음 꺼짐**(`opx.archive = off`). 켜면 매일 04:20 지난 달까지 묶습니다(한 번 6개).
4. S3 버킷은 아직 없으므로 **서버 디스크**(`DATA_DIR/backup/log-archive` — 앱 폴더 밖 · 올린 파일 백업 폴더 옆)에만 둡니다. 화면에 **「디스크 밖 보관 아님」** 경고가 뜹니다. 버킷을 만들고 `opx.archive_s3 = on` 이면 묶음을 S3 에 올립니다(디스크 사본도 남김).
5. 36개월이 지난 묶음은 정기 작업이 **파기 기록(파일 · sha256 · 줄 수 · 목록 지문) · 감사 한 줄 `OPX_ARCHIVE_DISPOSE`** 를 먼저 남기고 파일(· S3 사본)을 지웁니다. 목록 줄은 남습니다.
6. 운영 DB 의 원래 줄은 **처음 「지우지 않음」**(`opx.archive_db_purge_months = 0`). 13 ~ 120 으로 바꾸면 그 개월이 지난 달 중 **묶음 · 복원 확인이 끝나고 DB 줄 수가 묶음과 같은 달만** 지웁니다(확인 전 · 확인 실패 · 줄 수 다름이면 DB 함수가 막음).

## 2. 보관 기간 — 일반 원칙 · 법무 확인 표시

| 설정 | 처음 | 범위 | 근거 |
|---|---|---|---|
| `opx.archive_keep_months` | **36** | 12 ~ 120 | 대표 11/20 「3년」 · 기존 `audit.retention_days` 1095일과 같음 |
| 최소 12 | — | 서버 정규식 `KEEP_MONTHS_RE` = DB 설정 무늬(같음) | 개인정보의 안전성 확보조치 기준 제8조 — 접속기록 **1년 이상**, 이용자 5만 명 이상 · 고유식별정보 · 민감정보 처리 등이면 **2년 이상**(일반 원칙 · **법무 확인 필요**) |
| `opx.archive_db_purge_months` | **0(지우지 않음)** | 0 · 13 ~ 120 | 대표 11/20 「원래 줄을 언제 지울지 별도 설정 · 처음 지우지 않음」 |

- 24개월보다 짧게 두면 화면에 2년 조건 경고가 뜹니다(막지는 않음 — 조건 해당 여부는 법무 확인).
- 법령 · 고시 값은 바뀔 수 있습니다 — 적용 전 최신 고시를 법무가 확인합니다.

## 3. 구조

| 구분 | 이름 | 내용 |
|---|---|---|
| 표 | `opx_archive_bundles` | 종류 · 달 · 줄 수 · 첫 · 끝 번호 · 파일 이름 · 크기 · sha256 · 감사 사슬 머리 · 앞 목록 지문 · 목록 지문 — **쌓기만** |
| 표 | `opx_archive_events` | S3_PUT · VERIFY(복원 확인) · DISPOSE(파기) · PURGE(DB 정리) — **쌓기만** |
| 함수 | `fn_opx_purge_month(묶음)` | 확인 끝난 달만 DB 원래 줄 정리 · 거래 설정 `app.opx_purge = 종류:YYYY-MM` 을 걸고 지움 |
| 함수 | `fn_block_audit_write` 고침 | 지우기는 `app.opx_purge = 'AUDIT:그 달'` + `fn_opx_purge_ok` 조건일 때만 허용(그 밖은 그대로 막음 · 고치기 규칙 그대로) |
| 함수 | `fn_opx_ro_or_purge` | 개인정보 접속기록 · 설정 바뀐 기록 — 고치기 막음 · 지우기는 정리 표시 달만 |
| 정기 작업 | `opx_archive` 매일 04:20 | 묶음 → S3 → 복원 확인 1개 → 파기 → DB 정리 |
| 알림 | `OPX_ARCHIVE_BAD`(긴급) · `OPX_ARCHIVE_FAIL` · `OPX_ARCHIVE_S3_FAIL` | 복원 확인 실패 · 묶음 실패 · S3 실패(하루 한 번) |

- 묶음에 **IP · User-Agent 는 넣지 않습니다**(1년 뒤 마스킹 규칙 · 사슬 본문과 같은 이유). 운영자 로그인은 원래 표처럼 가린 IP 만.
- 운영자 로그인(LOGIN)은 `privacy.login_history_days` 파기가 따로 있어 DB 정리 대상이 아닙니다.
- 감사 기록 정리는 사슬 확인 시작점(마지막 확인 지점)보다 오래된 달만 지우게 됩니다(13개월 이상) — 사슬 확인에 영향 없음.

### 3-1. 보안 검토 반영(2026-11-20 · B-1 ~ B-4 고침)

| # | 고친 것 |
|---|---|
| B-1 | 지우기 트리거(`fn_block_audit_write` · `fn_opx_ro_or_purge`)가 정리 표시(`app.opx_purge`) 글자만 믿지 않고 `fn_opx_purge_ok` 로 다시 봄 — 설정 13 이상 · 줄의 달(한국 달)이 기준보다 오래됨 · 그 종류 · 그 달 묶음에 복원 확인 성공 + S3 올림 성공 · 파기 · 정리 전. 아니면 원래 막는 오류. 고치기(UPDATE) 막기는 그대로 |
| B-2 | `fn_opx_purge_month` · 서버 `purgeDb` 모두 **S3 올림 성공(S3_PUT) 묶음만** 정리 — 디스크 밖 사본이 없으면 DB 줄을 지우지 않음 |
| B-3 | `fn_opx_purge_month` 안에서 개월 13 미만이면 설정과 상관없이 막음(서버도 13 미만이면 부르지 않음) |
| B-4 | 감사 기록 · 개인정보 접속기록 · 설정 바뀐 기록에 `BEFORE TRUNCATE … FOR EACH STATEMENT` 트리거(`fn_block_write`) — 통째 비우기 막음 |

## 4. 복원 확인

파일(없으면 S3)을 다시 읽어 ① sha256 · 크기 ② 압축 풀기 ③ 머리 줄(종류 · 달) ④ 줄 수 · 첫 · 끝 번호 ⑤ 목록 지문 다시 셈 ⑥ 앞 묶음 연결 ⑦ DB 줄이 남아 있으면 줄 수 · (감사) 끝 줄 사슬 지문을 대조합니다. 실패면 급한 알림. 정기 작업이 매일 가장 오래 확인하지 않은 묶음 하나를, DB 정리 직전에는 그 묶음을 한 번 더 확인합니다.
