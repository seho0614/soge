# 소개뱅크 — 연계 설계서 v1

**작성일** 2026-09-03
**범위** 내부 모듈·계층 간 연계. **외부 시스템은 `12_연동설계서`**

---

## 1. 연계 원칙

```
① 모듈 간 호출은 서비스 인터페이스로만. DB 테이블 직접 참조 금지
② 의존 방향은 한쪽. modules → engines → db → core
③ 상태 전이는 도메인 서비스 한 곳에서만
④ 트랜잭션 경계는 서비스가 연다. 리포지토리는 열지 않는다
⑤ 트리거가 하는 일을 앱이 다시 하지 않는다
```

**⑤가 이 시스템의 특징입니다.** 모듈 간 연계의 상당수가 코드가 아니라 **DB 트리거로** 일어납니다.

---

## 2. 모듈 의존도

```
identity ──┬─→ (전 모듈이 principal 을 씀)
           └─→ attribution.link()      로그인·가입 시 귀속 연결

catalog ───┬─→ listing    등급·업종·제한업종
           └─→ code       라벨 (전 모듈)

listing ───┬─→ review.enqueue()        등록 → 검수 큐
           └─→ exposure                목록 정렬

request ───→ review.enqueue()

deal ──────┬─→ attribution.resolve()   귀속 판정
           └─→ (settlement 은 트리거가 만듭니다)

review ────→ (대상 상태 전이는 같은 트랜잭션에서 직접)

worker ────→ DB 함수만 호출. 판정 로직 없음
```

**순환이 없습니다.** `deal` 이 `settlement` 을 부르지 않는 것이 중요합니다 — 정산은 트리거가 만듭니다.

---

## 3. 트리거로 일어나는 연계 18건

앱 코드에 없는 연계입니다. **모르면 "왜 이게 만들어졌지"가 됩니다.**

| # | 계기 | 결과 | 트리거 |
|---|---|---|---|
| 1 | `review_items` INSERT | 자동검수 판정 → 통과 시 `listings` PUBLISHED | `trg_auto_review` |
| 2 | `deal_contracts` INSERT | 합의 금액 LOCKED 고정 | `trg_contract_lock_fee` |
| 3 | 계약 **양측 서명** | 확인 2행 + `deals` CONFIRMED + **`settlements` 생성** | `trg_contract_auto_confirm` |
| 4 | `deals` → CONFIRMED | 귀속 first-touch 판정·스냅샷 | `trg_deal_attr_snapshot` |
| 5 | `disputes` INSERT | `settlements` → HELD | `trg_dispute_hold` |
| 6 | `subscriptions` → CANCELLED | 미성사 `referral_codes` 실효 | `trg_sub_revoke_codes` |
| 7 | `restricted_industries` INSERT(BLOCK) | 기존 매물 SUSPENDED + 안내 발송 | `trg_restriction_enforce` |
| 8 | `listings.version` 변경 | 부여된 배지 REVOKED | `trg_badge_revoke_on_edit` |
| 9 | `listing_badges` INSERT | 검수 큐 적재 (전건 수동) | `trg_badge_enqueue` |
| 10 | `review_items` → APPROVED (배지) | 배지 GRANTED + 노출 반영 | `trg_badge_decision` |
| 11 | `listings.is_priority_exposed` = true | 라벨 자동 부여 | `trg_priority_label` |
| 12 | `terms` → PUBLISHED | 같은 코드 이전 버전 ARCHIVED | `trg_archive_prior_terms` |
| 13 | `listings`·`requests` INSERT | **금칙어 BLOCK 검사** → 거부 | `trg_listing_banned_words` |
| 14 | `accounts.withdrawn_at` 설정 | 거래 이력에 따라 보관기간 계산 | `trg_account_withdraw` |
| 15 | `audit_logs` INSERT | **개인정보 키 자동 제거** | `trg_redact_audit` |
| 16 | `site_settings` UPDATE | 자리표시자·형식 검증 | `trg_validate_setting` |
| 17 | `gwans.is_active` → true | 업종·폼 문구 없으면 거부 | `trg_gwan_open` |
| 18 | `notifications` INSERT | 미치환 변수 발송 차단 | `trg_notification_vars` |

### 3번이 이 시스템의 핵심 연계입니다

```
POST /deals/{id}/contract/sign  (두 번째 서명)
  └─ trg_contract_auto_confirm
       ├─ deal_confirmations ×2 (source=CONTRACT)
       ├─ deals → CONFIRMED
       │    └─ trg_deal_attr_snapshot → 귀속 판정·스냅샷
       ├─ settlements INSERT
       │    └─ trg_settlement_rules → INV-3·9·10 검사
       └─ 개인이면 notifications (사업자 전환 안내)
```

**API 하나가 5개 테이블을 바꿉니다.** 앱 코드에는 서명 UPDATE 한 줄뿐입니다.

## 4. 계층 간 계약

### 4-1. 컨트롤러 → 서비스

```ts
create(@Body() dto) {
  return this.service.submit({ ...dto, ownerAccountId: RequestCtx.actorId()! });
}
```

**컨트롤러가 하는 일** — DTO 바인딩 · actor 주입 · 데코레이터 5종.
**하지 않는 일** — 상태 판단 · 쿼리 · 트랜잭션.

### 4-2. 서비스 → 리포지토리

```ts
return this.db.transaction(async () => {
  const id = await this.repo.insert(...);      // tx 인자 없음
  await this.reviews.enqueue({ targetId: id }); // 다른 모듈도 같은 트랜잭션
});
```

**리포지토리는 트랜잭션을 열지 않습니다.** `RequestCtx` 가 커넥션을 전달하므로 **다른 모듈의 리포지토리도 같은 트랜잭션에 들어옵니다.**

### 4-3. 서비스 → 엔진

```ts
const res = await this.attribution.resolve(accountId, at);
```

엔진은 **판정만** 하고 상태를 바꾸지 않습니다. 예외는 `record`/`link` 로, 이건 append 입니다.

### 4-4. 워커 → DB

```ts
const [r] = await this.db.query(`SELECT fn_check_k_alert()`);
```

**워커에 판정 로직이 없습니다.** DB 함수를 부르기만 하므로 워커가 죽어도 규칙은 그대로입니다.

## 5. 데이터 흐름 — 소개비

INV-9·11 때문에 **두 흐름이 물리적으로 분리**돼 있습니다.

```
소개비 흐름 (플랫폼 밖)
  fee_agreements → deals.agreed_fee → settlements.amount
  └ 공제 컬럼 없음 · 금액 이동 컬럼 없음

플랫폼 매출 (플랫폼 안)
  payment_transactions → ledger_entries
  └ entry_type 에 REFERRAL_FEE 없음
```

**두 흐름을 잇는 코드가 없습니다.** `deal` 모듈과 `ledger` 가 서로를 모릅니다. 이게 INV-9를 구조로 지키는 방법입니다.

## 6. 알림 연계

```
도메인 이벤트 → notifications INSERT → q-notify → 채널별 발송
                                              └ notification_deliveries (멱등키)
```

| 규칙 | 내용 |
|---|---|
| 수신거부 | `notification_event_policies` 가 판정. **불가 이벤트를 끄면 DB가 거부** |
| 조용한 시간 | 21:00~08:00 SMS·PUSH 안 함. 인앱·메일은 제한 없음 |
| 중복 | 같은 event_code + 대상 10분 내 1회 |
| 실패 | 인앱 폴백. **알림 실패로 본 처리를 롤백하지 않습니다** |

## 7. 프런트 ↔ 백엔드 계약

| 항목 | 서버가 내려줌 | 프런트가 하지 않음 |
|---|---|---|
| 상태 라벨 | `status` + `statusLabel` | 문구 하드코딩 |
| 권한 판정 | `canInquire` + `inquireBlockReason` | 역할·게이트 재계산 |
| 목록 | `promoted` / `organic` **분리** | 합쳐서 렌더 |
| 링크 | `available` + `tip` | 목적지 없는 링크 숨김 |
| 스텁 | `stub: true` | 실동작처럼 표시 |
| 코드 번들 | `GET /codes` 1회 | 화면마다 조회 |

**"프런트가 하지 않음"이 계약의 본체입니다.** 프런트가 재계산하면 규칙이 두 곳에 생깁니다.

---

## 8. 연계가 끊어지는 지점

| 지점 | 증상 | 관측 |
|---|---|---|
| `attribution.link()` 미호출 | 비로그인 유입 유실 | `v_attribution_health` |
| 컨트롤러 미배선 | 라우트 0건 | `smoke-boot.ts` |
| `@Audit` 누락 | 감사 기록 없음 | `[AUDIT_WRITE_FAILED]` 로그 |
| `tx` 밖 쿼리 | 부분 커밋 | 잔액 불일치 (사후 발견) |
| 트리거 비활성 이관 | 무결성 붕괴 | `fn_verify_invariants()` |

**위 두 개는 에러가 나지 않습니다.** 정상 동작하면서 조용히 새기 때문에 관측 지표가 유일한 탐지 수단입니다.
