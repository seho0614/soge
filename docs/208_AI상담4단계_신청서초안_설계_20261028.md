## 0. 먼저 짚을 것 — 결정 기록과 맞지 않는 부분

| 기록 | 내용 | 지금 |
|---|---|---|
| ai-agent #2(10/4) · docs/149 5절 | 4단계 「신청서 초안」은 **알림톡 연동 뒤** | 알림톡은 **NOT_STARTED**(open-blockers #1) — 기록대로면 지금 만들 수 없음 |
| 같은 곳 | 알림톡이 왜 먼저인지 | **이유가 남아 있지 않음** |

이 설계(가안)는 알림톡이 없어도 됩니다. 회원이 **사이트 화면에서 직접 제출**하고, 제출 뒤 알림은 지금 쓰는 사이트 알림(`notifications`)과 메일(구축 뒤)로 보내기 때문입니다.
**알림톡을 기다리지 않고 만들되 꺼진 채로 둘지는 대표님이 정하실 일입니다**(4절 ①).

## 1. 결론 (추천)

| 항목 | 추천 |
|---|---|
| 하는 일 | 로그인 회원이 AI 상담에서 「반품하고 싶어요」 · 「배송이 안 와서 문의하고 싶어요」라고 하면, AI 가 **신청서 초안**을 만들어 대화창에 카드로 보여 줌 → 회원이 「신청서 열기」를 누르면 **지금 쓰는 신청 화면**이 초안으로 채워져 열림 → **회원이 그 화면에서 직접 제출** |
| 처음 범위 | **2가지** — ① 1:1 문의(`/support/new`) ② 건강몰 취소 · 반품 · 교환(`/my/health/returns/new`) |
| 빼는 것 | 분쟁 접수 · 신고 · 매물 · 요청 등록 · 구독 해지 · 정산 이의 — 법적 무게가 크거나 단계가 길어 사람 화면 그대로 |
| AI 가 못 하는 것 | **접수 · 취소 · 신청을 하지 않음** — AI 쪽에서 신청 API 를 부르는 길 자체가 없음(초안 저장만). 「회원 확인 없이 접수 0」(docs/149 5절)을 구조로 지킴 |
| 스위치 | 새 스위치 `agent.chat.drafts.enabled` **꺼짐** · 3단계 「내 정보 조회」가 켜져 있어야 함(주문을 찾아야 하므로) |

## 2. 방식 비교

| | 가. 초안 → 신청 화면에서 제출 (**추천**) | 나. 대화창 카드에서 바로 접수 | 다. 지금은 만들지 않음 |
|---|---|---|---|
| 회원 동작 | 카드 → 「신청서 열기」 → 화면 확인 → 「신청」 | 카드 → 「이대로 접수」 한 번 | — |
| 법정 안내(청약철회 7일 · 개봉 식품 등) | 신청 화면에 있는 그대로 봄 | 카드에 다시 넣어야 함 · 빠질 위험 | — |
| 입력 검사 · 판정(fn_hlt_return_judge) | 지금 화면 · API 그대로 | 같은 API 지만 화면 확인 단계가 없음 | — |
| 잘못 만든 초안 | 회원이 화면에서 고침 | 접수된 뒤 취소해야 함 | — |
| 개발 크기 | 중간 | 중간 | 없음 |
| 기록(#2 · docs/149) | 알림톡 조건만 대표 결정 필요 | 같음 + 「확인」이 약함 | 그대로 |

## 3. 세부 (가안)

### 3-1. 도구 2개 (AI 에게 주는 것)

| 도구 | 입력(AI 가 채움) | 서버가 하는 것 | AI 에게 돌려주는 것 |
|---|---|---|---|
| `draft_inquiry` | category(정해진 목록) · title(60자) · body(2,000자) | 연락처 · 계좌 가림(redactChat) · 초안 저장 | 초안 번호 · 화면 링크 |
| `draft_return` | orderTail(주문번호 끝 4자리) · kind(CANCEL · RETURN · EXCHANGE) · reason(사유 코드 목록) · detail(500자) | **회원 본인 주문에서** 끝 4자리로 찾음 — 없거나 둘 이상이면 초안을 만들지 않고 「주문을 골라 주세요」 · 사유 · 종류는 목록 밖이면 거절 · 판정은 하지 않음(제출 때 지금처럼) | 초안 번호 · 화면 링크 · 「제출은 회원이 화면에서」 |

- 회원 번호 칸은 **없음**(3단계와 같이 서버가 로그인한 사람으로 넣음).
- **전체 주문번호는 AI 에게 보내지 않음** — 끝 4자리로 서버가 찾고, 초안에는 서버가 주문 id 를 넣음.
- 한 질문에 초안 1개까지 · 도구 왕복 한도(2번)는 3단계 것을 함께 씀.

### 3-2. 저장 (마이그레이션 1개 · D135 예정)

```sql
CREATE TABLE public.agent_drafts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id uuid   NOT NULL REFERENCES agent_conversations(id) ON DELETE CASCADE,
  account_id      uuid   NOT NULL,
  kind            text   NOT NULL CHECK (kind IN ('INQUIRY','HLT_RETURN')),
  fields          jsonb  NOT NULL,          -- 화면에 채울 값(가린 뒤) · 주문은 id 로
  created_at      timestamptz NOT NULL DEFAULT now(),
  opened_at       timestamptz,              -- 회원이 「신청서 열기」
  submitted_at    timestamptz,              -- 그 초안으로 실제 제출됨
  submitted_ref   text,                     -- 접수 번호(문의 id · 반품 id)
  expires_at      timestamptz NOT NULL DEFAULT now() + interval '7 days'
);
-- 스위치 agent.chat.drafts.enabled 'off' 한 줄
```

- 초안은 **7일 뒤 지움**(배치 `agent_chat_purge` 에 한 줄). 제출된 신청서 자체는 지금 표(inquiries · hlt_returns)에 지금 규칙대로 남음.
- 대화를 지우면 초안도 함께 지워짐(5년 보관 규칙 그대로).

### 3-3. 화면

| 곳 | 바뀌는 것 |
|---|---|
| 사용자 웹 AI 상담 창(`AiChat.tsx`) | 초안 카드 — 종류 · 채운 값 요약 · 「신청서 열기」 · 「AI 가 만든 초안입니다. 제출 전에 꼭 확인해 주세요」 |
| `/support/new?draft=…` · `/my/health/returns/new?o=…&draft=…` | 초안 값으로 칸을 채움(본인 초안만 · 만료 · 남의 것이면 빈 화면) · 맨 위 「AI 초안으로 채웠습니다」 · **제출 단추는 지금 그대로** |
| 신청 API(`POST /inquiries` · `POST /me/health/returns`) | 선택 칸 `agentDraftId` — 있으면 본인 초안인지 보고 `submitted_at` 만 적음(신청 판정 · 검사는 그대로) |
| 운영 화면 › AI 에이전트 | 스위치 줄 「AI 상담 — 신청서 초안」(SUPER · 켜기 전 확인 문장) · 상담 기록에 「초안」 줄 · 「답 · 넘김 비율」 옆에 초안 수 · 열어 본 수 · 제출 수 |

### 3-4. 처리방침

AI 에게 새로 보내는 정보는 **없습니다** — 회원이 대화에 쓴 글(2단계에서 이미 보냄)과 주문 끝 4자리(3단계 ④ 줄)뿐입니다. 그래서 처리방침을 고치지 않아도 된다고 봅니다. 다만 **법무 확인이 필요합니다**(「AI 가 신청서 초안을 만든다」를 고지에 넣을지).

### 3-5. 시험(개발 때)

| 확인 | 맞으면 |
|---|---|
| 스위치 꺼짐 · 3단계 꺼짐 · 비회원 | 도구를 주지 않음 · 초안 0 |
| `draft_return` 끝 4자리가 남의 주문 · 없음 · 둘 이상 | 초안 안 만듦 |
| 목록 밖 사유 · 종류 · 긴 글 | 거절 · 잘라냄 |
| 남의 초안 번호로 화면 열기 · 만료 초안 | 빈 화면 |
| AI 대화만으로 접수 | **0건**(inquiries · hlt_returns 줄 수 그대로) |
| 초안 → 화면 → 제출 | 접수 1건 · `submitted_at` · 판정은 지금과 같음(발송 뒤 취소 422 등) |
| 7일 지난 초안 | 배치가 지움 |
