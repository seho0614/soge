## 4-2부 — K6 반영 (2026-09-25)

**사장님 결정**: 정지는 그대로, 탈퇴만 내립니다.

| 계정 상태 | 매물 | 이유 |
|---|---|---|
| **SUSPENDED** (정지) | **그대로** | 소명하면 돌아옵니다 |
| **WITHDRAWN** (탈퇴) | **ARCHIVED 로 내림** | 연락이 닿지 않습니다 |

### 반영 — `C980_withdraw_takedown`

| 항목 | 내용 |
|---|---|
| 트리거 | `trg_withdraw_takedown` — WITHDRAWN 으로 바뀔 때만 |
| 대상 | listings · requests 의 PUBLISHED · IN_REVIEW · DRAFT |
| 감시 | `v_withdrawn_still_public` (0이어야 정상) |
| 소급 | 적용 시 이미 탈퇴한 계정을 한 번 정리 |

### 왜 DB 에서 막았나

`status='PUBLISHED'` 로 거르는 곳이 **앱 소스에 22군데**입니다. 한 곳만 빠뜨려도 탈퇴자 매물이 계속 노출됩니다. 소유자가 탈퇴하는 순간 매물 상태를 바꾸면 22곳이 저절로 따라옵니다.

`SUSPENDED` 가 아니라 `ARCHIVED` 를 쓴 이유는 `SUSPENDED` 가 **운영자가 제재했다**는 뜻이기 때문입니다. 섞으면 통계와 이의제기 처리가 어긋납니다.

### 시험

```
계정을 정지 → 공개 매물 4건 그대로
계정을 탈퇴 → 공개 0건 · ARCHIVED 4건
v_withdrawn_still_public → 0건
```

### `v_restricted_unlinked` 는 시험이 남긴 것입니다

`verify-invariants.sh` 의 I-06 시험이 제한업종 `NEWR` 을 넣고 **지우지 않습니다.**

```
이관 직후    NEWR 0건 · 감시 0건   ← 배포본은 깨끗
불변식 후    NEWR 1건              ← 시험이 넣음
공격 검정 후  NEWR 0건              ← 공격이 지움
```

**배포본의 결함이 아닙니다.** 다만 시험 순서에 따라 보고가 달라지니, 판정하실 때는 **이관 직후**나 **공격 검정 후**를 기준으로 보십시오.

| 파는 것 | 게시물 | **소비자 문의 자체** |

개인정보는 만든 뒤에 거르면 이미 저장된 뒤라 INSERT 시점에 세웠습니다.

### ② 업종 8종 (`C993`)

| 업종 | 규제 |
|---|---|
| 의료 · 보험 · **카드** · **금융** · **통신사 대리점** | **GATED** |
| 이사짐 · 중고차 · 렌터카 | 일반 |

카드·금융·통신도 걸었습니다 — **모집인 등록 없이 유치하면 불법**이라 리드 전달도 같은 문제가 생깁니다.

**검정 두 곳이 우리 데이터를 지우고 있었습니다.** LED 가 빈 관이라는 전제로 쓰인 시험이 폼 문구를 삭제해, 검정을 돌릴 때마다 관을 못 여는 상태가 됐을 것입니다. 임시 관(ZZT)으로 시험하도록 고쳤습니다.

### ③ 개인정보 격리 (`C994` · `C996`)

배치 코드가 **없는 표를 지우고 있었습니다.**

```js
UPDATE pii.lead_contacts ... .catch(() => []);
```

`.catch` 로 조용히 넘어가, 리드를 받기 시작하면 **아무것도 파기되지 않습니다.**

| 만든 것 | 역할 |
|---|---|
| `pii.lead_contacts` | 암호화 보관 |
| 삭제 금지 | 행을 지우면 파기 기록이 사라짐 |
| 기한 연장 금지 | 늘리면 파기가 영원히 안 옴 |
| `fn_read_lead_contact` | 복호화 + 열람 기록 · 사유 필수 |

**열쇠 이름이 셋으로 갈려 있어** `fn_enc_key()` 하나로 모았습니다. `ENC_KEY` 를 DB 세션에 거는 고리도 비어 있어 이었습니다.

## 5부 — ★ 찾은 문제와 조치 (전부 해결)

**아래 셋은 모두 조치를 마쳤고, 깨끗한 DB에서 재측정해 확인했습니다.**

### ① 기준 데이터에 시험 흔적이 굳어 있었습니다

`B900_reference_data`가 당시 DB를 그대로 떠서 만들어져 검정 찌꺼기까지 정식 데이터가 됐습니다.

|---|---|---|
| `categories` | `TESTRSTR` 시험제한업종 · **APPROVED** | **삭제** |

`C960_baseline_cleanup`으로 지웠습니다. **B900 자체는 건드리지 않았습니다** — 고치면 `변경감지`에 걸립니다.

### ② ★ 가짜 계좌로 오픈 검정이 통과하고 있었습니다

```
company.bank_name    시험용가상은행
company.bank_account 999999-99-999999
company.bank_holder  주식회사 소개뱅크 시험용
```

`v_company_account`가 **빈 값만 보고** 있어 `missing = 0`, 즉 「정상」으로 나왔습니다. 이대로 열었다면 **입금 안내에 가짜 계좌번호가 나갔을 것입니다.**

설정은 `is_required_for_open = true`라 지울 수 없습니다. 대신 **뷰가 시험용 값을 잡도록** 고쳤습니다.

```
missing  0 → 3
```

계약 후 실제 계좌를 넣으면 저절로 0이 됩니다.

### ③ ★ 감시 뷰 2개가 목록에서 빠져 있었습니다

감시 뷰는 설명에 `0이어야`가 있는지로 찾는데, 두 개가 문구가 달라 **빠진 채 「이상 없음」으로 보고돼 왔습니다.**

| 뷰 | 옛 문구 | 지금 |
|---|---|---|
| `v_assumed_on` | "오픈 전 반드시 0" | **3건 검출** |
| `v_broker_gate_leak` | "관을 열기 전에 반드시 0 이어야" | 0건 (정상) |

`C961_watch_comment`로 문구를 표준화했습니다. **감시 뷰 70 → 66.**

`v_assumed_on` 3건은 **간주 모드**입니다.

| 설정 | 뜻 |
|---|---|
| `assume.payment` | 결제된 것으로 간주 — **실제 결제 안 일어남** |
| `assume.broker` | 중개사 인증 통과로 간주 — **국토부 대조 안 함** |

**셋 다 연동 후 off로 바꾸셔야 합니다.** 여태 감시에서 빠져 있어 드러나지 않았습니다.
