# 1부. 배포 절차

## 1-1. 환경 3개

| 환경 | 계정 | DB | 용도 |
|---|---|---|---|
| dev | 비운영 | 단일 AZ · 야간 중지 | 개발자 공용 |
| **stg** | 비운영 | 운영과 동일 구성 · 축소 | 인수검증 · 마이그레이션 리허설 |
| **prod** | 운영 | Multi-AZ · PITR 35일 | 실서비스 |

**개발자는 prod 에 상시 권한을 갖지 않습니다.** IAM Identity Center 승인형 임시 권한만 씁니다.

## 1-2. 배포 전 점검

```bash
DATABASE_URL=... ENVIRONMENT=prod npm run deploy:check
```

7항목을 봅니다. **하나라도 실패하면 배포하지 않습니다.**

| # | 항목 | 실패 시 |
|---|---|---|
| 1 | 타입 오류 · 생성 파일 최신 | `npm run docs` 후 커밋 |
| 2 | 마이그레이션 미적용 · 변조 | **변조는 절대 무시하지 마십시오** |
| 3 | **불변식 위반 0건** | **롤백 대상** |
| 4 | 코드 라벨 누락 | 화면에 영문이 나갑니다 |
| 5 | **오픈 차단 항목** | prod 에서만 차단 |
| 6 | 미확인 CRITICAL 경보 | 먼저 처리 |
| 7 | **부팅 · 라우트 · 중복** | 배선 확인 |

## 1-3. stg 배포

```
1. main 브랜치 CI 통과 확인
2. ENVIRONMENT=stg npm run deploy:check
3. 이미지 빌드 → ECR 푸시
4. npm run db:migrate
5. ECS 서비스 갱신 (롤링)
6. npm run smoke
7. 인수 시나리오 실행
```

## 1-4. prod 배포

**수동 승인 1클릭.** 자동 배포하지 않습니다.

```
1. stg 인수 통과 확인
2. ENVIRONMENT=prod npm run deploy:check   ← 7건 전부 통과
3. RDS 스냅샷 수동 생성                     ← 롤백의 유일한 근거
4. npm run db:migrate
   실패 시 → 중단. 이력이 남아 원인 제거 후 이어서 적용됩니다
5. 이미지 배포 (롤링 · 최소 2 태스크)
6. 헬스체크 통과 대기
7. SELECT * FROM fn_verify_invariants();
8. 15분 관찰 — ops_alerts · 에러율 · 응답시간
```

## 1-5. 롤백

| 상황 | 조치 |
|---|---|
| 코드 결함 | 이전 이미지로 ECS 롤백. **DB 는 건드리지 않습니다** |
| 마이그레이션 실패 | 원인 제거 후 재실행 (이력이 남아 있습니다) |
| **불변식 위반 발견** | **즉시 서비스 중단 → 스냅샷 복원** |
| 데이터 손상 | PITR 복원 |

**코드 롤백과 DB 롤백을 함께 하지 않습니다.** 2단계 배포를 지켰다면 구 코드가 새 스키마에서 돕니다.

# 2부. 오픈 준비 절차

> **오픈 당일 절차는  에 있습니다.**
> D-14 부터 D+30 까지의 체크리스트가 거기 있습니다.

## 2-1. 오픈 차단 18건 해소

```bash
psql "$DATABASE_URL" -c "SELECT kind, item, reason FROM v_open_blockers;"
```

### ① 약관 6종 발행 (법무 회신 후)

```bash
# 초안 저장 — 기존 버전을 덮지 않고 새 버전을 만듭니다
curl -X PUT $API/admin/terms/SERVICE -H "Authorization: Bearer $T" \
  -d '{"version":"1.1","title":"이용약관","body":"..."}'

# 발행 — 내용과 시행일이 없으면 DB 가 거부합니다
curl -X PATCH $API/admin/terms/SERVICE/publish -H "Authorization: Bearer $T" \
  -d '{"version":"1.1","effectiveFrom":"2026-11-01T00:00:00Z"}'
```

발행하면 **푸터 링크가 자동으로 활성화**되고 오픈 차단이 줄어듭니다.

### ② 푸터 법정고지 입력

```bash
BIZ_REG_NO=123-45-67890 \
MAIL_ORDER_NO=제2027-서울강남-01234호 \
ADDRESS="서울특별시 강남구 …" \
PHONE=02-1234-5678 \
HOSTING="Amazon Web Services" \
CEO_NAME=홍길동 \
PRIVACY_OFFICER=김보안 \
npm run open:seed
```

**값이 없으면 실행되지 않습니다.** 자리표시자("대표자명")를 넣으면 DB가 거부합니다.

### ③ 외부 연동

관리자 화면 → 외부 연동 탭에서 **발신 IP 를 한 번 넣으면 6종에 일괄 반영**됩니다.

```
NAT EIP 고정 → IP 등록 신청 → 심사 2~4주 → 상태를 LIVE 로 변경
```

**키 값은 Secrets Manager 에 넣고 화면에서는 "등록 완료"만 체크**하십시오. DB에 키를 넣으면 백업·복제본에 전부 퍼집니다.

## 2-2. 대량 이관 (필요 시)

```
1. 트리거 비활성화
2. 벌크 적재
3. SELECT * FROM fn_verify_invariants();
4. 위반 0건 확인          ← 하나라도 걸리면 롤백
5. 트리거 재활성화
6. 재실행 확인
```

**리허설 없이 본이관하지 않습니다.** 잔액 불일치는 오픈 당일에 발견하면 회복이 불가능합니다.

## 2-3. 오픈 게이트 — 배포 가능 ≠ 오픈 가능

배포 가능과 오픈 가능은 다릅니다.

| 구분 | 조건 | 현재 |
|---|---|---|
| 법무 | 약관 6종 · **푸터 7건** | 미입력 |
| 불변식 | INV-1~11 CI 전건 통과 | ✅ 80건 |
| API | 필수 69건 스키마 정의 | 39/69 |
| 흐름 | 7단계 완주 · 단절 3곳 해소 | 화면 대기 |
| 연동 | PASS · NTS · 알림톡 · PG · 계좌인증 | 미착수 |
| 데이터 | 마이그레이션 리허설 · 잔액 정합성 100% | |
| 인프라 | Multi-AZ · PITR · 취약점 조치 · 롤백 절차 | |
| 운영 | 검수 1명 채용·교육 · 공급측 20곳 | |
| **임시경로** | 스테이징 임시 승인 경로 차단 확인 | B3 완료 시 |

`v_open_blockers` 가 미입력 필수 설정을 계속 보여 줍니다.

# 3부. 운영 절차

## 3-1. 매일

| 시각 | 무엇 | 어디서 |
|---|---|---|
| 오전 | **검수 큐** — SLA 24시간 | BO 검수 큐 탭 |
| 오전 | 배지 신청 (전건 수동) | BO 배지 탭 |
| 오전 | 사업자 승인 | BO 사업자 인증 탭 |
| 수시 | CRITICAL 경보 | BO 대시보드 |

**검수가 병목입니다.** 자동 승인된 건은 큐에 안 보이므로, 큐에 있는 것은 전부 사람이 봐야 하는 것입니다.

## 3-2. 매주

| 요일 | 무엇 |
|---|---|
| **수요일** | **정산 배치** — 아래 절차 |
| 주 1회 | 표본 감사 (자동 승인의 5%) |
| 주 1회 | 분쟁 처리 |

### 정산 배치 — 되돌릴 수 없습니다

```
1. 재대조 확인      GET /admin/settlement-batches/reconcile
                    ok=true 인지 확인. false 면 여기서 멈춥니다
2. 배치 생성        POST /admin/settlement-batches
                    같은 날 두 번 만들 수 없습니다 (run_date UNIQUE)
3. 내역 확인        지급 대상·금액 눈으로 확인
4. 이체 실행        POST /admin/settlement-batches/{id}/execute
                    ★ 이체 직전에 재대조를 다시 합니다
```

**재대조가 실패하면 이체하지 않고 CRITICAL 경보를 남깁니다.**

```
!! 금액 불일치: 정산 2700000 vs 합의 3000000 — INV-9 위반
→ RECONCILE_FAILED
```

이 경보가 뜨면 **원인을 찾기 전에는 절대 재시도하지 마십시오.**

## 3-3. 매월

| 무엇 | 임계 |
|---|---|
| **k값 확인** | **1.30 · 2개월 연속이면 검수 증원 발의** |
| 자동화율 추이 | `v_auto_review_rate` |
| 개입 사유 분포 | `v_manual_reasons` — 다음 자동화 후보 |
| 파기 기한 초과 | `v_purge_overdue` |

**k값이 병목의 선행 지표입니다.** 검수 1명의 한계가 17개월차인데 손익분기가 19개월차라, 이 지표를 놓치면 증원(2~3개월 소요)이 늦습니다.

## 3-4. 오픈 첫 주에 반드시 볼 것 ★

```sql
SELECT * FROM v_attribution_health;      -- 귀속률
SELECT * FROM v_contract_conversion;     -- 계약 발급률
```

| 지표 | 급락하면 |
|---|---|
| **귀속률** | `attribution.link()` 호출 누락 — 에러가 안 나고 조용히 샙니다 |
| **계약 발급률** | 시스템 밖에서 계약 — 성사가 포착되지 않습니다 |

**둘 다 시스템은 정상인데 사업 모델이 새는 형태**로 나타납니다. 인프라 지표로는 잡히지 않습니다.

## 3-5. 배치

### 스케줄은 하나입니다

EventBridge 가 매분 `POST /api/v1/admin/jobs/tick` 만 부릅니다.
**무엇을 언제 돌릴지는 DB(`job_schedules`)가 정합니다.**

```bash
aws cloudformation deploy \
  --template-file infra/eventbridge-jobs.yaml \
  --stack-name sgb-jobs \
  --parameter-overrides ApiEndpoint=https://api.sogaebank.com JobTokenArn=<시크릿ARN> \
  --capabilities CAPABILITY_IAM

aws scheduler list-schedules --group-name sgb-jobs    # 1건
```

전에는 배치마다 스케줄을 하나씩 뒀습니다. 그러면 **주기를 바꿀 때마다 스택을
다시 배포**해야 하고, **배치를 새로 만들면 스케줄 추가를 잊습니다.**
잊으면 그 배치는 영원히 안 도는데 오류도 나지 않습니다.

이제 주기는 SQL 한 줄입니다.

```sql
UPDATE job_schedules SET every_min = 30 WHERE job = 'notify_dispatch';
```

### 개발도 같은 경로입니다

```bash
npm run scheduler          # 로컬
docker compose up -d       # Docker (scheduler 컨테이너가 함께 뜹니다)
```

호출 대상·주기·인증이 운영과 같습니다 — `POST /admin/jobs/tick` 에 `X-Job-Token`.
**"로컬에선 되는데"가 생기지 않습니다.**

다만 운영에서는 이 데몬을 쓰지 마십시오. 프로세스가 죽으면 아무도 모릅니다.

### 매분 불러도 안전합니다

같은 시간대의 같은 작업은 `job_runs` 의 `UNIQUE (job, slot)` 때문에
**한 번만** 실행됩니다. 스케줄러가 둘이어도, ECS 태스크가 여럿이어도 마찬가지입니다.

### 현재 주기

| 주기 | job | 하는 일 |
|---|---|---|
| 10분 | `notify_dispatch` | 알림 외부 발송 |
| **2시간** | **`subscription_billing`** | **구독 자동 청구 — 매출 직결** |
| 매시간 | `sla_alert` · `expire_badges` · `risk_scan` · `k_alert` | SLA · 배지 · 위험감지 · 지표 |
| 매일 03:00 | `attribution_archive` | 귀속 로그 보관 |
| **매일 03:30** | **`pii_purge`** | **탈퇴 파기 — 법적 의무** |
| 매일 09:00 | `deal_auto_confirm` | 7일 무응답 자동 확정 |
| 매일 10:00 | `promo_expiry` | 무료 종료 D-14 고지 |
| 수요일 10:00 | `settlement_audit` | 정산 정합성 점검 (지급 아님) |

### 인증

`X-Job-Token` 헤더입니다. **SUPER 계정의 JWT 를 스케줄러에 심지 마십시오** —
만료되면 배치가 조용히 멈추고, 새면 관리자 전 권한이 넘어갑니다.
전용 토큰으로는 job 실행만 됩니다.

`JOB_TOKEN` 이 없거나 32자 미만이면 **항상 거부**합니다.

### 멈춘 것을 어떻게 아는가

| 감시 | 봅니다 |
|---|---|
| `v_job_stale` | 주기의 3배가 지나도록 안 돈 작업 — **0행이어야 정상** |
| `v_job_failures` | 최근 24시간 실패 |
| `sgb-tick-failure` | 5분 안에 3번 이상 실패 |
| **`sgb-tick-silent`** | **15분 동안 한 번도 안 불림 — 스케줄러가 멈춤** |

마지막 것이 중요합니다. 실패 알람은 "실패"를 보지 **"멈춤"을 못 봅니다.**

## 3-6. 경보 대응

| 경보 | 뜻 | 조치 |
|---|---|---|
| `SETTLEMENT_BATCH_BLOCKED` | 재대조 실패 | **이체하지 마십시오.** 원인 규명 우선 |
| `SETTLEMENT_TRANSFER_BLOCKED` | 이체 직전 실패 | 위와 같음 |
| `K_VALUE_ALERT` | k ≥ 1.30 2개월 | 검수 증원 발의 |
| `PII_PURGE_OVERDUE` | 파기 기한 초과 | **법정 기한 위반.** 즉시 확인 |
| `SLA_BREACH` | 검수 24시간 초과 | 큐 처리 |
| DLQ 적재 | 알림 발송 3회 실패 | 발송 사업자 확인 |

## 3-7. 콘텐츠 관리

현재 **BO 화면이 없어 SQL 로 수정**합니다.

```sql
-- FAQ
UPDATE faqs SET answer = '...' WHERE question LIKE '소개비는 언제%';

-- 화면 문구 — basis 가 있는 것은 함부로 고치지 마십시오

-- 코드 라벨 (관리자 화면 있음)
-- BO → 코드 라벨 탭
```

**FAQ 관리 화면은 오픈 전에 붙이는 것을 권합니다.** 문의가 늘면 자주 고칩니다.

# 4부. 사고 대응

## 4-1. 판단 기준

| 증상 | 우선순위 | 첫 조치 |
|---|---|---|
| **불변식 위반 발견** | **최상** | 서비스 중단 → 스냅샷 복원 |
| 정산 재대조 실패 | 최상 | 이체 중단 · 원인 규명 |
| 개인정보 유출 의심 | 최상 | `audit.pii_access_logs` 조회 |
| API 5xx 급증 | 상 | 이전 이미지로 롤백 |
| 검수 큐 적체 | 중 | 자동검수 정책 조정 |
| 알림 미발송 | 하 | 인앱 폴백 중. 발송사 확인 |

## 4-2. 하지 말아야 할 것

| 유혹 | 결과 |
|---|---|
| **`session_replication_role` 로 트리거 우회** | 무결성이 통째로 열립니다 |
| 정산 이체 자동 재시도 | 중복 지급 |
| 감사 로그 삭제 | DB가 거부합니다 (IP 마스킹만 허용) |
| 적용된 마이그레이션 수정 | 체크섬이 거부합니다 |
| 코드·DB 동시 롤백 | 2단계 배포를 지켰다면 불필요합니다 |

## 4-3. 조회용 쿼리

```sql
-- 오픈 차단
SELECT kind, item, reason FROM v_open_blockers;

-- 불변식 위반
SELECT * FROM fn_verify_invariants() WHERE violation_count > 0;

-- 개인정보 보관 현황
SELECT * FROM v_privacy_inventory;

-- 파기 기한 초과
SELECT * FROM v_purge_overdue;

-- 연동 진행
SELECT code, status, est_weeks_remaining FROM v_integration_status;

-- 콘텐츠 누락
SELECT * FROM v_content_missing;

-- 미확인 경보
SELECT alert_code, severity, title, created_at FROM ops_alerts
 WHERE acknowledged_at IS NULL ORDER BY created_at DESC;
```
