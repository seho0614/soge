# 2. 핵심 결정 12건 (17 아키텍처설계서)

## D1. 모듈형 모놀리식 · 배포 4개

| 후보 | 판단 |
|---|---|
| 마이크로서비스 | **정산·귀속이 서비스를 가로지릅니다.** 분산 트랜잭션을 직접 만들게 됩니다 |
| 단일 배포 | 검수 BO 배포가 사용자 트래픽에 영향을 줍니다 |
| **채택** | 코드 경계는 폴더, 배포 경계는 ECS 태스크 |

**되돌리는 비용** 낮음 — 모듈이 분리돼 있어 나중에 떼어낼 수 있습니다.

## D2. 규칙을 DB에 둡니다 ★

불변식·제한업종·한도·금칙어·설정 형식을 트리거와 CHECK로 강제합니다.

**이유** — 앱 코드에만 두면 데이터 보정 한 번에 조용히 깨집니다. 운영 중 DB를 직접 만지는 순간 무력화되고, **그때 아무도 모릅니다.**

**실제로 겪었습니다.** 관 열기 조건이 앱에만 있어 SQL로 직접 열면 통과했습니다.

**대가** — 서비스 코드가 얇아 처음 보면 "검증이 빠졌다"고 오해합니다.
**되돌리는 비용** **높음** — 127건의 검증이 이 위에 서 있습니다.

## D3. 컬럼의 부재로 지킵니다 ★

`settlements` 에 공제 컬럼이 없고, `deal_payment_records` 에 금액·계좌가 없습니다.

**이유** — 컬럼이 있으면 언젠가 화면에 나타납니다. **없으면 띄우려 해도 데이터가 없습니다.** INV-9·11을 코드 리뷰가 아니라 스키마로 지킵니다.

## D4. 트랜잭션을 인자로 넘기지 않습니다

`AsyncLocalStorage` 로 전달합니다.

**이유** — 인자로 넘기면 한 곳만 빠뜨려도 그 쿼리가 트랜잭션 밖에서 돌고 **컴파일도 테스트도 통과합니다.** 정산에서는 나중에 잔액으로 드러납니다.

**고친 결함** — 초기 구현은 단일 커넥션을 공유해서 무관한 요청 A가 B의 ROLLBACK에 휩쓸려 사라졌습니다.

## D5. 토큰을 믿지 않습니다

principal 을 매 요청 DB에서 재조립합니다.

**이유** — 구독 만료·사업자 승인이 15분 뒤에 반영되면 안 됩니다. **조회 1회 비용보다 "만료됐는데 통과"가 훨씬 비쌉니다.**

## D6. 자동 처리를 기본값으로

검수·성사 확정·정산 신청이 자동입니다.

**이유** — 검수 1명이 최대 병목이고 증원에 2~3개월이 걸립니다. 자동화율 70%면 실질 처리량이 3배가 됩니다.

**판정을 뒤집은 것이 핵심입니다.** "자동 승인해도 되는가"가 아니라 **"사람이 봐야 할 이유가 있는가"** 를 묻습니다. 기본값이 자동이므로 새 위험은 개입 사유를 하나 추가해 대응합니다.

**안전장치** — 표본 감사 5% · 정책 스위치로 전건 수동 전환 · 배지는 자동화 제외.

## D7. 문서를 손으로 쓰지 않습니다

**이유** — 화면·API·권한을 각각 손으로 쓰면 반드시 어긋납니다. 하나의 레지스트리에서 뽑으면 **어긋날 자리가 없습니다.**

## D8. 반응형 단일 코드베이스

**이유** — `m.` 분리면 화면이 90개 이상으로 늘고, 더 중요하게는 **PC 문의 단절이 화면 수만큼 재발합니다.** 상세 화면이 하나면 그 결함이 생길 자리가 없습니다.

## D9. 3관 우선 · 리드관 보류

**이유** — 리드관은 개인정보·보험·의료 부담을 함께 들고 옵니다. 미루면 그 부담도 미뤄집니다.

**되돌리는 비용** 낮음 — `100_lead` 마이그레이션을 폴더만 옮기면 됩니다.

## D10. 백업 기반 DR

**이유** — 멀티 리전은 비용 2배인데 자금 가정이 이미 안전지대 가장자리입니다. RPO 5분 · RTO 4시간으로 충분합니다.

## D11. 문구도 데이터입니다 ★

FAQ · 안내 문구 · 관별 폼 문구 · 코드 라벨을 소스에서 걷어냈습니다.

**이유** — 문구 하나 고치는 데 배포가 필요하면 안 됩니다. 법정 고지 문구라면 **배포 대기 시간이 곧 위반 기간**이 됩니다.

`ui_messages.basis` 에 근거를 함께 두어 **왜 있는 문구인지 모른 채 지우는 일**을 막습니다.

## D12. 문서를 코드에서 생성합니다

**이유** — 손으로 쓰면 반드시 어긋나고, **어긋난 문서는 없는 것보다 나쁩니다.**

# 3. API 규약의 근거 (09 API설계서)

## 3-1. `X-Ref-Code` 를 헤더에 둔 이유

소개코드를 쿼리 파라미터가 아니라 헤더로 받습니다.

**이유** — 쿼리에 두면 URL 공유·북마크·리다이렉트에서 사라집니다. 헤더는 클라이언트가 세션 내내 붙입니다. **귀속이 끊기면 모델이 무너집니다.**

## 3-2. `version` 을 본문에 둔 이유

낙관적 잠금 버전을 헤더(`If-Match`)가 아니라 본문에 둡니다.

**이유** — 프런트가 폼 hidden 필드로 자연스럽게 실어 보냅니다. 헤더로 두면 폼 제출 경로에서 빠뜨리기 쉽습니다.

## 3-3. 목록은 섞지 않습니다 ★

`promoted` 와 `organic` 을 분리해 반환합니다.

**이유** — 하나로 합치면 프런트가 라벨을 빠뜨릴 수 있고, **그게 곧 노출순위 표시 의무 위반**입니다(전자상거래법). 서버가 분리하면 섞을 수 없습니다.

## 3-4. 라벨은 서버가 내려 줍니다

`status` 와 `statusLabel` 을 함께 보냅니다.

**이유** — `REJECTED` 가 매물에서는 "반려", 분쟁에서는 "기각", 제안에서는 "거절"입니다. **코드만 보고 화면에서 판단하면 틀립니다.**

## 3-5. 금액은 정수입니다

DB `NUMERIC` ↔ 응답 정수. `Float` 금지.

**이유** — 부동소수점은 정산에서 원 단위가 틀립니다. `node-postgres` 가 `NUMERIC` 을 문자열로 주는 것도 경계에서 변환합니다 — **문자열로 두면 프런트가 매번 `Number()` 를 부르다 한 곳을 빠뜨립니다.**

## 3-6. 오류 4종을 구분하는 이유

| 상태 | 프런트가 해야 할 일 |
|---|---|
| 400 | 입력 고치기 |
| 403 | **무엇을 하면 되는지 안내** — 막는 게 목적이 아닙니다 |
| **409** | **재시도 버튼을 띄우지 않습니다** |
| **422** | `message` 를 **그대로** 표시 |

**409와 422를 섞지 않는 이유**는 프런트가 재시도할지 말지를 판단해야 하기 때문입니다.

**422 message 를 프런트가 가공하지 않는 이유**는 제한업종 차단 문구처럼 **관리자가 바꿀 수 있어야** 하기 때문입니다.

# 4. 백엔드 규약의 근거 (15 백엔드설계서)

## 4-1. 이 백엔드가 다른 곳과 다른 점

**규칙 판정을 서버가 하지 않습니다.** 그래서 서비스 코드에 검증 로직이 거의 없습니다.

처음 보면 "검증이 빠졌다"고 오해합니다. **의도된 것입니다** — 두 곳에 두면 어긋나고, 어긋나면 어느 쪽이 맞는지 판단할 근거가 없습니다.

## 4-2. 리포지토리가 트랜잭션을 열지 않습니다

서비스가 열고 리포지토리는 `RequestCtx` 로 커넥션을 받습니다.

**이유** — 그래야 **다른 모듈의 리포지토리도 같은 트랜잭션에 들어옵니다.** 리스팅 등록과 검수 큐 적재가 한 트랜잭션이어야 하니까요.

## 4-3. 중첩 트랜잭션을 savepoint 없이 합류시키는 이유

**안쪽에서 COMMIT 이 나가면 바깥의 실패가 이미 확정된 데이터를 되돌리지 못합니다.**

## 4-4. 목 DB를 쓰지 않는 이유

이 시스템의 규칙 대부분이 트리거와 CHECK에 있습니다. **목으로 테스트하면 아무것도 검증되지 않습니다.**

## 4-5. 부팅 스모크가 필요한 이유 ★

컨트롤러를 `app.module.ts` 에 등록하지 않아도 **타입 검사와 문서 생성은 통과합니다.**

실제로 컨트롤러 7개가 배선되지 않은 상태였고, **앱을 띄우면 라우트가 0건이었습니다.** 배포 후에야 알았을 결함입니다.

중복 라우트 검사도 같은 이유로 붙였습니다 — 같은 경로를 두 컨트롤러가 정의하면 뒤에 등록된 쪽이 무시되고, **권한이 다르면 조용히 잘못된 게이트가 걸립니다.**

## 4-6. 컨트롤러 데코레이터 6종을 한 세트로 두는 이유

```
@Roles  @RequireGate  @Audit  @PiiAccess  @ApiOperation  @ApiResponse(422)
```

하나라도 빠지면 권한이 뚫리거나, 감사 기록이 없거나, 프런트가 스키마를 못 받습니다.

# 5. 프런트 판단의 근거 (16 프런트엔드설계서)

## 5-1. 앱을 2개로 나눈 이유

| 앱 | 이유 |
|---|---|
| 사용자 웹 (Next.js **SSR**) | **매물 노출이 SEO에 걸려 있습니다.** CSR이면 리스팅이 검색에 안 잡힙니다 |
| 운영 BO (Vite **SPA**) | SEO 무의미. **검수가 병목이라 착수 속도 우선** |

## 5-2. 이 제품이 무엇인가

금액이 수백만~수억이고, 사용자는 하루에도 여러 건을 훑는 실무자입니다.

**소비자 마켓플레이스가 아닙니다.** 설레게 만들 필요가 없고, **빠르게 판단하게** 만들어야 합니다.

## 5-3. 색을 다섯 개로 제한한 이유

**관이 셋이라 관별 색을 쓰고 싶어지는데, 그러면 금액과 경쟁합니다.** 관 구분은 색이 아니라 라벨과 위치로 합니다.

금액에 짙은 초록(`#0F6B4A`)을 **전용**으로 두고 다른 어디에도 쓰지 않습니다.

## 5-4. 금액에 `tabular-nums` 를 쓰는 이유

목록에서 **자릿수가 흔들리면 비교가 안 됩니다.**

## 5-5. 등급을 카드에 표시하지 않는 이유

필터·정렬에만 씁니다. **"브론즈 매물"로 보이면 낙인이 됩니다.**

## 5-6. ★ 상세 화면 CTA 배치 — 남은 유일한 귀속 구멍

```
[문의하기]   주 동선 · 시각적 우위 · 귀속 안 (INV-2)
[전화하기]   보조 · 하단 · 낮은 대비 · 귀속 밖
```

모바일 하단 고정바가 같은 컴포넌트의 CSS 분기라 **배치가 한 줄로 뒤집힙니다.** 전화가 위로 올라가면 통화가 귀속 밖으로 샙니다.

**050 안심번호가 붙기 전까지 이 배치가 유일한 방어입니다.**

## 5-7. Redux를 쓰지 않는 이유

서버 데이터가 대부분이고 TanStack Query 가 캐시를 갖습니다. **Redux를 얹으면 같은 데이터가 두 곳에 생깁니다.**

## 5-8. 화면 컴포넌트 파일명에 화면 ID를 넣는 이유

**71화면을 소수 인원이 추적하는 유일한 방법입니다.** 화면정의서에서 ID로 검색하면 바로 파일을 찾습니다.

# 6. 시스템 판단의 근거 (13 시스템설계서)

## 6-1. `ap-northeast-2` 고정

**개인정보 국외이전 판단을 아예 발생시키지 않는 것이 가장 싼 법무 대응입니다.**

## 6-2. 커넥션 풀 계산

```
태스크 4 × 풀 10 = 40 ≤ db.t4g.medium max_connections
```

스케일 아웃 시 다시 계산해야 합니다. **커넥션 고갈은 CPU가 한가한데 응답이 멈추는 형태**라 원인 찾기가 어렵습니다.

## 6-3. 앱 내 cron 을 쓰지 않는 이유

**ECS 태스크가 2개면 두 번 실행됩니다.** EventBridge 가 엔드포인트를 호출하고, 판정 로직이 DB에 있으므로 워커가 죽어도 규칙은 그대로입니다.

## 6-4. 운영 계정에 상시 권한을 주지 않는 이유

**개발자가 운영 DB에 상시 접근할 수 있으면 앞의 모든 통제가 우회됩니다.** 인원이 적을수록 지켜지기 어려우니 처음부터 승인형 임시 권한을 깔아야 합니다.

## 6-5. 사업 지표가 곧 경보인 이유

| 뷰 | 의미 |
|---|---|
| `v_attribution_health` | 급락 = `link()` 호출 누락 |
| `v_contract_conversion` | 낮음 = **시스템 밖 거래** |

**둘 다 시스템은 정상인데 사업 모델이 새는 형태**로 나타납니다. 인프라 지표로는 잡히지 않습니다.

---

# 7. 연동 판단의 근거 (12 연동설계서)

## 7-1. 발신 IP 등록이 임계 경로인 이유

**6종 전부 화이트리스트를 요구하고 심사에 2~4주 걸립니다.**

```
코드보다 IP가 먼저 필요합니다.
```

## 7-2. NTS를 1순위로 둔 이유

리드타임이 2주로 가장 짧고 **키 주입만으로 전환**되며, 사업자 승인 자동화의 전제이기도 합니다.

## 7-3. `stub: true` 를 응답에 싣는 이유 ★

구 모델에서 **"클릭 즉시 통과"가 실동작처럼 보인 것**이 시연 리스크로 지목됐습니다.

같은 실수를 막으려면 **데이터에 표시가 있어야** 합니다. 화면은 그걸 받아 "연동 준비 중 — 실제 확인이 이루어지지 않았습니다"를 띄웁니다.

## 7-4. PG 웹훅에서 200을 먼저 응답하는 이유

```
서명 검증 → 멱등키 조회 → 200 즉시 응답 → 큐 적재 후 비동기 처리
```

**처리하고 응답하면** 타임아웃 때 PG가 재전송하고, 그러면 중복 결제로 보입니다.

## 7-5. PG에 소개비를 태우지 않는 이유 ★

**그 순간 자금 수탁이 되고 INV-11이 깨집니다.** 전자금융거래법 등록 문제로 번집니다.

## 7-6. 시크릿을 DB에 넣지 않는 이유

**DB에 키를 넣으면 백업·복제본에 전부 퍼집니다.** Secrets Manager 키 이름과 등록 여부만 기록합니다.

## 7-7. 정산 이체를 자동 재시도하지 않는 이유

**원인을 모르는 상태에서 다시 쏘는 것이 가장 위험합니다.**

---

# 8. 연계 판단의 근거 (18 연계설계서)

## 8-1. 모듈 간 연계의 상당수가 트리거입니다 ★

**앱 코드에 없는 연계가 18건 있습니다.** 모르면 "왜 이 정산이 만들어졌지"가 됩니다.

가장 중요한 것 —

```
POST /deals/{id}/contract/sign  (두 번째 서명)
  └─ 확인 2행 → CONFIRMED → 귀속 스냅샷 → settlements 생성 → 알림
```

**API 하나가 5개 테이블을 바꿉니다.** 앱 코드에는 서명 UPDATE 한 줄뿐입니다.

## 8-2. `deal` 이 `settlement` 을 부르지 않는 이유

**정산은 트리거가 만듭니다.** 그래서 의존 순환이 없고, 어느 엔진부터 테스트할지 정할 수 있습니다.

## 8-3. 소개비와 플랫폼 매출을 잇는 코드가 없는 이유 ★

```
소개비 흐름 (플랫폼 밖)   fee_agreements → deals.agreed_fee → settlements.amount
플랫폼 매출 (플랫폼 안)   payment_transactions → ledger_entries
```

**`deal` 모듈과 `ledger` 가 서로를 모릅니다.** 이게 INV-9를 구조로 지키는 방법입니다.

## 8-4. 알림 실패로 본 처리를 롤백하지 않는 이유

**성사됐는데 알림이 안 갔다고 성사를 취소할 수는 없습니다.**

---

# 9. 배포 판단의 근거 (25 배포운영서)

## 9-1. 코드 롤백과 DB 롤백을 함께 하지 않는 이유

2단계 배포를 지켰다면 **구 코드가 새 스키마에서 돕니다.** 불변식 위반이 발견됐을 때만 스냅샷 복원입니다.

## 9-2. DB 변경을 2단계로 나누는 이유

```
1차  컬럼 추가만. 기존 코드가 계속 동작해야 함
     코드 배포
2차  구 컬럼 제거 (1주 후)
```

**정산 데이터는 롤백이 불가능합니다.**

## 9-3. 오픈 차단을 네 곳에서 보는 이유

```
SETTING      값이 있고 형식도 맞아야 합니다
TERM         내용과 시행일 없이 발행 불가
FOOTER       목적지 없는 약관 링크
INTEGRATION  PG·PASS·1원인증이 LIVE 여야 함
```

**값이 있는 것과 값이 맞는 것은 다릅니다.** "대표자명" 같은 자리표시자를 넣으면 `v_open_blockers` 는 통과하지만 **그대로 푸터에 나가면 통신판매업 고지 위반**입니다.

## 9-4. 대량 이관에서 트리거를 끄되 반드시 재검증하는 이유

```
트리거 비활성화 → 벌크 적재 → fn_verify_invariants() → 위반 0건 확인 → 재활성화
```

**4번에서 하나라도 걸리면 롤백.** 잔액 불일치는 오픈 당일에 발견하면 회복이 불가능합니다.

# 부록. 이 설계가 배운 것

**설계서에 적혀 있다고 동작하는 것은 아닙니다.** 이번 세션에서 13건의 결함을 찾았는데, 전부 "설계서에는 있는데 코드에는 없는" 유형이었습니다.

| 유형 | 예 | 발견 방법 |
|---|---|---|
| 배선 누락 | 컨트롤러 7개 미등록 → 라우트 0건 | **앱을 띄워 봄** |
| 호출부 부재 | 워커 없이 배치 함수만 존재 | 함수 사용처 검색 |
| 시드 누락 | 알림 템플릿 0건 · 약관 1종 | 실제 데이터 조회 |
| **검사 부재** | **금칙어 테이블만 있고 검사 없음** | 실제로 넣어 봄 |
| 우회 가능 | 관 열기 조건이 앱에만 있음 | SQL로 직접 실행 |

**타입 검사와 문서 생성은 이 중 무엇도 잡지 못합니다.** 그래서 검증을 127건까지 늘렸고, 부팅 스모크와 중복 라우트 검사를 CI에 넣었습니다.
