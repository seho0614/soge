# 352. 포인트 출금(현금 지급) — v10.219 (2026-11-09)

> 계기: 대표 「포인트 현금 가능」(11/9) · v10.218 추천 보상을 켜기 전 「포인트 쓰임」 결정(partner-affiliate 미정 #4).
> 정한 것(11/9 AskUserQuestion): 대상 **현금화 가능 포인트 모두** · 최소 출금 **10,000원** · 원천징수는 **운영 화면에서 비율(SUPER)** · 운영 반영은 **v10.216 → v10.219 한 번에** · 계획 「승인」 · 원천징수율 **3.3** · **신고 자료 내려받기 + 주민등록번호 받기(「모두」)**.
>
> **마이그레이션 1개 D190(227 → 228)** · 새 API 6개(회원 4 · 운영 반려 · 신고 자료) · 지급 데스크에 종류 「포인트」 · **원천징수율 처음 값 3.3%**(대표 11/9 「원천징수율 3.3」 — 적용하면 바로 출금 신청을 받음).

## 1. 흐름

```
회원 신청(REQUESTED) ──확정(ADMIN)──► CONFIRMED ──이체 뒤 지급 기록(PAYOUT · 다른 사람)──► PAID
      │                         │
      └─ 회원 취소(CANCELED)     └─ 반려(REJECTED · 사유) — 신청 · 확정 상태에서 · 포인트는 출금 가능 잔액으로 돌아감
```

- 출금 가능 잔액 = 현금화 가능(`redeemable`) 포인트 합계 − 신청 · 확정 · 지급된 출금(`fn_point_cashable`).
- 1포인트 = 1원 · 원천징수 = **소득세(비율의 10/11 · 10원 미만 버림) + 지방소득세(소득세의 10% · 10원 미만 버림)** · 실지급액 = 포인트 − 원천징수. 예) 3.3% · 12,345 → 370 + 30 = 400 · 받는 금액 11,945.
- 실제 송금은 은행 연동이 없어 지급 담당이 직접 이체하고 「지급 기록」에 이체 참조를 적음(제휴 정산과 같음).

## 2. DB — D190_point_cashout

| 무엇 | 내용 |
|---|---|
| ① 추천 보상 현금화 | `point_rules.REFERRAL_DIRECT.needs_valid` → false(가입한 분 본인인증이 곧 확인) · `fn_referral_reward` 가 `redeemable true` 로 넣음. `point_ledger` 는 고칠 수 없는 표라 이미 쌓인 줄은 그대로(운영은 보상이 꺼져 있어 줄 없음) |
| ② 설정 | `point.cashout_min` 10000 · `point.cashout_tax_rate` **3.3**(대표 11/9 · 비우면 신청 막힘 · 0 ~ 50 · 소수 한 자리) · 바꾸기 SUPER(`POINT_SETTING_SUPER`) |
| ③ `point_cashouts` | 포인트 · 원천징수율 · 세액 · 실지급액(신청 때 값) · 받을 계좌(`payout_accounts` 참조 + 은행 이름 · 뒤 4자리 · 예금주를 신청 때 값으로) · 상태 · 확정 · 지급 · 반려(사람 · 시각 · 이체 참조 · 사유). **계좌번호 칸 없음(INV-11)** · 처리 중 신청은 한 사람 하나(`ux_point_cashouts_open`) |

| ⑥ 신고 자료 · 주민등록번호 | `point_cashouts.income_tax · local_tax`(합 = 원천징수) · `account_tax_ids`(주민등록번호 `pgp_sym_encrypt` · 가린 값 `900101-1******` 만 화면) · 스위치 `point.cashout_tax_id`(**꺼진 채**) — 켜지면 등록 없이 출금 신청을 DB 가 막음. **지금 처리방침에는 주민등록번호 수집 줄이 없어** 처리방침(지금 판) 본문에 「주민등록번호(암호화)」가 있어야 켤 수 있음(API 422 `TAX_ID_PRIVACY_FIRST`) |
| ⑦ 주민등록번호 파기 | 마지막 지급(지급이 없으면 등록 · 고친 날)이 있는 해(한국 시각)의 **다음 해 1월 1일부터 5년**(`privacy.tax_id_retention_years` 5 · 5 ~ 10) 지나면 매일 03:00 개인정보 파기 작업(`pii_purge` → `fn_purge_tax_ids`)이 지움 · 처리 중 신청이 있으면 남김 · 파기 날짜 `v_tax_id_purge_due` · 운영 화면 「파기 실행 기록」에 「주민등록번호」 칸 |
| 지급 대기열 | `v_payout_queue` 에 `POINT`(받는 사람 = 회원 이름 · 계좌 확인이 풀리면 「지급 불가」) |
| DB 오류 | `POINT: …` → 422 `POINT_RULE` · **`PAYOUT: …`(2인 원칙) → 422 `PAYOUT_RULE`** — 전에는 잡지 않아 제휴 · 소개몰 정산에서도 500 으로 나갔음(이번에 바로잡음) |

## 7. 운영 반영 · 남은 일

1. 운영 반영은 v10.216 → v10.219 한 번에(절차서 따로) — 마이그레이션 2개(D189 · D190) · apply 가 스냅샷 yes 를 물음.
2. **원천징수율 3.3%(대표 11/9)** — 운영 적용 뒤 바로 출금 신청을 받음. 3.3% 는 사업소득(소득세 3% + 지방소득세 0.3%) 비율 — 과세최저한(얼마 이하 비과세) · 지급명세서 신고는 이번에 넣지 않음. 세무 확인 결과가 다르면 운영 화면에서 SUPER 가 바꿈(이미 들어온 신청은 신청 때 비율).
3. 앞선 법무 확인(11/9 이상 없음 · 다단계 해당 안 됨)은 「현금화 안 됨」 기준이었음 — 현금 지급으로 바뀐 것을 법무에 한 번 더 알릴 것을 권함.
4. **주민등록번호 받기는 꺼진 채** — 처리방침 개정(초안 docs/19 에 「포인트 출금 신청 시 · 주민등록번호(암호화)」 줄 · 목적 · 보유 5년을 넣음 · 법령 조항은 법무 확인) → 법무 확인 → 약관 화면에서 게시 → 운영 화면 지급 데스크에서 SUPER 가 켬. 그 전에 지급한 건은 신고 자료에 주민등록번호가 비어 있어 따로 받아 채워야 함(내려받기 안내 글에 건수).
5. 주민등록번호 보관 5년 자동 파기는 넣음(대표 11/9) — 5년의 근거(국세기본법 장부 보존)와 처리방침 문구는 법무 · 세무 확인 필요.
