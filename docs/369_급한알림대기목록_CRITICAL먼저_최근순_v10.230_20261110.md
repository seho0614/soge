# 369. 급한 운영 알림 대기 목록 — CRITICAL 먼저 · 최근 순 — v10.230 (2026-11-10)

> **마이그레이션 1개 D198(235 → 236)** · 새 API 없음 · 화면 없음 · 보내는 쪽(메일 · 텔레그램) 글 한 줄.

## 1. 왜

- 급한 알림 메일 · 텔레그램 대기 목록(`fn_ops_alert_mail_pending` · `fn_ops_alert_push_pending`)은 **오래된 순 50건**이었습니다.
- 메일 · 텔레그램을 못 보내는 동안(운영은 메일 설정 전 · 텔레그램 켜기 전) 하루 안에 50건 넘게 쌓이면 **새 CRITICAL 이 목록에 들지 못했습니다**.
- v10.228 점검 때 시험이 이 일로 실패한 것을 보고 찾음(docs/368 4-2 ⑤).

## 2. 바뀐 것

| 곳 | 내용 |
|---|---|
| D198 | 두 대기 함수 — 고르는 기준(종류 · 24시간 · 풀린 것 빼고 · 확인 안 한 것 · 종류마다 1시간에 1통)은 그대로, 순서만 `CRITICAL 먼저 → 최근 순` 50건 |
| D198 | `fn_ops_alert_mail_backlog()` · `fn_ops_alert_push_backlog()` — 같은 기준의 전체 수(50건 제한 없음) |
| 보내는 쪽 | 메일 · 텔레그램 끝에 남은 것이 있으면 「보내지 못한 알림 n건 더 — 다음 차례에 이어서 보냅니다(운영 화면 › 운영 알림에서 모두 볼 수 있음).」 |

- 남은 알림도 24시간 안에는 다음 차례(정기 작업)에 계속 보냅니다. 24시간이 지나면 메일 · 텔레그램 대상에서 빠지고 운영 화면에만 남습니다(전과 같음).
- 「다시 알림」(12시간 넘게 확인 안 한 CRITICAL)은 그대로.

## 3. 시험

- `qa/test_v1230.py` — ① 코드 ② DB(한 거래 · 되돌림): 오래된 WARN 60건 + 새 CRITICAL 1건 + 새 WARN → 목록 50건 · 맨 앞 새 CRITICAL · 그다음 최근 순 · 남은 수 = 전체 기준 수 · 1시간 규칙 그대로.
