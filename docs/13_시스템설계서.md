## 2. 배포 단위 4개

배포는 4개, 코드는 단일 저장소입니다. **코드 경계는 폴더로, 배포 경계는 ECS 태스크로** 나눕니다.

| 태스크 | 담당 | 사양(초기) | 스케일 |
|---|---|---|---|
| `web-api` | 사용자 3관 · 인증 · 리스팅 · Deal | 0.5 vCPU / 1GB × 2 | CPU 70% |
| `admin-bo` | 검수 · 정산 조회 · 정책 · 코드 | 0.25 / 0.5GB × 1 | 고정 |
| `worker` | 배치 8종 · 알림 발송 · 아카이브 | 0.25 / 0.5GB × 1 | 고정 |
| `lead-api` | 리드관 | — | **보류** |

### 왜 모듈형 모놀리식인가

| 후보 | 판단 |
|---|---|
| 마이크로서비스 | **정산·귀속이 서비스를 가로지릅니다.** 분산 트랜잭션을 직접 만들게 됩니다 |
| 단일 배포 | 검수 BO 배포가 사용자 트래픽에 영향을 줍니다 |
| **모듈형 모놀리식 · 배포 4** | 코드는 하나, 장애 격리는 태스크 단위 |

**`admin-bo` 를 분리한 이유**는 검수가 병목이라 사용자 트래픽과 무관하게 배포하고 스케일해야 하기 때문입니다.

**`worker` 를 분리한 이유**는 배치가 오래 걸리는 쿼리를 돌리기 때문입니다. 같은 태스크면 사용자 요청이 커넥션을 못 얻습니다.

## 3. 런타임

### 3-1. 프로세스

| 항목 | 값 |
|---|---|
| Node.js | LTS · TypeScript 5 (strict) |
| 프레임워크 | NestJS 11 |
| 부팅 | 환경변수 검증 → 실패 시 **프로세스가 뜨지 않음** |
| 종료 | `enableShutdownHooks()` — 풀 정리. 배포 시 커넥션 누수 방지 |
| 헬스체크 | ALB → `/health` · DB 연결 확인 포함 |

**부팅 시 검증이 배포 안전장치입니다.** `JWT_SECRET` 이 없거나 운영에서 32자 미만이면 뜨지 않고, ECS 헬스체크가 롤아웃을 막습니다.

### 3-2. 커넥션 풀

```
DB_POOL_MAX = 10 (태스크당)
statement_timeout = 15초
idleTimeoutMillis = 30초
```

**태스크 수 × 풀 크기가 RDS max_connections 를 넘지 않아야 합니다.** web-api 2 + admin-bo 1 + worker 1 = 4 태스크 × 10 = 40. `db.t4g.medium` 의 기본값 안입니다.

스케일 아웃 시 이 계산을 다시 하십시오. **커넥션 고갈은 CPU 가 한가한데 응답이 멈추는 형태로 나타나** 원인을 찾기 어렵습니다.

### 3-3. 트랜잭션 격리

트랜잭션마다 **전용 커넥션**을 잡고 `AsyncLocalStorage` 로 전달합니다.

```
옛 구현(단일 커넥션 공유): A 유실 — B의 ROLLBACK에 휘말림
현재:                      A는 커밋 · B만 롤백
```

중첩 호출은 savepoint 없이 합류합니다 — 안쪽에서 COMMIT 이 나가면 바깥의 실패가 확정된 데이터를 되돌리지 못합니다.

### 3-4. 요청 컨텍스트

```
ContextMiddleware  →  requestId · ip · userAgent
AuthMiddleware     →  principal (DB 재조립)
AuthGuard          →  @Roles · @RequireGate
AuditInterceptor   →  @Audit → audit.audit_logs
DbErrorFilter      →  DB 예외 → 422 / 409
```

**순서가 중요합니다.** 컨텍스트가 먼저 열려야 인증이 actor 를 담고, 감사 로그에 누가 했는지가 남습니다.

## 4. 데이터 계층

### 4-1. RDS

| 항목 | dev/stg | prod |
|---|---|---|
| 인스턴스 | db.t4g.small | db.t4g.medium |
| 가용성 | Single-AZ | **Multi-AZ** |
| 백업 | 7일 | **35일 + PITR** |
| 암호화 | KMS | KMS |

**오픈 D-14 에 Multi-AZ 로 전환**합니다. 그 전까지는 월 $130 을 아낍니다.

### 4-2. Redis

세션 · 정책 캐시(TTL 60초) · 분산 락.

> **초기 단일 노드는 단일 장애점입니다.** 세션이 날아가면 전원 재로그인이고, 오픈 직후에는 치명적입니다. **오픈 전 Multi-AZ 전환**하거나 세션만이라도 DB 폴백을 두십시오.

### 4-3. S3

| 버킷 | 용도 | 설정 |
|---|---|---|
| `sgb-uploads` | 첨부 · 사업자등록증 · 매물 이미지 | presigned URL 만 |
| `sgb-contracts` | 계약서 PDF | **Object Lock** |
| `sgb-audit` | 귀속 로그 · 감사 로그 아카이브 | **Object Lock (Compliance, 5년)** |

**사업자등록증·계약서는 직접 노출하지 않습니다.** CloudFront 서명 URL 로만 내려갑니다.

### 4-4. SQS

| 큐 | 용도 |
|---|---|
| `q-notify` | 알림 발송 (DLQ 有) |
| `q-review` | 검수 이벤트 |
| `q-settlement` | 정산 이체 요청·대사 |
| `q-archive` | S3 아카이브 |

DLQ 는 3회 실패 후. **DLQ 적재는 CRITICAL 경보 대상**입니다.

## 5. 보안

| 계층 | 통제 |
|---|---|
| 엣지 | WAF (SQLi · XSS · rate limit) · CloudFront 서명 URL |
| 인증 | JWT access 15분 + refresh 쿠키 14일 · 계좌·정산은 재인증 |
| 인가 | 역할 7종 · `@Roles` · `@RequireGate` 3종 |
| 데이터 | `pii` 스키마 격리 · 컬럼 암호화 · 조회 전건 감사 |
| DB | 불변 테이블 9종에서 앱 유저 UPDATE/DELETE **권한 회수** |
| 인프라 | 운영 계정 상시 권한 없음 · IAM Identity Center 승인형 |
| 감사 | `audit.audit_logs` append-only → S3 Object Lock 5년 |
| 시크릿 | Secrets Manager · 코드·저장소에 두지 않음 |

### 마지막 두 줄이 핵심입니다

개발자가 운영 DB 에 상시 접근할 수 있으면 앞의 통제가 전부 우회됩니다. **인원이 적을수록 지켜지기 어려우니 처음부터 승인형 임시 권한을 깔아야 합니다.**

### 계정 구조

| 환경 | AWS 계정 |
|---|---|
| dev · stg | 비운영 계정 (VPC 분리) |
| prod | 운영 계정 |

Organizations + SCP 로 운영 계정의 위험 작업(리전 이탈 · CloudTrail 중지)을 차단합니다.

## 6. 관측

### 6-1. 지표 3층

```
인프라   CloudWatch — CPU · 메모리 · 커넥션 · ALB 5xx · RDS 지연
애플리케이션  구조화 로그 (requestId 상관관계) · Sentry
사업     DB 뷰 15종 — 아래
```

### 6-2. 사업 지표가 곧 경보입니다

| 뷰 | 임계 | 의미 |
|---|---|---|
| `v_k_value` | **1.30 · 2개월 연속** | 검수 증원 발의 |
| `v_auto_review_rate` | 하락 | 자동화율 = 검수 여력 |
| `v_review_throughput` | SLA 위반 | 일 50건 한계 |
| `v_attribution_health` | **급락** | `link()` 호출 누락 |
| `v_contract_conversion` | 낮음 | **시스템 밖 거래** |
| `v_open_blockers` | ≠ 0 | prod 배포 차단 |

**`v_attribution_health` 와 `v_contract_conversion` 을 오픈 첫 주부터 보십시오.** 둘 다 시스템이 정상 동작하는데 사업 모델이 새는 형태로 나타납니다.

### 6-3. 경보 등급

| 등급 | 예 | 대응 |
|---|---|---|
| CRITICAL | k값 초과 · 정산 배치 중단 · DLQ 적재 · 불변식 위반 | 즉시 |
| WARN | SLA 위반 · 프로모션 미고지 · 제한업종 차단 | 당일 |
| INFO | 자동 승인 표본 | 주간 |

`ops_alerts` 에 쌓이고, **미확인 CRITICAL 이 있으면 배포가 막힙니다.**

## 7. 확장 계획

지금은 필요 없지만 **어디서 갈아탈지**는 정해 둡니다.

| 지점 | 현재 | 전환 시점 | 대안 |
|---|---|---|---|
| 검색 | pg_trgm | 매물 5만 건 | OpenSearch + Nori |
| DB | RDS Postgres | 쓰기 포화 | Aurora (읽기 복제) |
| 캐시 | Redis 단일 | 오픈 전 | Multi-AZ |
| 컴퓨트 | Fargate | 운영 인력 확보 후 | (전환 불필요) |
| 파일 | S3 직접 | 트래픽 증가 | CloudFront 오리진 |

**한국어 검색이 가장 먼저 한계에 닿습니다.** `pg_trgm` 은 형태소 분석을 하지 않아 조사·복합어 처리가 약합니다. 통합 검색이 P0 인데 초기 품질이 기대에 못 미칠 수 있습니다.

## 8. 재해 복구

| 항목 | 목표 |
|---|---|
| RPO | 5분 (PITR) |
| RTO | 4시간 |
| 방식 | **백업 기반.** 멀티 리전 DR 없음 |

**멀티 리전을 하지 않는 이유**는 비용이 2배이고, 자금 가정이 이미 안전지대 가장자리이기 때문입니다. 백업 기반 복구로 충분합니다.

### 복구 시나리오

| 상황 | 조치 |
|---|---|
| 태스크 장애 | ECS 자동 재기동 |
| AZ 장애 | Multi-AZ 자동 페일오버 |
| 데이터 손상 | PITR — 손상 시각 직전으로 |
| **불변식 위반 발견** | **즉시 서비스 중단 → 스냅샷 복원** |
| 리전 장애 | 백업으로 재구축 (RTO 4시간) |

**DR 리허설을 오픈 전 1회 수행**하십시오. 해 본 적 없는 복구 절차는 절차가 아닙니다.
