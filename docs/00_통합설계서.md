# 1. 사업 모델과 불변식

## 1-1. 무엇을 파는가

소개자가 사업자 간 거래를 연결하고 **소개비를 당사자로부터 직접** 받습니다. 플랫폼은 그 돈에 손대지 않고 **구독료와 광고**로 수익을 냅니다.

이 구조가 차별점이자 최대 리스크입니다. 공제하지 않으니 소개자에게 유리하지만, **성사를 숨겨도 플랫폼이 잃을 게 없어 보입니다.**

## 1-2. 불변식 11개

| INV | 내용 | 구현 |
|---|---|---|
| 1 | tier = 1 고정 | `CHECK (tier = 1)` |
| 2 | first-touch 90일 귀속 | append-only + `fn_attribution_resolve` |
| 3 | CONFIRMED 이후에만 정산 | `fn_assert_settlement_rules` |
| 4 | 양측 확인 필수 | `fn_assert_both_confirmed` |
| 5 | 후기는 Deal 종속 | `deal_id NOT NULL FK` |
| 6 | 제한업종 API 제외 | `fn_block_restricted_listing` → 422 |
| 7 | 인증 게이트 | `@RequireGate` + DB |
| 8 | 구독 없이 코드 발급 불가 | `fn_assert_active_subscription` |
| 9 | 소개비 무공제 | **공제 컬럼 부재** + 3단계 재대조 |
| 10 | 사업자만 소개비 수령 | `payee_business_id` + `verified_at` |
| 11 | 플랫폼 자금 미수탁 | **금액·계좌 컬럼 부재** |

## 1-3. 설계를 관통하는 네 원칙

**① 컬럼의 부재가 곧 설계입니다.**
`settlements` 에 공제 컬럼이 없고, `deal_payment_records` 에 금액·계좌가 없습니다. 화면에 띄우려 해도 데이터가 없습니다.

**② 검사를 두 곳에 두지 않습니다.**
제한업종·금칙어·한도·설정 형식·관 열기 조건은 DB가 판정하고 앱은 다시 검사하지 않습니다.

**③ 규칙은 코드가 아니라 데이터입니다.**
자동검수 사유, 반려 코드, 제한업종, 배지 정책, 코드 라벨, 약관 상태, 금칙어, 연동 상태가 전부 테이블에 있습니다.

**④ 문구도 데이터입니다.**
FAQ · 안내 문구 · 관별 폼 문구 · **약관 본문**을 소스에서 걷어냈습니다. **법정 고지 문구라면 배포 대기 시간이 곧 위반 기간**이 됩니다.

## 1-4. 중개 이탈 — 최대 리스크

| | 상태 |
|---|---|
| ① 구독 해지 시 미성사 코드 실효 | ✅ |
| ② 성사 신고 유인 | ✅ **자동 처리로 불필요해짐** |
| ③ 050 안심번호 | 스키마 완료 · **도입 여부 미결** |
| ④ 구독 가치 이전 | ✅ |
| ⑤ 플랫폼 밖 유도 차단 | ✅ 금칙어 WARN |

**남은 구멍** — 계약이 시스템 밖에서 이루어지면 포착되지 않습니다. `v_contract_conversion` 이 유일한 탐지 수단입니다.

# 4. 엔진 계층

## 4-1. 귀속 엔진 — 모델의 급소

**해결한 결함**: `attribution_events.account_id` 가 INSERT 시점에 고정되는데 테이블이 append-only라, **비로그인 유입 후 로그인한 방문자가 영원히 연결되지 않았습니다.**

```
visitor_identities (visitor_key, account_id, linked_at)   append-only
  판정 시 조인. linked_at >= occurred_at 으로 공용 PC 오귀속 차단
```

> **`attribution.link()` 호출이 빠져도 에러가 나지 않습니다.** 귀속률만 조용히 낮아집니다.

## 4-2. 자동검수 엔진

**"자동 승인해도 되는가"가 아니라 "사람이 봐야 할 이유가 있는가"** 를 묻습니다.

개입 사유 7종 — `UNVERIFIED_BUSINESS` · `FIRST_LISTING` · `HIGH_FEE` · `PRIOR_REJECT` · `GATED_CATEGORY` · `THIN_CONTENT` · `BANNED_WORD_WARN`

전부 `auto_review_policies` 에서 배포 없이 켜고 끕니다. **표본 감사 5%** — 없으면 오판을 영원히 모릅니다.

## 4-3. 금칙어 55종

| 등급 | 처리 | 예 |
|---|---|---|
| **BLOCK** (32) | 등록 거부 | 원금보장 · 사채 · 다단계 · 소송대리 |
| **WARN** (21) | 통과 + 사람이 봄 | 최고 · 카톡 · 직거래 · 전화번호 패턴 |

**WARN을 차단하지 않은 게 판단입니다.** "최고 사양 설비"는 정상이고, 문맥에 따라 다를 수 있는 것은 사람에게 보냅니다.

## 4-4. 노출·랭킹 엔진

`promoted` 와 `organic` 을 **분리 반환**합니다. 하나로 섞으면 프런트가 라벨을 빠뜨릴 수 있고 그게 곧 표시 의무 위반입니다.

## 4-5. 정산 엔진 — 되돌릴 수 없는 유일한 처리

### ★ 원장 3단계 재대조

```
1단계  settlements 합계        지급하려는 금액
2단계  deals.agreed_fee 합계   당사자가 합의한 금액 (INV-9)
3단계  fn_verify_invariants()  스키마 수준 위반
```

**배치 생성 시와 이체 직전에 각각** 돌립니다. 실측 — 금액을 3,000,000 → 2,700,000으로 조작하니 잡혔습니다.

```
!! 금액 불일치: 정산 2700000 vs 합의 3000000 — INV-9 위반
→ RECONCILE_FAILED, 배치를 만들지 않았습니다
```

**중복 지급 방어 3중** — `run_date UNIQUE` · 멱등키 · `ALREADY_EXECUTED`.

# 5. 애플리케이션

## 5-1. 계층

```
src/
  core/       컨텍스트 · 오류 · 인증 · 페이지네이션 · 감사 · PII감사 · 멱등성
  db/         풀 · 트랜잭션 경계
  engines/    attribution · exposure · review
  modules/    identity · catalog · listing · request · deal · review · me
              · public · billing · settlement · admin · site
  worker/     배치 8종
```

의존 방향은 `modules → engines → db → core` 한쪽입니다.

## 5-2. 트랜잭션 — 인자로 넘기지 않습니다

```
옛 구현(단일 커넥션 공유): A 유실 — B의 ROLLBACK에 휘말림
현재:                      A는 커밋 · B만 롤백
```

`tx` 인자를 없앤 이유는 **한 곳만 빠뜨려도 트랜잭션 밖에서 돌고 컴파일도 테스트도 통과하기** 때문입니다.

## 5-3. 오류 규약

| 상태 | 의미 | 프런트 |
|---|---|---|
| 400 | 형식 오류 | 입력 고치기 |
| 403 | 권한·게이트 | 인증·전환 유도 |
| **409** | 상태 충돌 | **재시도 무의미** |
| **422** | 정책 위반 | **message 를 그대로 표시** |

## 5-4. 인증 — 토큰을 믿지 않습니다

principal 을 클레임이 아니라 **DB에서 다시 조립**합니다. 구독 만료·사업자 승인이 15분 뒤에 반영되면 안 됩니다.

## 5-5. 컨트롤러 데코레이터

```ts
@Roles  @RequireGate  @Audit  @PiiAccess  @ApiOperation  @ApiResponse(422)
```

하나라도 빠지면 권한이 뚫리거나, 감사 기록이 없거나, 프런트가 스키마를 못 받습니다.

## 6-2. 약관도 생성합니다

`scripts/gen-terms-draft.js` 가 **요금제·불변식·연동 현황을 DB에서 읽어** 씁니다.

```
· 베이직 — 월 무료 · 소개코드 0건 · 노출 슬롯 3건
· 스탠다드 — 월 49,000원 · 소개코드 3건 · ...
```

**"월 49,000원"을 손으로 쓰면 요금이 바뀔 때 약관이 거짓말이 됩니다.**

수탁자 표도 `integrations.provider` 에서 나오므로, PG사를 정해 입력하면 개인정보처리방침에 자동 반영됩니다.

## 6-3. 발행은 막혀 있습니다

```
!! SERVICE — 미확정 표시 4곳
〔 〕로 표시된 부분이 남아 있습니다. 법무 확인 후 채우십시오.
그대로 발행하면 이용자에게 그 표시가 그대로 보입니다.
```

내용·시행일 없이 발행할 수 없고, 시행일을 과거로 넣을 수도 없습니다 — **동의 이력의 기준이 되는 날짜**이기 때문입니다.

## 6-4. 관을 열 때의 전제

```
NO_FORM_COPY: 등록 폼 문구가 없어 관을 열 수 없습니다.
NO_APPROVED_CATEGORY: 승인된 업종이 없어 관을 열 수 없습니다.
```

**앱에도 같은 검사가 있었으나 SQL 로 직접 열면 통과했습니다.** DB로 옮겼습니다.

# 7. 외부 연동

| 연동 | 리드타임 | 오픈 차단 | 없으면 |
|---|---:|:-:|---|
| **NTS** 사업자 진위 | 2주 | | 항상 "유효" |
| **1원 계좌인증** | 4주 | **●** | 정산 계좌 검증 불가 |
| **PG** 전자결제 | 5주 | **●** | **매출 발생 불가** |
| **PASS** 본인인증 | 6주 | **●** | 게이트 무력 |
| **알림톡·SMS** | **8주** | | 인앱·메일만 |
| 050 안심번호 | 미정 | | 통화가 귀속 밖 |

**6종 전부 발신 IP 화이트리스트를 요구하고 심사에 2~4주 걸립니다.** 관리자 화면에서 IP를 한 번 넣으면 일괄 반영됩니다.

**시크릿은 DB에 넣지 않습니다** — Secrets Manager 키 이름과 등록 여부만 기록합니다.

**`stub: true` 를 응답에 싣습니다** — 화면이 "연동 준비 중"을 표시합니다.

> **PG에 소개비를 태우지 마십시오.** 자금 수탁이 되어 INV-11이 깨집니다.
