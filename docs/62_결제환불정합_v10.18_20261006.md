| # | 장면 | 고치기 전 | 돈 · 회원에게 생기는 일 |
|---|---|---|---|
| 1 | 정기결제가 한 번 거절된 뒤 재시도에서 승인 | 배치가 `409 DUPLICATE` · 청구서는 실패 그대로 | **결제는 됐는데** 구독은 「결제 실패」. 다음 배치는 같은 주문번호라 결제사가 거절 → 유예 뒤 만료 |

| 5 | 승인 뒤 우리 DB 저장 실패 → 같은 결제로 다시 요청 | 「이미 처리된 결제」를 결제 실패로 돌려줌 | **돈은 나갔는데** 구독 · 코드가 영영 안 열림 |

| 7 | 해지 예약한 회원이 다시 결제 | 승인 뒤 `422 BILLING_RULE` 로 전체 되돌림 | **돈만 나감** |
| 8 | 만료된 카드 | 같은 날 다시 청구(하루 10번까지) | 카드사 이상거래 탐지 · 가맹점 제재 위험 |

| 10 | 정기결제 실패가 생긴 날의 배치 | 운영 알림을 넣다 `422 CHECK_VIOLATION` — 작업이 실패로 기록 | **운영이 결제 실패를 알림으로 받지 못함** |

## 2. 바꾼 것 — 설계안 4건

### ① 정기결제 — 한 기간은 청구서 한 줄, 결과를 모르면 모른다고 적는다

```
대상(v_billing_due) → [구독 줄 잠금 · 지금도 대상인지 다시 확인] → 청구서 PENDING(주문번호 · 잡은 시각) → 커밋
        → 결제사 청구(멱등 키) ─┬─ 승인            → 청구서 PAID(결제 키) + 기간 연장(한 번만)      ← 한 트랜잭션
                               ├─ 거절(확정)       → 청구서 FAILED · 구독 「결제 실패」(유예)       ← 다음 시도는 새 주문번호
                               ├─ 우리 쪽 문제     → 청구서 FAILED 만 · 구독 · 회원 안내는 그대로 · 배치 중단 · 운영 알림
                               └─ 불명확           → 청구서 PENDING 그대로(새 결제 금지)
                                                     └ 주문번호로 결제사 조회(곧바로 1번 + 배치마다)
                                                         승인 · 금액 같음 → PAID      금액 다름 → 그대로 두고 사람이 확인
                                                         「그런 주문 없음」을 30분 뒤에도 → FAILED 로 닫고 새 주문번호로 다시
                                                         조회 실패 → 아무것도 확정하지 않음
```

- **실패했던 그 줄을 다시 잡습니다.** 새 줄을 만들지 않으므로 유일 제약에 걸리지 않고, 시도 횟수(`attempt`)가 그 줄에 쌓입니다.
- **주문번호는 시도마다 새로** `sub_<구독 id>_<기간 시작(ms)>_a<시도>` (64자 이내). 결제사의 결제 키는 `payment_key`, 우리 주문번호는 `order_id` 에 따로 둡니다.
- **불명확 = 응답 지연(10초) · 연결 끊김 · 5xx · 「이미 처리된 주문」 · 금액이 다르게 승인.** 실패로 적지 않습니다.
- **서버가 2대여도 · 배치가 겹쳐도** 한 번만 나갑니다 — 구독 줄 잠금 아래에서 청구서를 PENDING 으로 만든 쪽만 결제사를 부릅니다.
- **거절의 종류는 결제사 코드로** 가릅니다(전에는 문구의 낱말). 카드를 바꿔야 하는 11종은 하루 1회, 우리 쪽 연동 오류 6종은 회원을 건드리지 않습니다.

### ② 환불 — 결제사가 취소를 확인한 뒤에만 「환불 완료」

```
POST /me/subscription/refund
  [구독 줄 잠금] 진행 중인 환불 요청이 있으면 그것을 이어서 처리(새로 접수하지 않음)
  없으면 → 자격 판단(결제 당일 · 미이용 — DB) → 환불 요청 REQUESTED (자격 근거 · 결제사 멱등 키 저장) → 커밋
  → PROCESSING(커밋) → [전에 보낸 적 있으면 먼저 조회] → 결제사 취소(저장된 결제 키 · 금액 · 사유 · 멱등 키)
      ─┬─ 취소 확인   → 환불 요청 SUCCEEDED + 청구서 REFUNDED + 구독 CANCELLED   ← 한 트랜잭션   → 201 「환불 완료」
       ├─ 거절(확정)  → 환불 요청 FAILED(사유) · 구독 · 청구서 그대로                            → 422 REFUND_FAILED 「환불 실패」
       └─ 불명확      → 곧바로 조회 → 취소됐으면 완료 / 아니면 UNKNOWN                           → 202 「환불 결과 확인 중」
                         └ 다시 요청하거나 배치가 돌 때: 먼저 조회 → 취소됐으면 닫고, 아니면 같은 멱등 키로 다시 취소
```

- **「접수되었습니다」라는 답이 없습니다.** 회원이 보는 말은 셋뿐입니다 — 환불 완료 · 환불 결과 확인 중 · 환불 실패.
- **자격은 접수할 때만** 봅니다(그때의 결제일 · 이용 수를 요청에 적어 둡니다). 당일 접수한 환불이 자정을 넘겨 끝나도 저장됩니다.
- **환불 처리 중에는** 그 구독의 유료 이용(열람 · 소개코드) · 갱신 청구 · 요금제 변경을 DB 가 막습니다.
- **같은 환불을 여러 번 눌러도** 결제사 취소는 한 번입니다(청구서당 살아 있는 요청 1건 · 요청마다 고유한 멱등 키 `sub-refund-<요청 id>`).
- **결과는 알림으로도** 갑니다(환불 완료 · 환불 실패) — 「확인 중」 답을 받은 회원이 화면을 다시 열지 않아도 알 수 있게.

### ③ 같은 요청은 한 번만 — 작업 전에 선점

| 상황 | 응답 |
|---|---|
| 같은 키 · 같은 내용 — 앞 요청이 끝남 | 저장된 응답 그대로(같은 HTTP 상태) |
| 같은 키 · 같은 내용 — 앞 요청이 처리 중 | `409 REQUEST_IN_PROGRESS` |
| 같은 키 · **다른 내용** | `409 IDEMPOTENCY_KEY_REUSED` |
| 앞 요청이 확정 실패(결제 거절 등 — 돈이 움직이지 않음) | 다시 실행 |
| 앞 요청이 **결과 불명확**(결제를 보냈는데 끝을 못 봄 · 처리하다 서버가 죽음) | 다시 실행하되 **결제사에 먼저 조회**해 이미 승인된 결제는 다시 받지 않음 |

- 기록(`idempotency_records`)에 사용자 · 작업 경로 · 요청 키 · 본문 해시 · 상태(`PROCESSING` · `SUCCEEDED` · `FAILED` · `UNKNOWN`) · HTTP 상태 · 시작/완료 시각을 둡니다.
- 「처리 중」은 **시간이 아니라 DB 잠금**으로 압니다 — 처리하던 서버가 죽으면 잠금이 풀려 다음 요청이 이어받습니다(오래됐다고 함부로 다시 실행하지 않습니다).
- 결과 기록은 **업무 자료와 같은 트랜잭션**에 넣습니다. 실패해도 키를 지우지 않습니다.
- 적용 대상은 지금처럼 구독 시작 · 소개코드 발급입니다. 고치기 전에 쌓인 기록(옛 형식)은 그대로 응답합니다.

### ④ 해지 — 결제 실패 상태에서도, 청구와 순서가 섞이지 않게

- `ACTIVE` · `PAST_DUE` 모두 해지됩니다. 이미 해지한 구독이면 오류가 아니라 그때의 결과(`alreadyCancelled: true`).
- 해지와 「청구 잡기」는 **같은 구독 줄을 잠급니다.** 해지가 먼저 끝나면 배치는 대상을 읽은 뒤라도 청구를 보내지 않습니다. DB 트리거도 해지한 구독의 청구 잡기를 막습니다(API 를 거치지 않는 길 포함).
- 해지보다 먼저 잡혀 이미 결제사로 나간 청구는 되돌릴 수 없습니다 — 응답에 `chargeInFlight: true` 와 안내를 냅니다(승인되면 한 기간 연장 · 그 뒤로는 청구 없음 · 원하지 않으면 당일 환불).
- 해지한 「결제 실패」 구독은 유예 기간이 지나면 배치가 만료로 닫습니다(청구는 하지 않습니다).

## 3. 고친 것 전체 (결함표 G-96 ~ G-113)

| 번호 | 무엇이 | 어떻게 고쳤나 |
|---|---|---|
| G-96 · 상 | 정기결제 재시도가 승인되면 결제는 됐는데 실패로 끝남 — 구독은 「결제 실패」 그대로 | 한 기간 = 청구서 한 줄: 실패했던 줄을 다시 잡아(PENDING) 결제 완료로 바꿈 · 시도마다 새 주문번호(sub_<구독>_<기간>_a<시도>) · 결제사 결제 키(payment_key)와 우리 주문번호(order_id)를 따로 저장 · 기간 연장은 한 번만(구독의 기간 끝 = 청구서의 기간 시작일 때) |
| G-97 · 상 | 결제사 답을 받지 못한 청구(응답 지연 · 연결 끊김 · 5xx · 승인 직후 서버 종료)를 실패로 적고 다시 청구할 수 있었음 — 이중 청구 · 「돈은 나갔는데 기록 없음」 | 셋으로 가름(승인 · 확정 거절 · 불명확). 먼저 청구서를 PENDING 으로 잡고 커밋한 뒤 결제사 호출 · 불명확이면 PENDING 유지(새 결제 금지) · 주문번호로 결제사에 조회(곧바로 한 번 + 배치마다)해 승인됐으면 PAID · 「그런 주문 없음」을 30분 뒤에도 받으면 그때 닫고 새 주문번호로 · 결제사 멱등 키 전송 |

## 9. 남은 것 — 결제사 테스트 환경 검증 (★ 완료 판정 전 필수)

**왜 필요한가.** 이번 검증의 결제사 자리는 제가 만든 서버입니다. 토스 문서(맨 아래 근거)의 주소 · 응답 모양 · 에러 코드 이름을 따랐지만, **문서와 실제 응답이 다른 곳이 있으면 이번 검증으로는 드러나지 않습니다.** 특히 ① 에러 코드 이름(거절 / 불명확을 가르는 기준) ② 같은 멱등 키를 다시 보냈을 때의 실제 응답 ③ 주문번호 조회(`GET /v1/payments/orders/{orderId}`)가 자동결제 승인 건에도 답하는지 — 이 셋은 결제사에서만 확인됩니다.

### 순서

1. 킷 폴더의 `.env` 에 `TOSS_SECRET_KEY=test_sk_…` 를 넣고 `docker compose up -d api` (`TOSS_API_BASE` 는 비워 둡니다 — 기본이 토스 주소). 비워 두면 다시 열쇠 없는 방식(스텁)입니다.
2. 결제창으로 테스트 카드를 등록(빌링키) · 첫 결제를 합니다.
3. 아래 표를 위에서부터 합니다. 각 줄에서 **결제사 관리자 화면(테스트)의 결제 내역**과 운영 「청구 현황」 · DB 를 나란히 봅니다.

### 확인표

| # | 장면 | 만드는 방법 | 기대 |
|---|---|---|---|
| T-1 | 정기결제 정상 | 구독의 기간 끝을 과거로 옮기고 「지금 청구 실행」 | 결제사 승인 1건 · 청구서 PAID · `payment_key` = 결제사의 결제 키 · `order_id` = 우리 주문번호 |
| T-2 | 거절 뒤 재시도 승인 | 토스 테스트 카드 중 거절되는 카드 → 정상 카드로 교체 후 다시 실행 | 청구서 1줄 · PAID · 시도 2 · 주문번호가 시도마다 다름 |
| T-3 | **응답 유실** | 청구 실행 직후 API 서버와 결제사 사이 통신을 끊음(방화벽 규칙 · 또는 `TOSS_API_BASE` 를 응답을 버리는 중계 서버로) | 청구서 PENDING → 통신 복구 뒤 배치 → 조회로 PAID · 결제사 승인 1건뿐 |
| T-4 | **승인 직후 서버 종료** | 청구 실행 중 API 프로세스를 강제 종료(`docker compose kill api`) | 다시 띄운 뒤 배치 → 조회로 PAID · 승인 1건뿐 |
| T-5 | 같은 멱등 키 재전송 | T-3 상태에서 같은 주문을 손으로 다시 보냄 | 결제사가 **같은 응답**을 돌려주는지 · 처리 중이면 `409 IDEMPOTENT_REQUEST_PROCESSING` 인지 |
| T-6 | 환불 정상 | 당일 결제 · 미이용 구독에서 환불 신청 | 결제사 취소 1건 · 「환불 완료」 · 청구서 REFUNDED |
| T-7 | **환불 완료 직전 DB 장애** | 환불 신청과 동시에 DB 를 잠깐 내림(`docker compose stop db` → 취소 응답 뒤 `start`) | 응답은 「환불 완료」가 아님 → DB 복구 뒤 「환불 결과 다시 확인」 → 조회로 「환불 완료」 · 결제사 취소 1건뿐 |
| T-8 | 환불 거절 | 이미 결제사에서 취소한 결제 · 취소할 수 없는 결제로 환불 신청 | `ALREADY_CANCELED_PAYMENT` → 조회로 완료 처리 / `NOT_CANCELABLE_PAYMENT` → 「환불 실패」 |
| T-9 | 에러 코드 이름 | T-2 · T-8 에서 실제로 온 `code` 값을 기록 | `recurring.service.ts` 의 `CARD_UNUSABLE` · `INTEGRATION` · `payment.provider.ts` 의 `uncertainHttp` 목록과 대조 — 다르면 목록을 고칩니다 |
| T-10 | 틀린 시크릿 키 | 키 끝 글자를 바꿔 「지금 청구 실행」 | 배치 중단(`HALTED`) · 회원 상태 변화 없음 · 운영 알림 |

결과를 알려 주시면(실제 `code` 값 · 다른 점) 목록을 맞추고 완료 판정용 보고서를 드립니다.

## 11. 한계 · 알아 둘 것

1. **결제사 테스트 환경 미검증**(9절).
2. 결제사 멱등 키는 15일간 유효합니다(토스 문서). 15일 넘게 「확인 중」으로 남은 환불을 다시 보내면 결제사는 새 요청으로 봅니다 — 이미 취소된 결제라면 `ALREADY_CANCELED_PAYMENT` 가 오고, 조회로 완료 처리합니다(그래서 다시 보내기 전에 늘 먼저 조회합니다).
3. 「결제사에 그런 주문 없음」을 30분 뒤에 믿는 것은 가정입니다 — 결제사가 30분 넘게 지나 승인하는 일은 없다고 봤습니다. 9절 T-3 에서 실제 동작을 보십시오.
4. 금액이 다르게 승인된 청구 · 승인됐는데 기간에 반영하지 못한 청구는 자동으로 닫지 않습니다(8절). 닫는 운영 화면 버튼은 아직 없습니다.
5. 환불은 **전액 · 이번 기간 1건**입니다. 부분 환불 · 지난 기간 환불은 없습니다(기존 정책 그대로: 결제 당일 · 미이용).
6. 환불하면 그 구독은 끝납니다(`CANCELLED`) — 받지 않은 소개코드는 기존 규칙대로 실효됩니다.
7. 해지만 하고 기간이 끝난 구독(`ACTIVE` + 해지)은 상태값이 그대로 남습니다 — 이용 권한은 기간으로 막히므로 동작에는 문제가 없습니다(기존 그대로). 만료로 바꾸는 것은 이번 범위가 아닙니다.
8. 이메일 · 문자 발송은 기존대로 연동 전입니다 — 환불 결과는 앱 안 알림으로만 갑니다.
9. **운영 서버는 결제사 열쇠 없이(스텁 방식으로) 띄우면 안 됩니다**(기존과 같음 — 스텁은 모든 결제를 승인으로 답합니다). 이번 판은 그런 실수가 있어도 스텁 방식의 서버가 **실제 결제로 생긴 확인 중 청구 · 환불을 닫지 못하게**만 막았습니다(G-112). 스텁 방식에서 새로 일어나는 청구가 가짜 승인이 되는 것은 그대로입니다.
10. Windows PowerShell 5.1 · ISE 에서의 `dev.ps1` 은 v10.17 과 같습니다(PC 에서 한 번 확인 필요 — docs/61).
