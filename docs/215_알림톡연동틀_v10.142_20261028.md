## 1. 결론

| 항목 | 내용 |
|---|---|
| 방식(`alimtalk.provider`) | **NONE**(처음 · 보내지 않음) · **MOCK**(점검판 — 보내지 않고 기록만 · 운영 서버에서는 못 고름) · **HTTP**(키 2개 + `ALIMTALK_URL` 이 있어야 고름) — 바꾸기 SUPER |
| 켜기 | 기존 스위치 **`notify.alimtalk_ready`** = 「알림톡 켜기」 — 방식 · 키가 갖춰지고 **승인된 템플릿이 하나는 있어야** 켜짐(아니면 422 `ALIMTALK_NOT_READY`) |
| 템플릿 4개 | 상담 인증번호 · AI 상담 넘김 알림(운영자 · 템플릿만 — 붙이는 곳은 운영자 번호를 정한 뒤) · 주문 · 반품 상태 · 알림 일반. 본문은 `alimtalk.templates.ts` 가 기준 — 대행사에 **그대로** 등록 · 대행사 코드 · 심의 상태는 운영 화면에서 · **승인된 것만 회원에게** |
| 붙는 곳 | ① 상담 신청 인증번호 — 알림톡이 준비되면 휴대폰으로(메일도 켜져 있으면 둘 다) ② 알림 발송 SMS 채널 — 대기(QUEUED)를 1분마다 「알림 일반」으로 · 3번 재시도 |
| 기록 | `alimtalk_sends` — 목적 · 템플릿 · **받는 번호 끝 4자리만** · 결과 · 대행사 번호 · 까닭(120자) |
| 운영 화면 | 외부 연동 › **「알림톡」**(다섯 줄 · 방식 단추 · 켜기 · 템플릿 표 · 시험 발송 하루 20 · 보낸 기록) · 「연동 키」에 발신 프로필 키 |

## 2. 오류 처리

| 경우 | 결과 |
|---|---|
| 방식 NONE · 키 · 주소 없음 | 보내지 않음 · `NOT_READY` 기록 |
| 휴대폰 번호 형식 아님 | 보내지 않음 · `BAD_PHONE` |
| 대행사 코드 없음 · 심의 승인 전(시험 발송은 심의 중이어도 코드가 있으면 보냄) | 보내지 않음 · `TEMPLATE` |
| 연결 실패 · 시간 초과(8초) · 대행사 5xx | `NETWORK` · `TIMEOUT` · `SERVER` — 알림은 **다시 시도**(3번째 실패에서 FAILED) |
| 401 · 403 | `AUTH`(키 확인) — 다시 하지 않음 |
| 그 밖 4xx | `REJECTED` — 다시 하지 않음 |
| 상담 인증번호 — 알림톡 실패 · 메일 성공 | 메일로 안내(접수 그대로) |
| 상담 인증번호 — 알림톡 실패 · 메일 없음 | 신청을 지우고 422 `OTP_SEND_FAILED` |
| 알림 문자 — 번호 없음 · 쓰지 않는 계정 · 회원이 문자를 끔 · 3일 지남 | 보내지 않고 FAILED(까닭) |
| 배치에서 알림톡 쪽 예외 | 기록만 남기고 메일 · 다른 일은 계속 |
| 운영 화면 — 시험 한도 · 번호 형식 · 템플릿 코드 형식 · 코드 없이 승인 | 422 `ALIMTALK_TEST_LIMIT` · `PHONE_INVALID` · `TEMPLATE_CODE_FORMAT` · `TEMPLATE_CODE_REQUIRED` |

## 3. 대행사가 정해진 뒤

1. 대행사 계약 · 카카오 채널 · 발신 프로필 · 발신 IP 3.37.95.217(자동화 EC2 에서 보내면 그 IP 도)
2. 운영 화면 › 「알림톡」 템플릿 글 4개를 **그대로** 대행사에 심의 신청 → 받은 템플릿 코드 · 「심의 중」
3. 운영 `.env` 에 `ALIMTALK_URL`(필요하면 `ALIMTALK_AUTH_HEADER` · `ALIMTALK_AUTH_PREFIX` · `ALIMTALK_RESULT_ID_PATH`) · 연동 키에 API 키 · 발신 프로필 키 → 방식 HTTP
4. 대행사 안내서와 `alimtalk.service.ts` 의 `http()` 본문 칸 대조 — 다르면 그 부분만 고침
5. 시험 발송(대표 휴대폰) → 심의 승인 → 「승인」 → 「알림톡 켜기」
