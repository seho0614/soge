# 소개뱅크 — 연동 설계서 v1

**작성일** 2026-09-03
**범위** 외부 시스템 6종 · 어댑터 계약 · 스텁 정책 · 장애 대응
**현황** 전건 미착수 (스텁 동작 중)

---

## 0. 이 문서가 다루는 것

외부에 의존하는 지점은 **우리가 통제할 수 없는 유일한 부분**입니다. 여기서 세 가지를 정합니다.

1. 계약이 언제 필요한가 — 리드타임이 개발보다 깁니다
2. 붙기 전까지 무엇으로 대신하는가 — 스텁이 실동작처럼 보이면 안 됩니다
3. 붙은 뒤 죽으면 어떻게 되는가 — 외부가 죽어도 우리가 죽으면 안 됩니다

## 1. 연동 6종

| # | 연동 | 용도 | 리드타임 | IP 등록 | 미연동 시 |
|---|---|---|---|:-:|---|
| 1 | **PASS** | 본인인증 (INV-7 게이트) | 4~6주 | 필요 | 스텁 통과 — 게이트 무력 |
| 2 | **NTS** | 사업자 진위 확인 | **1~2주** | 필요 | 항상 "유효" 반환 |
| 3 | **알림톡·SMS** | 거래 알림 · 서명 요청 | 4~8주 | 필요 | 인앱·메일만 발송 |
| 4 | **PG** | 구독료 · 초과 코드 결제 | 3~5주 | 필요 | **매출 발생 불가** |
| 5 | **1원 계좌인증** | 정산 계좌 검증 | 3~4주 | 필요 | 등록 즉시 인증 처리 |
| 6 | **050 안심번호** | 통화 귀속 (B-19) | 미정 | 필요 | 통화가 귀속 밖 |

### ★ 공통 선행 — 발신 IP 등록

**6종 중 5종이 IP 화이트리스트를 요구하고 심사에 2~4주 걸립니다.**

```
W2   NAT Gateway EIP 고정
     → 각 사업자에 발신 IP 등록 신청
W6   심사 완료 → 연동 착수 가능
```

**코드보다 IP가 먼저 필요합니다.** 이걸 놓치면 개발이 끝나도 붙일 수 없습니다.

### 착수 우선순위

| 순서 | 연동 | 이유 |
|---|---|---|
| 1 | **NTS** | 리드타임 1~2주로 가장 짧고, **코드 수정 없이 키 주입만으로 전환**됩니다. 사업자 승인 자동화의 전제이기도 합니다 |
| 2 | PG | 매출이 여기 걸려 있습니다 |
| 3 | PASS | INV-7 게이트 |
| 4 | 1원 계좌인증 | 정산(T8) 시점에 필요 |
| 5 | 알림톡 | 3관에서는 거래 알림용. 임계 경로 아님 |
| 6 | 050 | B-19 결정 후 |

## 2. 어댑터 계약

교체 지점을 인터페이스로 고정합니다. **스텁과 실연동이 같은 타입을 만족해야** 코드 수정 없이 바뀝니다.

```ts
abstract class IdentityProvider {
  abstract verify(input: { name: string; phone: string }): Promise<IdentityResult>;
}
abstract class BizStatusProvider {
  abstract check(bizRegNo: string): Promise<BizStatusResult>;
}

interface IdentityResult  { success: boolean; ciHash?: string; stub: boolean }
interface BizStatusResult { status: 'VALID'|'CLOSED'|'SUSPENDED'|'UNKNOWN'; stub: boolean }
```

### `stub: true` 를 응답에 싣습니다

구 모델에서 **"클릭 즉시 통과"가 실동작처럼 보인 것**이 시연 리스크로 지목됐습니다. 같은 실수를 막으려면 **데이터에 표시가 있어야** 합니다.

화면은 `stub: true` 를 받으면 "연동 준비 중 — 실제 확인이 이루어지지 않았습니다"를 표시합니다. **숨기지 않습니다.**

### 해석기

```ts
function resolveBizStatusProvider(): BizStatusProvider {
  const key = process.env.NTS_SERVICE_KEY;
  return key ? new NtsBizStatusProvider(key) : new StubBizStatusProvider();
}
```

**키가 주입되면 자동으로 실연동으로 바뀝니다.** 배포도 코드 수정도 필요 없습니다(T-07).

## 3. 연동별 설계

### 3-1. NTS — 사업자 진위

| | |
|---|---|
| 제공 | 공공데이터포털 국세청 사업자등록 상태조회 |
| 인증 | 서비스키 (`NTS_SERVICE_KEY`) |
| 호출 시점 | 사업자 신청 시 1회 · 이후 월 1회 재확인 |
| 저장 | `businesses.nts_status` · `nts_checked_at` |
| 실패 | `UNKNOWN` 저장 후 **수동 검수로 넘김.** 신청을 막지 않습니다 |

**연동되면 사업자 승인이 자동화 후보가 됩니다.** 국세청이 판정해 주므로 사람이 더 볼 것이 많지 않고, 자동검수의 `UNVERIFIED_BUSINESS` 개입 사유도 줄어듭니다.

### 3-2. PASS — 본인인증

| | |
|---|---|
| 저장 | `identity_verifications` · CI 는 **해시만** (`ci_hash`). 원문 저장 금지 |
| 게이트 | `@RequireGate('IDENTITY_VERIFIED')` — INV-7 |
| 재인증 | 계좌 변경 · 정산 지급 시 |
| 실패 | 게이트 통과 불가. 사용자에게 재시도 안내 |

**CI 원문을 저장하지 않는 것이 핵심입니다.** 유출 시 피해 범위가 달라집니다.

### 3-3. PG — 구독료 결제

| | |
|---|---|
| 용도 | **구독료 · 초과 코드 요금만.** 소개비는 흐르지 않습니다 (INV-9·11) |
| 저장 | `payment_transactions` (pg_provider · pg_tid UNIQUE) |
| 원장 | `ledger_entries` — `entry_type` 에 `REFERRAL_FEE` 가 **없습니다** |
| 멱등성 | `Idempotency-Key` 필수 · `payment_transactions.idempotency_key` UNIQUE |

**웹훅은 재전송됩니다.**

```
1. 서명 검증
2. 멱등키 조회 → 있으면 저장된 응답 반환 (재처리 안 함)
3. 200 즉시 응답
4. 큐 적재 후 비동기 처리
```

**3번과 4번의 순서가 중요합니다.** 처리하고 응답하면 타임아웃 때 PG가 재전송하고, 그러면 중복 결제로 보입니다.

> **PG에 소개비를 태우지 마십시오.** 그 순간 자금 수탁이 되고 INV-11이 깨집니다. 전자금융거래법 등록 문제로 번집니다.

### 3-4. 알림톡 · SMS

| | |
|---|---|
| 선행 | 계약 + **발신번호 사전등록** |
| 템플릿 | 사전 승인 필요. `notification_templates` 51건과 매핑 |
| 저장 | `notification_deliveries` (provider_msg_id · idempotency_key) |
| 조용한 시간 | **21:00~08:00 SMS·PUSH 발송 안 함.** 인앱·메일은 제한 없음 |
| 실패 | 인앱으로 폴백. 알림 실패가 본 처리를 막지 않습니다 |

**수신거부 불가 이벤트 19건**은 `notification_event_policies` 가 관리하고, 끄려는 시도를 DB가 막습니다.

```
NOTIFICATION_OPTOUT_FORBIDDEN: 정산 지급 완료는 수신거부할 수 없습니다.
```

### 3-5. 1원 계좌인증

| | |
|---|---|
| 시점 | 정산 계좌 등록 시 |
| 저장 | **저장하지 않습니다.** 플랫폼이 이체하지 않으므로 계좌를 보관할 이유가 없습니다(INV-11). 계좌 확인이 필요하면 당사자끼리 직접 주고받습니다 |
| 게이트 | 미인증 계좌로는 정산 지급 불가 |
| 실패 | 재시도 3회 제한. 초과 시 고객센터 |

### 3-6. 050 안심번호 (B-19 · 미결정)

| | |
|---|---|
| 목적 | **통화를 귀속 안으로** — INV-2 "위험" 판정의 유일한 해소 수단 |
| 스키마 | `safe_numbers` · `call_logs` **준비 완료** |
| 동작 | 통화 발생 → `fn_attribute_call()` → `attribution_events(channel='CALL')` |
| 미도입 시 | 상세 화면 CTA 배치가 유일한 방어 (문의 우선 · 전화 보조) |

## 4. 장애 대응

### 원칙 — 외부가 죽어도 우리는 삽니다

| 연동 | 죽으면 |
|---|---|
| NTS | `UNKNOWN` 저장 → 수동 검수. **신청은 받습니다** |
| PASS | 게이트 통과 불가. 탐색·등록은 계속 |
| PG | 구독 결제 실패 → `PAST_DUE`. **기존 구독은 유지**(즉시 해지 아님) |
| 알림톡 | 인앱 폴백. 발송 실패를 `notification_deliveries` 에 기록 |
| 1원 인증 | 계좌 등록 대기. 정산 신청까지는 가능 |

**공통** — 외부 호출은 **타임아웃 5초 · 재시도 2회 · 지수 백오프**. 서킷 브레이커는 연속 실패 10회에서 60초 개방.

### 절대 하지 않는 것

| 금지 | 이유 |
|---|---|
| 외부 응답을 기다리며 트랜잭션 유지 | 커넥션 풀이 마릅니다 |
| 결제 실패 자동 재시도 | 중복 결제 위험 |
| **정산 이체 자동 재시도** | 원인을 모르는 상태에서 다시 쏘는 것이 가장 위험합니다 |
| 알림 실패로 본 처리 롤백 | 성사됐는데 알림이 안 갔다고 성사를 취소할 수는 없습니다 |

## 5. 시크릿 관리

| 키 | 저장 | 주입 |
|---|---|---|
| `NTS_SERVICE_KEY` · `PG_*` · `PASS_*` · `ALIMTALK_*` | **AWS Secrets Manager** | ECS 태스크 정의 |
| `JWT_SECRET` | Secrets Manager | 부팅 시 검증 — **운영은 32자 이상** |
| `DATABASE_URL` | Secrets Manager | |

**코드·환경파일·저장소에 두지 않습니다.** 부팅 시 필수 키를 검증하고, 없으면 **프로세스가 뜨지 않습니다** — ECS 헬스체크가 롤아웃을 막습니다.

## 6. 연동 완료 판정

각 연동은 아래를 만족해야 "완료"입니다.

| # | 조건 |
|---|---|
| 1 | 실 계정으로 성공 경로 1회 |
| 2 | 실패 경로 1회 (잘못된 값 → 우리 시스템이 죽지 않음) |
| 3 | 타임아웃 시나리오 (외부 무응답 → 5초 후 폴백) |
| 4 | 멱등성 (같은 요청 2회 → 부작용 1회) |
| 5 | `stub: false` 로 응답 · 화면에서 스텁 표시 사라짐 |
| 6 | stg 발신 IP로 호출 성공 |

**4번을 빠뜨리면 PG 웹훅 재전송에서 사고가 납니다.**

## 7. 일정

| 주차 | 작업 |
|---|---|
| **W2** | NAT EIP 고정 → **5종 발신 IP 등록 신청** · NTS 키 신청 |
| W3~W4 | NTS 실연동 (키 주입만) |
| W5~W6 | PG 계약 · 심사 |
| W6~W8 | PASS 계약 · 연동 |
| W8~W10 | PG 연동 · 웹훅 |
| W10~W12 | 1원 계좌인증 |
| W12~W14 | 알림톡 (템플릿 사전 승인 포함) |
| 미정 | 050 안심번호 — B-19 결정 후 |

**W2가 전부입니다.** 여기서 IP 등록을 시작하지 않으면 나머지 일정이 통째로 밀립니다.
