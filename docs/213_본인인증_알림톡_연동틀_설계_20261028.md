## 2. v10.141 — 본인인증 NICE 표준창 틀

### 2-1. 흐름

```
회원 /verify 「휴대폰 본인확인」
  → POST /verifications/identity/start        서버: 요청 번호(1회용 · 10분) 만들고 표준창에 넘길 값 돌려줌
  → 브라우저가 표준창을 엶(팝업 · 휴대폰은 새 창)   NICE 화면 — 통신사 · 이름 · 생년월일 · 문자 확인
  → NICE 가 돌려보냄  GET /verify/return?…      사용자 웹(돌아오는 주소)
  → POST /verifications/identity/complete      서버: 무결성 확인 → 복호화 → 요청 번호 · 시간 대조
                                                → CI 를 해시로만 저장 · identity_verified_at 기록
  → 「본인인증이 끝났습니다」 · ?next= 로 돌아감
```

### 2-2. 어댑터 3가지 (`identity.provider` 설정 · 처음 `STUB`)

| 값 | 동작 | 쓰는 곳 |
|---|---|---|
| `STUB`(처음 · 지금과 같음) | 지금 그대로 — 누르면 통과 · 「시험용」 표시 | 운영(계약 전) |
| `MOCK` | **우리 사이트 안의 가짜 표준창**(`/verify/mock-nice` · 이름 · 생년월일 넣으면 NICE 와 같은 모양으로 암호화해 돌려보냄) — 시작 · 돌아오기 · 복호화 · 대조 전체를 시험 | 점검판 · 시험 |
| `NICE` | 실제 표준창 — 키 3개(운영 화면 「연동 키」) | 계약 뒤 |

`NICE` 로 바꾸려면 키 3개가 모두 있어야 함(없으면 422 · 운영 화면이 빠진 키를 알려 줌). **바꾸기는 SUPER.**

### 2-3. NICE 쪽 (공개 자료 기준 — 계약 뒤 안내서로 확인)

| 단계 | 내용 |
|---|---|
| 기관 토큰 | 클라이언트 ID · 비밀값으로 접근 토큰 받기(유효 기간 길어 서버가 보관 · 만료 전 갱신) |
| 암호화 토큰 | 요청 시각 · 요청 번호로 암호화 토큰 요청 → 그 값들로 **대칭키 · IV · 무결성 키**를 만듦 |
| 요청 자료 | 요청 번호 · 돌아오는 주소 · 인증 방식(휴대폰)을 암호화(AES)하고 무결성 값(HMAC-SHA256)을 붙여 표준창에 넘김 |
| 돌아온 자료 | 무결성 값 확인 → 복호화 → 요청 번호 대조 → CI · DI · 이름 · 생년월일 · 성별 · 내외국인 |

이 부분은 `nice-identity.adapter.ts` 한 파일에 모아, 안내서와 다르면 그 파일만 고친다.

### 2-4. 저장 · 개인정보

| 무엇 | 저장 | 이유 |
|---|---|---|
| CI | **HMAC-SHA256(서버 비밀값) 해시만** `identity_verifications.ci_hash` | 소개코드 무료분 사람 단위 · 중복 가입 확인 — 원문 CI 는 저장 안 함 |
| DI | 저장 안 함 | 쓰는 곳 없음 |
| 이름 · 생년월일 · 성별 | 저장 안 함. 대신 **회원 이름과 다르면 표시만**(`name_match` true/false) · 만 14세 미만이면 실패(`UNDER_14`) | 최소 수집 |
| 요청 번호 · 시각 · 결과 · 실패 까닭 | `identity_verifications`(새 칸) | 다시 쓰기 막기 · 운영 확인 |
| 같은 CI 로 다른 계정 | **설정 `identity.ci_duplicate`**: `warn`(처음 · 통과하고 운영 화면에 표시) · `block`(막음) | P2P 다계정 정책은 대표 결정 — 처음은 막지 않음 |

### 2-5. 마이그레이션 D137(175)

- `identity_verifications` 에 칸 더함: `req_no`(유일) · `req_expires_at` · `adapter`(STUB · MOCK · NICE) · `name_match` · `fail_code` · **지우는 칸 없음**
- 연동 키 이름(`ck_integ_secret_name`) + `fn_integ_secret_set` 형식: `PASS · NICE_CLIENT_ID` · `PASS · NICE_CLIENT_SECRET` · `PASS · NICE_PRODUCT_ID`
- 설정: `identity.provider = STUB` · `identity.ci_duplicate = warn`
- 기존 `stub-ci` 기록은 그대로(계약 뒤 회원이 다시 인증하면 새 줄)

### 2-6. 화면 · API

| 곳 | 바뀌는 것 |
|---|---|
| 사용자 웹 `/verify` | `STUB` 이면 지금 그대로 · `MOCK` · `NICE` 면 「휴대폰 본인확인」이 표준창을 엶 · 돌아오면 결과 |
| 사용자 웹 `/verify/return`(새) · `/verify/mock-nice`(새 · MOCK 일 때만 열림) | 돌아오는 곳 · 가짜 표준창 |

## 3. v10.142 — 알림톡 틀

### 3-1. 모양

| 항목 | 내용 |
|---|---|
| 어댑터(`alimtalk.provider` · 처음 `NONE`) | `NONE`(지금과 같음) · `MOCK`(보내지 않고 기록만 — 점검판) · `HTTP`(대행사 공통 — 주소 · 머리글 · 칸 이름을 환경 변수 · 운영 화면으로, 은행 · 중개사 연동과 같은 방식) |
| 대행사 | **미정** — NHN Cloud · 인포뱅크 · 카카오 비즈메시지 등. 대행사가 정해지면 `HTTP` 칸만 채우거나 그 대행사 전용 파일 하나 |
| 실패하면 문자(SMS)로 | 대행사 기능(대체 발송)을 켜는 칸 — 대행사마다 달라 `HTTP` 에 맡김 |
| 키 | 운영 화면 「연동 키」: `ALIMTALK · ALIMTALK_KEY`(있음) + `ALIMTALK_SENDER_KEY`(발신 프로필 키 · 새) |
| 템플릿 | 코드 안 목록 4개 — 상담 인증번호 · 넘김 알림(운영자) · 주문 · 반품 상태 · 알림 일반. 운영 화면에서 **대행사 템플릿 코드 · 심의 상태(심의 전 · 승인)** 를 넣음 → **승인된 템플릿만 보냄** |

### 3-2. 붙는 곳

| 곳 | 바뀌는 것 |
|---|---|
| 상담 신청 인증번호 | 알림톡이 준비되면(키 · 승인 템플릿 · 스위치) 휴대폰으로 · 메일은 그대로 같이(지금 코드의 「둘 중 하나」 문장 그대로 씀) |
| 알림 발송(SMS 채널) | `v_notify_channels` 의 SMS 준비 = 알림톡 준비 → `QUEUED` 를 1분마다 보내고 `SENT` · `FAILED`(메일과 같은 재시도 3번) |
| 기록 | `notification_deliveries`(provider = 대행사 · 받는 번호는 저장 안 함 — 이미 그럼) · 상담 인증번호는 감사에 끝 4자리만 |
| 운영 화면 › 외부 연동 › 「알림톡」(새 구역) | 준비 상태(키 · 발신 프로필 · 템플릿 승인 수 · 스위치) · 템플릿 표 · **시험 발송**(SUPER · 하루 20 · 받는 번호는 가림) · 발송 기록 |

### 3-3. 마이그레이션 D138(176)

- `alimtalk_templates`(코드 · 이름 · 대행사 템플릿 코드 · 심의 상태 · 본문 미리보기 · 바꾼 사람 · 시각) — 4줄 넣음(대행사 코드 비어 있음 · 「심의 전」)
- 연동 키 이름 `ALIMTALK · ALIMTALK_SENDER_KEY`
- 설정: `alimtalk.provider = NONE` · `alimtalk.test_daily = 20`
- `v_notify_channels` 의 SMS 줄: 알림톡 준비 조건으로(지금은 늘 「안 됨」 — 꺼져 있으면 그대로)
