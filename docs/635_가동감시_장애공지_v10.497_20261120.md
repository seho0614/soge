# 635. 가동 감시 · 장애 공지 (v10.497 · 2026-11-20)

## 1. 결론
**바깥 감시는 자동화 서버의 n8n**(decisions/automation-server-n8n.md #9 · #17 「판단은 소개뱅크 서버, 전달은 n8n」)이 5분마다 사용자 웹 · 상태 주소 · 운영 화면을 불러 보고, 그 결과를 소개뱅크 서버에 보냅니다(`POST /site/uptime/report` · 토큰). 서버는 **대상별 연속 실패**를 세어 기준(`uptime.fail_count` · 처음 2번)을 넘으면 **긴급 운영 알림 UPTIME_DOWN**(기존 급한 알림 길 = 메일 · 텔레그램 · 슬랙)을 한 번 보내고, 다시 되면 UPTIME_RECOVERED. **서버가 아예 응답하지 않으면** 보고가 실패하므로 그때만 **n8n 이 텔레그램으로 직접** 알립니다.
운영자는 **위험감지 › 가동 · 장애 공지**(SB-ADM-UPT-010)에서 **장애 공지**를 쓰고(정도 · 영향 · 진행 글), 공지는 **사용자 웹 맨 위 띠**(모든 화면 · 점검 중 화면 위에도)와 **서비스 상태 화면 /status**(SB-HOM-UPT-010)에 나갑니다. 서버에는 **가벼운 공개 상태 주소 `GET /site/status`** 를 더했습니다(DB 한 번 · 15초 기억 · 개인정보 없음). **모두 처음 꺼짐**(결과 받기 `uptime.report` off · 토큰 없음).

| 설정 | 처음 | 뜻 |
|---|---|---|
| `uptime.report` | off | n8n 결과 받기(토큰을 먼저 만들어야 켤 수 있음 · SUPER) |
| `uptime.report_token_hash` | (빈 값 · PRIVATE) | 감시 토큰 지문(sha256) — 원문은 「토큰 새로 만들기」 응답에 한 번만 |
| `uptime.fail_count` | 2 | 연속 몇 번 실패면 내려감(1 ~ 10) |
| `uptime.keep_days` | 90 | 감시 결과 보관 날수(7 ~ 400 · 정기 작업 `upt_daily` 04:50) |

## 2. 전체 구조
```
[자동화 EC2 · n8n] ──5분──▶ https://sogaebank.com/ (SITE) · /api/v1/site/status (API) · https://admin.sogaebank.com/ (ADMIN · 403 도 응답함)
        │ 결과 3줄
        ▼
POST https://sogaebank.com/api/v1/site/uptime/report  (X-Uptime-Token)
        │ 실패(서버 죽음) ─────────────▶ n8n 이 텔레그램 직접(내려감 · 올라옴 때 한 번씩)
        ▼ 성공
[소개뱅크 API] upt_checks 쌓기 · upt_targets 연속 실패 → UPTIME_DOWN(CRITICAL) ─▶ 기존 급한 알림(메일 · 텔레그램 · 슬랙)
        ▲
[운영 화면] 위험감지 › 가동 · 장애 공지 — 장애 공지 · 진행 글 · 띠 · 점검 예약(D239 상자 그대로)
        ▼
[사용자 웹] 맨 위 장애 띠(IncidentBar · 60초) · /status(30초) · 점검 중 화면 위에도 띠
```

## 3. API
| 누가 | 방법 · 주소 | 뜻 |
|---|---|---|
| 누구나 | `GET /site/status` | status(ok · minor · major · maintenance · degraded) · db · version · maintenance · 끝나지 않은 공지 5 · 30일 끝난 공지 10 · 대상별 마지막 감시(30분 안) |
| n8n(토큰) | `POST /site/uptime/report` | `{ checks: [{ target, ok, status?, ms?, note? }] }` 1 ~ 10줄 · 403 UPTIME_REPORT_OFF · UPTIME_TOKEN_INVALID · 422 UPTIME_ITEMS · UPTIME_TARGET |
| ADMIN · SUPER | `GET /admin/uptime` | 설정 · 마지막 n8n 결과 · 대상별 상태 · 24시간 가동률 · 평균 ms · 공지 30(진행 글) |
| ADMIN · SUPER | `POST /admin/uptime/incidents` | 제목(2 ~ 120) · 영어 제목(선택) · 정도 MINOR · MAJOR · CRITICAL · 영향(SITE · API · LOGIN · PAY · MALL · MAIL · ADMIN) · 첫 안내 글 · 띠(처음 켬) · 운영 알림(선택) |
| ADMIN · SUPER | `PUT /admin/uptime/incidents/{id}` | 보낸 칸만(규칙 11) · 끝난 공지는 띠만(409 UPT_RESOLVED) |
| ADMIN · SUPER | `POST /admin/uptime/incidents/{id}/notes` | 진행 글(조사 중 → 원인 찾음 → 지켜보는 중 → 끝남) · 끝남이면 띠가 내려가고 UPT_INCIDENT(끝남 · WARN) |
| SUPER | `PUT /admin/uptime/settings` | 받기 · 연속 실패 수 · 보관 날수 · 사유(설정 바뀜 기록) |
| SUPER | `POST /admin/uptime/token` | 새 토큰 — 원문은 응답에 한 번만 · DB 는 지문 · 감사 UPT_TOKEN_ROTATE(원문 없이 서비스가 직접 남김 · @Audit 를 쓰지 않음) |

## 4. DB(D272 ①)
| 표 | 칸 · 규칙 |
|---|---|
| `upt_incidents` | 제목 · 영어 제목 · 정도 · 상태 · 영향(정해진 7개 안) · 띠 · 시작 · 끝(상태 RESOLVED ⇔ 끝 시각 있음 CHECK) · 끝난 공지는 띠 말고 고치지 못함 · 지우지 못함(`trg_upt_incident_guard`) |
| `upt_incident_notes` | 진행 글 · 쌓기만(고치기 · 지우기 막음 · 끝난 공지에 더하기 막음 `trg_upt_note_guard`) |
| `upt_checks` | n8n 결과(대상 · 성공 · 응답 코드 · ms · 짧은 글) · 개인정보 없음 · 보관 날수 뒤 지움 |
| `upt_targets` | 대상별 연속 실패 · 내려간 때(내려감 ⇔ 내려간 때 있음 CHECK) |

운영 알림 코드: `UPTIME_DOWN`(CRITICAL) · `UPTIME_RECOVERED`(INFO) · `UPT_INCIDENT`(새 공지 MAJOR · CRITICAL = CRITICAL · 그 밖 WARN). 운영 알림 화면 이름표 3개 더함(OpsAlerts.tsx).

## 5. 자동화 서버 n8n 넣는 순서(대표 승인 뒤 · 자동화 EC2)
1. 소개뱅크 운영 화면 › 위험감지 › 가동 · 장애 공지 › **「토큰 새로 만들기」**(SUPER · 사유) → 나온 토큰을 복사(한 번만 보임).
2. n8n › Credentials › **Header Auth** 새로: 이름 `SGB Uptime Token (X-Uptime-Token)` · Name `X-Uptime-Token` · Value = 1의 토큰.
3. n8n › Credentials › **Telegram**: 급한 알림 봇 토큰(운영 화면 연동 키의 텔레그램 봇과 같은 봇 · 또는 n8n 전용 봇 — decisions #16 「봇 2개」).
4. n8n › Workflows › **Import from File** → `deploy/aws/n8n/uptime-watch.json` → 노드 「Report to SoGaeBank」 · 「Telegram ops」에 2 · 3 자격 증명 연결 · 「Telegram ops」의 chatId 를 운영 대화방 번호로.
5. 「Check targets」의 TARGETS 주소 확인(운영 화면은 허용 IP 밖이면 403 — 403 도 「응답함」으로 봄 · decisions 미정 #4).
6. 한 번 실행(Execute workflow) → 운영 화면 대상 3줄이 「정상」으로 보이는지 → 운영 화면 **「받기 켜기」**(SUPER) → n8n **Active**.
7. 시험: n8n 에서 TARGETS 하나를 없는 주소로 바꿔 두 번 실행 → 운영 알림 UPTIME_DOWN(텔레그램) → 되돌려 한 번 → UPTIME_RECOVERED.

| 무엇 | 비용 · 자원 |
|---|---|
| n8n 실행 | 5분마다 1회 · 하루 288회 · 결과 3줄(자동화 EC2 이미 있음 — 추가 비용 없음으로 봄 · **자동화 EC2 비용은 docs/337 추정 · 최신 확인 필요**) |
| 서버 부담 | 상태 주소 15초 기억 · 보고 하루 288번 × 3줄 INSERT(90일 약 7.8만 줄) |

## 6. 판단
1. **바깥 감시를 서버 안에 두지 않음** — 서버가 죽으면 스스로 알릴 수 없음. n8n 이 「보고 실패」를 알리고, 서버가 살아 있을 때의 판단(연속 실패 · 알림 · 기록)은 서버가 함(#17).
2. **알림이 두 번 가지 않게** — 서버에 닿으면 서버만, 못 닿으면 n8n 만 텔레그램을 보냄(n8n 은 저장 값으로 내려감 · 올라옴 때 한 번씩).
3. 상태 주소는 **기존 /api/v1/health(배포 확인용 · 그대로)와 따로** — 공개 화면용 정보(공지 · 점검)를 더함. 같은 프로세스 15초 기억이라 서버가 여럿이면 최대 15초 늦게 보일 수 있음.
4. 장애 공지 띠는 **점검 중 화면 위에도** 그림(점검 중에 생긴 장애를 알리려고) · 사이트 점검 예약 상자(D239)를 같은 화면 아래에 둠.
5. 공지는 **사람이 씀**(자동 공지 없음) — 잘못된 자동 공지가 회원을 놀라게 하지 않게. UPTIME_DOWN 알림을 받은 당번이 판단해 올림.

## 7. 오류가 날 때 확인 순서
1. 운영 화면 「마지막 n8n 결과」가 비어 있음 → n8n 실행 기록 → 「Report to SoGaeBank」 응답 403 이면 받기 꺼짐(UPTIME_REPORT_OFF) · 토큰 다름(UPTIME_TOKEN_INVALID — 토큰을 새로 만들었으면 n8n 자격 증명도 바꿈).
2. UPTIME_DOWN 이 오지 않음 → 운영 알림 화면에 줄이 있는지 → 있으면 급한 알림 길(메일 · 텔레그램 · 슬랙) 준비 상태(운영 상태 한눈에 「급한 알림 받는 길」).
3. 띠가 안 보임 → 공지의 「띠」 켬 · 끝나지 않음 확인 → 사용자 웹 캐시(최대 60초) → /status 는 30초.
4. 서버가 죽었는데 텔레그램이 안 옴 → n8n 이 켜져 있는지(Active) · Telegram 자격 증명 · chatId.

## 8. 권한
탭 `upt-status`(위험감지 · 따로 적지 않은 탭 = ADMIN · SUPER) · 업무 권한(D258) 업무 `upt-status`(admrsk · R_ADMIN 4단계) · 주소 맵 6줄(/admin/uptime …). 결과 받기 · 공개 상태는 탭이 아니라 주소 맵 없음. 세무사(ACCOUNTANT)는 보지 않음(/admin/acct/ 밖).
