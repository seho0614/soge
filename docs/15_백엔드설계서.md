## 1. 이 백엔드가 다른 곳과 다른 점

**규칙 판정을 서버가 하지 않습니다.**

제한업종·금칙어·한도·불변식은 DB 트리거와 CHECK가 막고, 서비스는 그 예외를 상태코드로 옮깁니다. 그래서 **서비스 코드에 검증 로직이 거의 없습니다.**

```ts
// catalog.service.ts — 업종 승인
async decideCategory(id, dto) {
  return this.db.transaction(async () => {
    const [row] = await this.db.query(`UPDATE categories SET status=$2, labor_law_flag=$3 ...`);
    // A-14 직업안정법 판정 검사가 여기 없습니다. 트리거가 합니다.
  });
}
```

처음 보면 "검증이 빠졌다"고 오해합니다. **의도된 것입니다.** 두 곳에 두면 어긋나고, 어긋나면 어느 쪽이 맞는지 판단할 근거가 없습니다.

## 2. 계층

```
src/
  core/        기초. 도메인 지식 없음
  db/          풀 · 트랜잭션 경계
  common/      DB 예외 → HTTP 매핑
  engines/     규칙이 데이터인 것
  modules/     화면·API 단위
  worker/      배치
  generated/   자동 생성 (codes.ts)
```

**의존 방향은 한쪽입니다.**

```
modules → engines → db → core
```

역방향 import 가 생기면 순환이 시작되고, 그때부터 무엇을 먼저 테스트해야 할지 정할 수 없습니다.

### 계층별 책임

| 계층 | 하는 것 | 하지 않는 것 |
|---|---|---|
| `core` | 컨텍스트 · 오류 · 인증 · 페이지네이션 · 감사 · 멱등성 · 설정 | 도메인 판단 |
| `db` | 커넥션 풀 · 트랜잭션 경계 | 쿼리 작성 |
| `engines` | 귀속 판정 · 노출 정렬 · 자동검수 | 화면 응답 조립 |
| `modules` | 상태 전이 · 응답 DTO | 규칙 재검사 |
| `worker` | 배치 트리거 | 판정 로직 (DB 함수 호출만) |


## 4. 트랜잭션 — 인자로 넘기지 않습니다

### 4-1. 고친 결함

초기 구현은 단일 커넥션을 공유하며 `BEGIN`/`COMMIT` 을 걸었습니다. PostgreSQL 에서 트랜잭션은 커넥션에 속하므로 동시 요청 두 개가 같은 트랜잭션에 들어갑니다.

```
옛 구현: A 유실 — B의 ROLLBACK에 휘말림 (남은 것: 없음)
현재:    A는 커밋 · B만 롤백 (남은 것: A)
```

**A는 아무 잘못이 없는데 사라집니다.** 정산 배치에서 이러면 지급 기록이 없어지고 로그에는 성공으로 남습니다.

### 4-2. 현재 구현

```ts
async transaction<T>(fn: () => Promise<T>): Promise<T> {
  const existing = RequestCtx.get()?.tx;
  if (existing) return fn();              // 중첩은 합류
  const client = await this.pool.connect();  // 전용 커넥션
  await client.query('BEGIN');
  const out = await RequestCtx.withTx(client, fn);
  await client.query('COMMIT');
  return out;
}
```

**`tx` 인자를 없앤 이유** — 인자로 넘기면 한 곳만 빠뜨려도 그 쿼리가 트랜잭션 밖에서 돌고, **컴파일도 테스트도 통과합니다.** 정산에서 이런 누락은 조용히 지나갔다가 나중에 잔액으로 드러납니다.

**중첩을 savepoint 없이 합류시키는 이유** — 안쪽에서 COMMIT 이 나가면 바깥의 실패가 이미 확정된 데이터를 되돌리지 못합니다.

### 4-3. 커넥션 풀

```
태스크 4 × 풀 10 = 40 ≤ RDS max_connections
statement_timeout = 15초
```

스케일 아웃 시 다시 계산하십시오. **커넥션 고갈은 CPU 가 한가한데 응답이 멈추는 형태**라 원인 찾기가 어렵습니다.

## 5. 요청 파이프라인

```
ContextMiddleware   requestId · ip · userAgent
AuthMiddleware      토큰 → principal (DB 재조립)
AuthGuard           @Roles · @RequireGate
ValidationPipe      DTO 검증 (whitelist · forbidNonWhitelisted)
[핸들러]
AuditInterceptor    @Audit → audit.audit_logs
DbErrorFilter       DB 예외 → 422 / 409
```

**순서가 중요합니다.** 컨텍스트가 먼저 열려야 인증이 actor 를 담고, 감사 로그에 누가 했는지가 남습니다.

### 인증 — 토큰을 믿지 않습니다

principal 을 클레임이 아니라 **DB에서 다시 조립**합니다.

```
구독 만료 → 토큰 15분 유효 → 클레임 sub_active=true
                          → DB 재조회 → SUBSCRIPTION_REQUIRED ✅
```

조회 1회 비용보다 "만료됐는데 15분간 통과"가 훨씬 비쌉니다. 반대로 사업자 승인도 즉시 반영돼야 합니다 — 승인받고 15분 기다리게 하면 문의가 옵니다.

### 게이트 3종

| 게이트 | 막는 것 | 근거 |
|---|---|---|
| `IDENTITY_VERIFIED` | 본인인증 전 거래 진입 | INV-7 |
| `BUSINESS_VERIFIED` | 개인 회원의 소개비 수령 | INV-10 |
| `ACTIVE_SUBSCRIPTION` | 구독 없는 코드 발급 | INV-8 |

**게이트는 사용자에게 이유를 알려주는 용도이고 최종 방어선은 DB입니다.** 게이트를 빠뜨려도 데이터는 안전하되 오류 메시지가 불친절해집니다.

## 6. 컨트롤러 작성 규칙

```ts
@Post()
@Roles('BIZ_OWNER', 'BIZ_STAFF')          // 역할
@RequireGate('IDENTITY_VERIFIED')          // 불변식 게이트
@Audit('LISTING_CREATE', 'LISTING')        // 감사 로그
@ApiOperation({ summary, description })     // 문서
@ApiResponse({ status: 422, type: ErrorDto, description: '...' })
create(@Body() dto: CreateListingDto) { ... }
```

**5개가 한 세트입니다.** 하나라도 빠지면 권한이 뚫리거나, 감사 기록이 없거나, 프런트가 스키마를 못 받습니다.

### DTO 규칙

| 항목 | 규칙 |
|---|---|
| 요청 | `class-validator` + `@ApiProperty` 를 같은 필드에 |
| 응답 | 별도 클래스. **엔티티를 그대로 내보내지 않습니다** |
| 열거형 | `@ApiProperty({ enum: [...] })` |
| 설명 | **왜 그런지**를 씁니다 |

```ts
@ApiPropertyOptional({
  description: '30자 미만이면 자동검수를 통과하지 못하고 사람이 봅니다',
})
body?: string;
```

"본문"이 아니라 이렇게 씁니다. **프런트가 UX를 설계하는 근거**가 됩니다.

## 7. 오류 규약

| 상태 | 의미 | 프런트 |
|---|---|---|
| 400 | 형식 오류 | 입력 고치기 |
| 403 | 권한·게이트 | 인증·전환 유도 |
| **409** | 상태 충돌 | **재시도 무의미** |
| **422** | 정책 위반 | 안내 후 다른 값 |

### DB 예외 매핑

| DB 예외 | HTTP | code |
|---|---|---|
| `RESTRICTED_CATEGORY: ...` | 422 | `RESTRICTED_CATEGORY` |
| `INV-n violated: ...` | 422 | `INV_n` |
| `view quota exceeded` | 422 | `VIEW_QUOTA_EXCEEDED` |
| `listing slot limit reached` | 422 | `LISTING_SLOT_LIMIT` |
| `A-14: ...` | 422 | `LABOR_LAW_CHECK_REQUIRED` |
| `append-only table: ...` | 409 | `IMMUTABLE_RECORD` |
| 0행 UPDATE | 409 | `VERSION_CONFLICT` · `ALREADY_DECIDED` |

**`message` 는 사용자에게 그대로 보여도 되는 문장**입니다. 제한업종 차단 문구는 `restricted_industries.block_message` 에서 오므로 관리자가 바꿀 수 있습니다.

## 8. 자동 처리 — 응답으로 알립니다

```json
POST /listings
{ "listingId": "...", "status": "PUBLISHED", "autoApproved": true }
```

자동검수를 통과하면 `IN_REVIEW` 가 아니라 **바로 `PUBLISHED`** 로 옵니다. 프런트는 `autoApproved` 로 분기해 "검수 요청됨" 대신 "등록 완료 · 노출 중"을 띄웁니다.

계약 서명도 같습니다. **두 번째 서명 응답에 성사 확정과 정산 신청 결과가 함께 담깁니다.**

## 9. 워커

```
EventBridge → POST /admin/jobs { job }  → SchedulerService.run()
                                         → DB 함수 호출
```

**앱 내 cron 을 쓰지 않습니다.** ECS 태스크가 2개면 두 번 실행됩니다.

**판정 로직이 DB 함수에 있으므로 워커가 죽어도 규칙은 그대로입니다.** 워커는 트리거일 뿐입니다.

| job | 하는 일 |
|---|---|
| `sla_alert` `expire_badges` | 매시간 |
| `attribution_archive` `pii_purge` | 매일 03:00 |
| `deal_auto_confirm` | 7일 무응답 자동 확정 (B-01) |
| `promo_expiry` | D-14 고지 (B-14) |
| `settlement_batch` | **이체 전 불변식 전건 재대조** |
| `k_alert` | 월 1회 |

모든 잡은 멱등합니다. `settlement_batch` 는 위반이 하나라도 있으면 **이체하지 않고 CRITICAL 경보**를 남깁니다.

## 10. 테스트 전략

| 층 | 방법 |
|---|---|
| 불변식 | **실 PostgreSQL** — `verify-invariants.sh` 127건 |
| 동시성 | 겹쳐 실행하고 결과 확인 — 3건 |
| 문서 정합성 | `verify-docs.js` 22건 |
| 부팅 | `smoke-boot.ts` — 라우트 113건 · 중복 검사 |

**목 DB 를 쓰지 않습니다.** 이 시스템의 규칙 대부분이 트리거와 CHECK에 있어서, 목으로 테스트하면 아무것도 검증되지 않습니다.

### 부팅 스모크가 왜 필요한가

컨트롤러를 `app.module.ts` 에 등록하지 않아도 **타입 검사와 문서 생성은 통과합니다.** 실제로 컨트롤러 7개가 배선되지 않은 상태로 있었고, 앱을 띄우면 라우트가 0건이었습니다.

```

```

## 11. 코딩 규약 8가지

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 상태 전이는 도메인 서비스 한 곳에서만 | 컨트롤러에서 `status = ...` 를 쓰면 규칙이 흩어집니다 |
| 2 | append-only 테이블에 update/delete 메서드 금지 | DB가 막지만 컴파일 타임이 낫습니다 |
| 3 | 금액은 DB `NUMERIC` ↔ 응답 정수. `Float` 금지 | 정산에서 원 단위가 틀립니다 |
| 4 | 검사를 DB와 앱 양쪽에 두지 않음 | 어긋나면 어느 쪽이 맞는지 알 수 없습니다 |
| 5 | `tx` 인자 전달 금지 | 한 곳만 빠뜨려도 트랜잭션 밖에서 돕니다 |
| 6 | 엔티티를 그대로 응답하지 않음 | 컬럼 추가가 곧 API 변경이 됩니다 |
| 7 | 커서 페이지네이션만. offset 금지 | 검수 큐에서 항목을 건너뜁니다 |
| 8 | DB 변경은 2단계 배포 | 정산 데이터는 롤백이 불가능합니다 |
