# 728. 무중단 반영 설계 (v10.586 · 2026-11-21 · 14차 운영 ② · 문서만)

> 대표 11/21 「모두 개발진행」. **설계 문서만** — 코드 · 서버 · 설정은 바꾸지 않습니다. 실제로 옮길지 · 언제 할지는 대표 결정(비용이 듭니다).
> 지금 구성: 운영 서버 1대(EC2 · pm2 `sgb` · `sgb-site` · `sgb-jobs`) + RDS 1개 · 반영은 사람이 `precheck.sh → 스냅샷 → apply.sh → postcheck.sh`.

## 1. 결론

- **가장 맞는 방법: 「서버 2대 + ALB(부하 분산기) + 한 대씩 갈아끼우기(롤링)」** — 블루/그린보다 싸고, 지금 apply.sh 의 「새 판 폴더 → 바로가기 교체 → 기동 확인 → 안 되면 자동 복귀」를 서버마다 그대로 쓸 수 있습니다.
- 먼저 고쳐야 할 것 **세 가지**(이것 없이 2대로 늘리면 오히려 고장): ① 올린 파일을 서버 디스크 → **S3**(이미 코드가 `S3_BUCKET` 을 읽음) ② 배치 호출기 `sgb-jobs` 는 **한 대에서만**(EventBridge 로 옮기거나 한 대만 띄움 — `job_runs UNIQUE` 라 둘이 돌아도 한 번만 실행되지만 부하 · 기록이 겹침) ③ **마이그레이션 앞뒤 호환 규칙**(아래 4절)을 지금부터 지킴.
- 한 번에 옮기지 않고 **1단계(규칙만 · 0원) → 2단계(S3 · EventBridge) → 3단계(2대 · ALB)** 로 나눕니다.

## 2. 비교

| 방식 | 끊김 | 비용(대략 · 확인 필요) | 되돌리기 | 이 프로젝트에 |
|---|---|---|---|---|
| 지금(1대 · pm2 다시 띄움) | pm2 재시작 몇 초 ~ 사이트 빌드 교체 수십 초 | 0 | 판 폴더 · rollback.sh | 그대로 두면 됨 |
| **롤링(2대 · ALB)** | 없음(한 대씩 빼고 넣음) | EC2 1대 더 + ALB 시간 · 처리량 요금 | 한 대씩 이전 판으로 | **추천** |
| 블루/그린(2벌 통째) | 없음 · 바꾸는 순간만 | 반영 동안 2배 | 묶음째 즉시 | 서버 1대 규모에 과함 |
| 한 서버 안 포트 두 개(pm2 두 벌 + Nginx upstream) | 거의 없음 | 메모리 2배(지금 3.5GB 전제 · 빠듯) | 포트 바꾸기 | 임시안 — 메모리 · 디스크가 같은 서버라 위험 |

> 비용 · 요금은 AWS 서울 리전 최신 값으로 **확인이 필요합니다**(이 문서는 구조만 정함).

## 3. 서버 2대 구조 · 순서

```
            ┌──────── ALB(HTTPS 인증서 · 상태 확인 /api/v1/health) ────────┐
            │                                                              │
     서버 A: Nginx → sgb(API) · sgb-site(Next) · 운영 화면 정적          서버 B: 같은 것
            │                                                              │
            └────────────── RDS(하나) · S3(올린 파일) · EventBridge → 배치 1곳 ┘
```

### 한 번 반영 순서(롤링)
1. `precheck.sh`(한 대에서) → RDS 스냅샷 → **마이그레이션만 먼저**(앞뒤 호환이라 옛 판 서버가 그대로 돎) — `apply.sh` 3단계를 따로 떼는 옵션이 필요(지금은 한 흐름).
2. 서버 A 를 ALB 대상에서 **빼기**(draining · 열린 요청이 끝날 때까지 최대 60초).
3. 서버 A 에 `apply.sh`(설치 · 빌드 · 바로가기 교체 · 기동 확인) — 실패하면 A 는 옛 판으로 자동 복귀 · ALB 에 다시 넣고 멈춤.
4. A 상태 확인 통과 → ALB 에 다시 넣기 → 몇 분 지켜보기(서버 오류 묶음 · 화면 속도 · 운영 알림).
5. 서버 B 같은 순서.
6. `postcheck.sh` · 화면 확인. 다음 판에서 「뒤 정리」 마이그레이션(옛 칸 지우기 등)을 할 수 있음.

### 되돌리기
- 마이그레이션이 앞뒤 호환이면 **코드만** 서버마다 `rollback.sh`(옛 판 폴더로) — DB 는 그대로.
- 마이그레이션이 깨지는 변경이었다면(규칙 위반) 스냅샷 복원이 필요 → 4절 규칙으로 막음.

## 4. 마이그레이션 앞뒤 호환 규칙(1단계 · 지금부터 · 0원)

「옛 판 코드」와 「새 판 코드」가 **같은 DB 에서 동시에** 몇 분 돌 수 있어야 합니다(롤링 중 · 되돌린 뒤).

| 하고 싶은 것 | 한 판에 하면 안 됨 | 이렇게 나눔(넓히기 → 옮기기 → 좁히기) |
|---|---|---|
| 칸 더하기 | NOT NULL 기본값 없음 | `ADD COLUMN … NULL` 또는 `DEFAULT` 있게 → 다음 판에서 NOT NULL |
| 칸 이름 바꾸기 | `RENAME COLUMN` | 새 칸 더하기 · 두 칸에 같이 쓰기(트리거 또는 코드) → 다음 판 새 칸만 읽기 → 그다음 판 옛 칸 지우기 |
| 칸 · 표 지우기 | 쓰던 판이 남아 있는데 `DROP` | 코드가 안 쓰는 판을 먼저 반영 → 다음 판에서 지우기 |
| CHECK · 값 목록 좁히기 | 옛 값이 들어올 수 있는데 바로 좁힘 | 새 코드 반영 · 옛 값 정리 → 다음 판에서 좁히기(넓히기는 한 판에 괜찮음) |
| 함수 · 뷰 인자 바꾸기 | 같은 이름 인자 바꿈 | 새 이름(또는 인자 더 받는 판) 더하기 → 옛 것은 다음 판에 |
| 큰 표 인덱스 | `CREATE INDEX`(쓰기 막힘) | `CREATE INDEX CONCURRENTLY`(마이그레이션 실행기가 트랜잭션 밖으로 돌릴 수 있어야 — 지금 migrate.js 확인 필요) |
| 트리거 · 설정 기본값 | 옛 코드가 모르는 값으로 바꿈 | 스위치는 늘 「처음 off」 · 옛 코드가 무시해도 되는 모양 |

- 지금도 마이그레이션은 「다시 돌려도 같음 · 지우는 문장 없음」 규칙이 있어 대부분 넓히기입니다. 추가로 **판 문서에 「앞뒤 호환: 예 / 아니오(까닭)」 한 줄**을 넣고, `tools/ops-doc-draft.py` 가 마이그레이션에서 `DROP COLUMN · RENAME · ALTER … SET NOT NULL · DROP FUNCTION` 을 찾아 경고하게 하는 것을 다음 판 후보로 둡니다.

## 5. 세션 · 메모리에 든 것(2대가 되면 서버마다 따로)

| 무엇 | 지금 있는 곳 | 2대에서 | 할 일 |
|---|---|---|---|
| 로그인 증표 | JWT(서명 키 .env) · `accounts.token_version` | 두 서버가 같은 키면 그대로 | `.env` 서명 키를 두 서버 같게(비밀 관리자) |
| 2단계 · 패스키 · 접속 인증 설정 | DB + 서버 메모리 캐시 몇십 초 | 서버마다 캐시 · 바꾼 뒤 몇십 초 차이 | 그대로 둠(짧음) · 문서에 적기 |
| 요청 한도(API · 사용 통계 · 화면 속도) | 서버 메모리(1분 · IP 지문) | 서버마다 따로 → 한도가 사실상 2배 | 처음엔 그대로 · 필요하면 한도 절반 또는 Nginx · ALB 단 |
| 서버 오류 · 느린 응답 · 보안 정책 보고 | 서버 메모리 → 10분마다 DB(D204 · D191) | 서버마다 쌓아 각자 DB 에 더함(UPSERT 라 합쳐짐) | 「지난 1시간」 화면은 그 서버 것만 — 화면에 서버 이름 표시 필요 |
| 오류 몰림 · 느린 응답 알림 | 서버 메모리 10분 건수 | 한 서버 몫만 보고 판단 | 기준을 DB 합계로(서버 오류는 D204 표로 셀 수 있음) |
| 올린 파일 | `UPLOAD_DIR`(서버 디스크) | **다른 서버에서 안 보임** | **S3 로 먼저**(env `S3_BUCKET` · 옮기기는 이미 있는 `deploy/aws/files-to-s3.sh`(docs/229 · check → copy → verify → apply)) |
| 배치(`sgb-jobs`) | 서버마다 pm2 | 두 번 부름(한 번만 실행되지만 낭비) | EventBridge 한 곳 또는 한 서버에만 `SKIP_JOBS=1` 반대로 |
| 사용자 웹(Next) 빌드 | 서버마다 `next build` | 빌드 번호가 서버마다 달라 화면 조각 불러오기 실패 가능 | 같은 킷 · 같은 빌드 산출물을 두 서버에 복사(한 곳에서 빌드) 또는 ALB 고정 세션(짧게) |
| Nginx 운영 화면 허용 IP | 서버의 `/etc/nginx/sites-enabled/sgb` | 두 서버 모두 · ALB 뒤에서는 진짜 IP 가 `X-Forwarded-For` | `set_real_ip_from` ALB 대역 · 허용 IP 반영 스크립트를 두 서버에 |

## 7. 위험 · 확인할 것

1. 지금 운영 서버는 개발 서버와 **같은 디스크 · 같은 기계**(메모) — 2대 구성은 운영을 개발과 떼는 「운영 전환 때 서버 다시 설계」(CLAUDE.md)와 함께 하는 것이 맞습니다.
2. ALB 를 쓰면 외부 연동 신청 발신 IP(3.37.95.217 · 바꾸지 않음)가 **나가는** 쪽은 그대로여야 함 — 나가는 연결은 NAT · 탄력 IP 설계 필요(**추가 확인이 필요합니다**).
3. `migrate.js` 가 `CONCURRENTLY` 를 트랜잭션 밖에서 돌릴 수 있는지 확인 필요.
4. 두 서버의 시각 · 시간대가 같아야 함(정기 작업 · 한국 날짜 셈).
